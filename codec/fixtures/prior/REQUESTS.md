### 10. The nine deferred operations are answered, not broken

**Closes:** nothing to edit; the adapter's reading of `codec/schemas/protocol.schema.json` (its `description`) and `codec/src/cli/ops.ts` lines 91, 112 and 294. Preferred form: none needed.

The protocol schema names fourteen operations. ### The replay and recovery contract Prior's adapter relies on

- **The sequence.** Every mutation runs one order: workbench state; the workbench write lock; sweep of transient entries; recovery of every pending intent; the replay lookup; the operation's plan function (reads, `expected_revision` against the stored bytes, the operation's rules, schema validation of every record it would write); the durable intent; each write by temp file, fsync and rename; the stored answer; the intent's removal.
- **The intent is the commit point.** It is the directory `.json-state/journal/<operation_id>/`, built under a dot name and committed by one rename. Before the rename nothing is written and nothing stored, so a retry is an ordinary first attempt. After it the operation lands, on this attempt or through recovery on a later one.
- **An unknown outcome is resolved by any later request.** When the adapter returns `ErrCodecOutcomeUnknown` (killed, deadline, malformed output), the next mutation of any kind recovers every pending intent under the lock before its own work, and a read that finds a pending intent whose files are all at pre or post takes the lock and recovers before it reads. A `show` therefore tells the host which state holds, and an identical retry returns the stored answer when the first attempt passed the commit point or runs as a first attempt when it did not. Whether the adapter retries on its own stays Prior's rule ("uncertain process outcomes without automatic retry"); the codec makes a `show` and a deliberate identical retry both safe.
- **Identical retry answered, divergent refused.** Replay equality is FJ01's comparison of the key-sorted request, now held as a `sha256:` digest: the same `operation_id` and the same request answer the stored response byte for byte; the same id with any other request is `conflict/operation-id-reused` and writes nothing. The digest covers every field, `workbench` included, so a workbench copied to another path answers a replay of an old id `operation-id-reused`, not the stored answer.
- **Fresh id against the old revision refused.** A new `operation_id` sent with the revision the first attempt started from is `conflict/revision-mismatch` once that attempt landed, so nothing runs twice.
- **`recovery-blocked` and what it means.** Recovery reads each file an intent names by three hashes, post first: at post it has landed, at pre (or absent where it is to be created) it has not and the staged bytes are written, at neither a hand edit or a pull intervened. A live writer's files are only ever at pre or post. A file at neither blocks the intent: the kernel leaves file and intent exactly as they stand and never overwrites either. A request that reads or writes a path a blocked intent names is `operation-unknown/recovery-blocked` naming the intent and the diverged path; a request reusing the blocked intent's id is `recovery-blocked` when it is the same request (the stored response would report a state the files do not hold) and `conflict/operation-id-reused` when it is not. Two hand corrections clear it, and the kernel performs neither: restore the file to its pre-bytes, after which the next request rolls forward; or delete the intent directory and accept the writes that had landed. `reconcile` lists the per-file state.
- **The read protocol.** A read takes no lock unless a writer may be mid-flight: it lists `journal/` then `ops/`, ignoring dot-named entries, reads, lists both again in that order, and retries on a difference. A blocked intent is classified without the lock and is a stable member of both listings, so it no longer sends every later read through the lock. A read that must wait for a live writer can reach the host's deadline before the codec's own `conflict/lock-timeout`; it has no effect either way.
- **Local state, not protocol.** The stored answer is `.json-state/ops/<operation_id>.json` as `{operation_id, op, request_digest, response}`; an answer the FJ01 bundle stored (`{operation_id, request, response}`) is still read, by digesting its `request`. No file under `.json-state/` carries a request body. `ops/` is not pruned (request 21).

### The lock

- **One file for the whole workbench:** `.json-state/write.lock`, content `pid: <n>\nhost: <hostname>\nnonce: <random>\nacquired_at: <iso>\n`, created by linking a complete file to the name, so every lock this codec writes records its PID. FJ01's per-record `.json-state/<sha256 of the record path>.lock` is neither written nor read by the FJ02 bundle.
- **A dead holder on the same host is replaced at once.** A lock of this host, or one recording no host (FJ01's format), is stale the moment its PID is dead, with no age condition, and live while the PID answers. A writer killed by the adapter's SIGKILL of the process group (`codec_process.go` line 108) no longer stalls the workbench for 60 s: the next request replaces its lock and lands. Only a lock recording no PID at all is stale by age, after 60 s. A stale lock is never unlinked: the one waiter that creates the takeover claim for that instance (`write.lock.takeover.<hash>`) renames its own lock over the name, so no waiter removes a lock it did not judge.
- **Another host's lock never.** A PID means nothing off the host that recorded it; the waiter answers `conflict/lock-timeout` after its wait (65 s by default), naming the holder and its host, and such a lock is removed by hand once its holder is known to be gone.
- **The live-owner behaviour Prior tests is unchanged:** a live PID keeps the codec waiting whatever the lock's age, and the lock's bytes and the record stay as they were. ### 21. The retention of `.json-state/ops/`

**Closes:** the retention of stored answers, unbounded in FJ02 (`codec/README.md` `## The kernel and the journal`). Preferred form: a reply.

`ops/` grows by one small file per landed mutation and is never pruned. A pruned answer turns a later identical retry into a first attempt, which the CAS refuses (`conflict/revision-mismatch`, or `conflict/record-exists` for a `create`), so pruning is safe for replay. It is not free for reads: the read protocol accepts a lock-free read when the id set of `journal/` and `ops/` is equal before and after, which holds because `ops/` only grows, so a bound means pruning under the lock and a change to how reads compare.
