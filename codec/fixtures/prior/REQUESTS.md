### 10. The nine deferred operations are answered, not broken

**Closes:** nothing to edit; the adapter's reading of `codec/schemas/protocol.schema.json` (its `description`) and `codec/src/cli/ops.ts` lines 91, 112 and 294. Preferred form: none needed.

The protocol schema names fourteen operations. ### The replay and recovery contract Prior's adapter relies on

- **The sequence.** Every mutation runs one order: workbench state; the workbench write lock; sweep of transient entries; recovery of every pending intent; the replay lookup; the operation's plan function (reads, `expected_revision` against the stored bytes, the operation's rules, schema validation of every record it would write); the durable intent; each write by temp file, fsync and rename; the stored answer; the intent's removal.
- **The intent is the commit point.** It is the directory `.json-state/journal/<operation_id>/`, built under a dot name and committed by one rename. Before the rename nothing is written and nothing stored, so a retry is an ordinary first attempt. After it the operation lands, on this attempt or through recovery on a later one.
- **An unknown outcome is resolved by any later request.** When the adapter returns `ErrCodecOutcomeUnknown` (killed, deadline, malformed output), the next mutation of any kind recovers every pending intent under the lock before its own work, and a read that finds a pending intent whose files are all at pre or post takes the lock and recovers before it reads. A `show` therefore tells the host which state holds, and an identical retry returns the stored answer when the first attempt passed the commit point or runs as a first attempt when it did not. Whether the adapter retries on its own stays Prior's rule ("uncertain process outcomes without automatic retry"); the codec makes a `show` and a deliberate identical retry both safe.
- **Identical retry answered, divergent refused.** Replay equality is FJ01's comparison of the key-sorted request, now held as a `sha256:` digest: the same `operation_id` and the same request answer the stored response byte for byte; the same id with any other request is `conflict/operation-id-reused` and writes nothing. The digest covers every field, `workbench` included, so a workbench copied to another path answers a replay of an old id `operation-id-reused`, not the stored answer.
- **Fresh id against the old revision refused.** A new `operation_id` sent with the revision the first attempt started from is `conflict/revision-mismatch` once that attempt landed, so nothing runs twice.
- **`recovery-blocked` and what it means.** Recovery reads each file an intent names by three hashes, post first: at post it has landed, at pre (or absent where it is to be created) it has not and the staged bytes are written, at neither a hand edit or a pull intervened. A live writer's files are only ever at pre or post. A file at neither blocks the intent: the kernel leaves file and intent exactly as they stand and never overwrites either. A request that reads or writes a path a blocked intent names is `operation-unknown/recovery-blocked` naming the intent and the diverged path; a request reusing the blocked intent's id is `recovery-blocked` when it is the same request (the stored response would report a state the files do not hold) and `conflict/operation-id-reused` when it is not. Two hand corrections clear it, and the kernel performs neither: restore the file to its pre-bytes, after which the next request rolls forward; or delete the intent directory and accept the writes that had landed. `reconcile` lists the per-file state.
- **The read protocol.** A read takes no lock unless a writer may be mid-flight: it lists `journal/` then `ops/`, ignoring dot-named entries, reads, lists both again in that order, and retries on a difference. A blocked intent is classified without the lock and is a stable member of both listings, so it no longer sends every later read through the lock. A read that must wait for a live writer can reach the host's deadline before the codec's own `conflict/lock-timeout`; it has no effect either way.
- **Local state, not protocol.** The stored answer is `.json-state/ops/<operation_id>.json` as `{operation_id, op, request_digest, response}`; an answer the FJ01 bundle stored (`{operation_id, request, response}`) is still read, by digesting its `request`. No file under `.json-state/` carries a request body. `ops/` is not pruned (request 21).

### The lock

- **One file for the whole workbench:** `.json-state/write.lock`, content `pid: <n>\nhost: <hostname>\nnonce: <random>\nacquired_at: <iso>\n`, created by linking a complete file to the name, so every lock this codec writes records its PID. FJ01's per-record `.json-state/<sha256 of the record path>.lock` is neither written nor read by the FJ02 bundle.
- **A dead holder on the same host is replaced at once.** A lock of this host, or one recording no host (FJ01's format), is stale the moment its PID is dead, with no age condition, and live while the PID answers. A writer killed by the adapter's SIGKILL of the process group (`codec_process.go` line 108) no longer stalls the workbench for 60 s: the next request replaces its lock and lands. Only a lock recording no PID at all is stale by age, after 60 s. A stale lock is never unlinked: the one waiter that creates the takeover claim for that instance (`write.lock.takeover.<hash>`) renames its own lock over the name, so no waiter removes a lock it did not judge.

2. **Plan progress through `transition` (request 18).** No fifteenth operation. A `transition` on a plan record reads `payload.steps` and `payload.criteria` as updates keyed by the `id` of an entry the stored plan already has. The checks run in this order after the CAS, and each refuses with nothing written. First, `steps` or `criteria` sent for a record that is not a plan is `schema-invalid/payload-field-not-admitted`. Second, the state: when `to` differs from the stored state, or the payload carries neither field, the move is the table's edge exactly as at FJ02; when `to` equals the stored state and the payload carries progress, a terminal plan (`closed`, `deferred`) is `conflict/transition-refused`. Third, the ids: an id repeated in the payload, or in the stored array the payload updates, is `schema-invalid/duplicate-step-id` or `duplicate-criterion-id`, and an id the stored plan lacks is `unresolved-reference/unknown-step-id` or `unknown-criterion-id`. ### What landed

1. **The record client** (`hooks/lib/record-client.ts`, `16a6387e`). This is the Claude side's counterpart of Prior's `CodecProcess`. `ask` starts the bundle beside the compiled module through `process.execPath`, in the bundle's directory and with an empty environment. It writes one request naming the workbench by absolute path, reads one response, and hands back one of three answers: `result` (with `revisions`), `refused` (class, reason, detail) or `unanswered` (`bundle-missing`, `exit`, `timeout`, `unparseable`). One process runs per request, with no retry, and the timeout is 70 s, above the codec's 65 s lock wait, so a typed `conflict/lock-timeout` arrives first. A caller never reads `refused` or `unanswered` as an empty store.
2. **The format gate** (`gate` in the same module). It sends `inspect` before any other request. On `json-control` it hands back the workbench id. Otherwise it hands back the state by name (`legacy`, or `unsupported` with the codec's diagnosis), `refused` or `unanswered`. This is the rule item 28 described as the one fusion applies meanwhile, and every FJ03a consumer asks it first. The Claude side sends four operations in all: `inspect`, `list`, `show` and `reconcile`.
3. **Scope: `bin/fusion-claimed-package`** (`hooks/lib/scope.ts` through the entry `hooks/scope.ts`, `3516d7a2`). A package is this checkout's when its `status` is `claimed` and its `claim.checkout_id` equals the identifier `bin/fusion-identity` prints. The sequence runs the gate, then `list`, then `show` of each claimed row at the revision `list` named. When a revision moved between the two, the read starts over from `list` once: that is a new observation and not a retry, and a second difference is `store-changing`. Output and exit table are unchanged. Exit 0 prints `PACKAGE=` and `CONTAINER=`, or nothing when no package is held. Exit 1 means no workbench, or `bin/fusion-identity` stopped. Exit 2 is a usage error. Exit 3 means the item in scope cannot be determined, with nothing on stdout and no fall back to the shared store. Exit 3 gains its causes by name: two or more claims naming this checkout (each named), `legacy`, `unsupported`, a read the codec refused (`recovery-blocked` among them, as a typed refusal or as a `problem` row inside an `ok: true` list), a read it did not answer, a package row that does not read, and `store-changing`. `bin/fusion-stores` and the v11 container root are no longer consulted. `bin/fusion-paths <agent> <item-dir>` asks the same entry whether the directory names a package: exit 1 when it names none, exit 3 when the workbench is refused.
4. **Order: `bin/fusion-work-order`** (`hooks/lib/work-graph.ts` through `hooks/order.ts`, `8afcc242`). The reader gates, sends `list`, then sends `reconcile`. It reads `reconcile`'s `records` findings before its `dependencies`, and places each dependency entry by the table in the module header. The graph algorithm (Tarjan, Kahn, depth, blocks, the paused override) is the pure `orderOf` and is unchanged. The hook side evaluates no dependency condition; `reconcile`'s `dependencySatisfied` is the one implementation. A dependency on a terminal package under `terminal` is satisfied and prints no row. A dependency on a dropped package under `succeeded` blocks the dependent and prints an `unmet=` row. The exit codes are 0 (the check ran; a cycle and `verdict=empty` are answers), 1 (usage), 2 (no workbench), 3 (the compiled hooks or the bundle missing) and 4, which is new. Exit 4 means the workbench was not read: the state or refusal goes on stderr and nothing goes on stdout. The `note=` line says, as Prior's review asked under `## Order output and activation`, that a satisfied terminal target is now told apart from an unresolved one, that an unresolved prerequisite is no proof that the condition holds, and that the report authorises no dispatch.

### Recovery and rollout consequences

The FJ02b section above says FJ03's consumers on the Claude side must honour the three statements of `Prior: docs/design/fusion-fj02-prior-response.md` `## Recovery and rollout consequences`. FJ03a honours each as follows.

- **A read may finish a committed intent.** The declaration stands in the header of `hooks/lib/record-client.ts` and in `README-hooks.md` `## Concept`, as item 30 quotes it. What the Claude side declares is the absence of new mutation requests from a reader, not a write-free read. The recovery is admitted for a helper somebody called and for nothing else. No automatic hook reaches the client, by import or by subprocess, and `hooks/lib/__tests__/hook-route-exclusion.test.ts` pins that on every command `hooks/hooks.json` configures. Neither resolver deletes an intent or repairs divergent bytes. `recovery-blocked` stops both with a named failure.
- **One compatible codec pin per workbench.** The client resolves the bundle relative to its own compiled module, so an install runs the bundle it shipped with and a work tree runs its own. There is no upward walk and no environment variable that could hand a request to another tree's bundle. One install therefore carries one bundle. A workbench is served by one pin as long as the installations writing to it agree on the release, which the activation window of item 26 governs.
- **No FJ01 writer beside a later one.** The Claude side has no FJ01 writer. No Claude-side code sent a mutation before FJ03a, and FJ03a sends none: the four operations of item 2 are reads. The only Claude-side writers of the codec are the test helpers, which run against temporary workbenches, and the recorded sessions under `codec/fixtures/`.

**Claim ownership under response 22.** FJ03a sends no `claim`, `release` or `transition`. The ownership check that Prior's option (a) places on the host is therefore not exercised on the Claude side yet: deciding ownership from `show` and sending that record's revision as `expected_revision`. FJ03c's write client is the first Claude-side caller that exercises it. Scope resolution reads a claim as the assignment it is, and whether its holder is authorised stays the host's question.
