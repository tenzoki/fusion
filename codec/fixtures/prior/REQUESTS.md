### 10. The nine deferred operations are answered, not broken

**Closes:** nothing to edit; the adapter's reading of `codec/schemas/protocol.schema.json` (its `description`) and `codec/src/cli/ops.ts` lines 91, 112 and 294. Preferred form: none needed.

The protocol schema names fourteen operations. ### The replay and recovery contract Prior's adapter relies on

- **The sequence.** Every mutation runs one order: workbench state; the workbench write lock; sweep of transient entries; recovery of every pending intent; the replay lookup; the operation's plan function (reads, `expected_revision` against the stored bytes, the operation's rules, schema validation of every record it would write); the durable intent; each write by temp file, fsync and rename; the stored answer; the intent's removal.
- **The intent is the commit point.** It is the directory `.json-state/journal/<operation_id>/`, built under a dot name and committed by one rename. Before the rename nothing is written and nothing stored, so a retry is an ordinary first attempt. After it the operation lands, on this attempt or through recovery on a later one.
- **An unknown outcome is resolved by any later request.** When the adapter returns `ErrCodecOutcomeUnknown` (killed, deadline, malformed output), the next mutation of any kind recovers every pending intent under the lock before its own work, and a read that finds a pending intent whose files are all at pre or post takes the lock and recovers before it reads. A `show` therefore tells the host which state holds, and an identical retry returns the stored answer when the first attempt passed the commit point or runs as a first attempt when it did not. Whether the adapter retries on its own stays Prior's rule ("uncertain process outcomes without automatic retry"); the codec makes a `show` and a deliberate identical retry both safe.
- **Identical retry answered, divergent refused.** Replay equality is FJ01's comparison of the key-sorted request, now held as a `sha256:` digest: the same `operation_id` and the same request answer the stored response byte for byte; the same id with any other request is `conflict/operation-id-reused` and writes nothing. The digest covers every field, `workbench` included, so a workbench copied to another path answers a replay of an old id `operation-id-reused`, not the stored answer.
- **Fresh id against the old revision refused.** A new `operation_id` sent with the revision the first attempt started from is `conflict/revision-mismatch` once that attempt landed, so nothing runs twice.
- **`recovery-blocked` and what it means.** Recovery reads each file an intent names by three hashes, post first: at post it has landed, at pre (or absent where it is to be created) it has not and the staged bytes are written, at neither a hand edit or a pull intervened. A live writer's files are only ever at pre or post. A file at neither blocks the intent: the kernel leaves file and intent exactly as they stand and never overwrites either. A request that reads or writes a path a blocked intent names is `operation-unknown/recovery-blocked` naming the intent and the diverged path; a request reusing the blocked intent's id is `recovery-blocked` when it is the same request (the stored response would report a state the files do not hold) and `conflict/operation-id-reused` when it is not. Two hand corrections clear it, and the kernel performs neither: restore the file to its pre-bytes, after which the next request rolls forward; or delete the intent directory and accept the writes that had landed. `reconcile` lists the per-file state.
- **The read protocol.** A read takes no lock unless a writer may be mid-flight: it lists `journal/` then `ops/`, ignoring dot-named entries, reads, lists both again in that order, and retries on a difference. A blocked intent is classified without the lock and is a stable member of both listings, so it no longer sends every later read through the lock. A read that must wait for a live writer can reach the host's deadline before the codec's own `conflict/lock-timeout`; it has no effect either way.
- **Local state, not protocol.** The stored answer is `.json-state/ops/<operation_id>.json` as `{operation_id, op, request_digest, response}`; an answer the FJ01 bundle stored (`{operation_id, request, response}`) is still read, by digesting its `request`. No file under `.json-state/` carries a request body. `ops/` is not pruned (request 21).

### The lock

- **One file for the whole workbench:** `.json-state/write.lock`, content `pid: <n>\nhost: <hostname>\nnonce: <random>\nacquired_at: <iso>\n`, created by linking a complete file to the name, so every lock this codec writes records its PID. FJ01's per-record `.json-state/<sha256 of the record path>.lock` is neither written nor read by the FJ02 bundle.
- **A dead holder on the same host is replaced at once.** A lock of this host, or one recording no host (FJ01's format), is stale the moment its PID is dead, with no age condition, and live while the PID answers. A writer killed by the adapter's SIGKILL of the process group (`codec_process.go` line 108) no longer stalls the workbench for 60 s: the next request replaces its lock and lands. Only a lock recording no PID at all is stale by age, after 60 s. A stale lock is never unlinked: the one waiter that creates the takeover claim for that instance (`write.lock.takeover.<hash>`) renames its own lock over the name, so no waiter removes a lock it did not judge.

2. **Plan progress through `transition` (request 18).** No fifteenth operation. A `transition` on a plan record reads `payload.steps` and `payload.criteria` as updates keyed by the `id` of an entry the stored plan already has. The checks run in this order after the CAS, and each refuses with nothing written. First, `steps` or `criteria` sent for a record that is not a plan is `schema-invalid/payload-field-not-admitted`. Second, the state: when `to` differs from the stored state, or the payload carries neither field, the move is the table's edge exactly as at FJ02; when `to` equals the stored state and the payload carries progress, a terminal plan (`closed`, `deferred`) is `conflict/transition-refused`. Third, the ids: an id repeated in the payload, or in the stored array the payload updates, is `schema-invalid/duplicate-step-id` or `duplicate-criterion-id`, and an id the stored plan lacks is `unresolved-reference/unknown-step-id` or `unknown-criterion-id`. | `path` | the workbench-relative control path, as the protocol's `record_selector` defines it | the request, or the answer |
| `kind` | the record's kind (`package`, `issue`, `plan`, `discussion`, `decision`, `evidence`), never the operation's | that `show`; for `create`, the request |
| `revision` | this path's entry in the answer's `revisions` map | the answer |
| `change` | per operation, below | the answer and the request |
| `person`, `checkout`, `session_id` | who wrote it | the host's identity; see (b) |

No answer carries a `record_id`. Requests name a record by `path`. `change`, per operation:

| Operation | `change` |
|---|---|
| `transition`, `claim`, `release` | `{from, to}` |
| `create` | `{created: <status>}` |
| `set-mode` | `{mode}` |
| `set-dependencies` | `{depends_on: <count>}` |
| `adopt-plan` | `{adopted: <role>}` on the package row, `{adopted_as: <role>}` on the document row, `{replaced_by: <record_id>}` on the replaced plan's row |

A row that moves no status carries no `from` or `to`; it does not repeat the old status. `adopt-plan` writes the package, the document and, where it replaces a live plan, that plan, in one intent, so it gives two or three rows sharing one `operation_id`. **What the monitor does with it.** The panel's work item is a container basename that the dispatch hook copies from the prompt (`task_start.work_item`). It reads `record_change` rows in a pass of their own before that filter, so a newer row from another checkout or with `host: "prior"` wins. **The timestamp, and how a line reaches the log.** The monitor orders rows by the raw `ts` string, with a stable sort, so rows sharing a `ts` keep file order. The log is class R2 (`rules/workbench-tracking.md`): tracked, appended by every checkout, never rewritten, and merged by git with `merge=union`. A writer appends whole newline-terminated lines and never rewrites or reorders the file.

### `initialize`

**The request.** `{op: "initialize", workbench, operation_id, id}`. `workbench` is required on this branch. `id` is the caller's workbench UUID. A manifest field sent by the caller is `schema-invalid/request`: the codec writes the manifest, and no host serialises one. `initialize` is added to the protocol schema's `op` enum after `validate`, with a `oneOf` branch of its own and `additionalProperties: false`.

**The manifest written.** `fusion.workbench/v1` with the caller's `id`, `required_features: ["json-control-v1"]`, `migration: null` and `extensions: {}`, serialised by the codec's serialiser and validated before the intent is written. `workbench.schema.json` already admits it.

**The answer.** `{operation_id, id, path: "workbench.json", revision}`, with `revisions` beside the result as on every mutation. The answer carries no absolute path.

**The order.** The kernel runs its one mutation sequence: replay, intent, recovery and lock stay as the FJ02 section above states them. The state gate becomes a parameter. Every other mutation still admits only `json-control`, and `initialize` admits every state. The steps, in order, each ending the request where it answers:

1. The request is validated under `fusion.protocol/v1`. An invalid one is `schema-invalid/request`.
2. A target that is absent or is not a directory is `unknown-scope/workbench-missing`.
3. If `.json-state` is absent or is not a directory, the content check runs once without the lock, since no intent, stored answer or lock can exist there. A `workbench.json` entry of any kind is `conflict/manifest-present`. Any other entry is `conflict/target-not-empty`, and a `.json-state` that is not a directory is such an entry. Nothing is written on either refusal. An empty directory goes on to step 4.
4. The lock is taken (a wait beyond 65 s is `conflict/lock-timeout`), the sweep runs, and every pending intent is recovered, as for any mutation.
5. If this request's `operation_id` names a pending intent that recovery left blocked, the same request is `operation-unknown/recovery-blocked` and another request is `conflict/operation-id-reused`.
6. If a stored answer exists under this `operation_id`, the same request digest answers the stored bytes, byte for byte, and another digest is `conflict/operation-id-reused`. This holds after later writes too: a replay after a `create` answers the stored bytes.
7. If any other intent is still blocked, the request is `operation-unknown/recovery-blocked`, before any content check.
8. The content check runs again under the lock, with the same two refusals as step 3. A target whose only entries are exempt goes on: the intent is written, `workbench.json` is written by temp file and rename, and the answer is stored and returned.

The plan function reads the directory under the lock and never the state the workbench was opened with, which recovery may have made stale. One content check serves steps 3 and 8.

**The reason names.** Two are new: `conflict/manifest-present` and `conflict/target-not-empty`. The detail of each names the first entries found, sorted. Every other refusal above already exists at `3c0903f4`. The fix of fusion issue `260930-1654_*_a-directory-named-workbench-json-makes-the-bundle-throw-and-exit-1-instead-of-answering.md` adds one diagnosis, `schema-invalid/manifest-not-a-file`: a `workbench.json` that is not a regular file is answered `unsupported` with that diagnosis on every operation, where the bundle throws and exits 1 today. None of the three names occurs under `codec/src`, `codec/contract`, `codec/schemas` or `codec/fixtures` at `3c0903f4`.

**The exemption.** One entry only: a `.json-state/` directory that holds nothing but what the lock protocol and the sweep own, with its `journal/` and `ops/` holding no named entry. The lock protocol owns the lock file, its takeover claims and the self-ignoring `.gitignore`. The sweep removes the dot-named entries of `journal/` and `ops/`. The names come from the codec's constants and are spelled once: `STATE_DIR`, `LOCK_FILE`, `TAKEOVER_INFIX` and `SELF_IGNORE` in `codec/src/store.ts`, and `JOURNAL_DIR` and `OPS_DIR` in `codec/src/journal.ts`. A stored answer of another operation in `ops/` is an entry, so such a target is `conflict/target-not-empty`. Scaffolding is not guessed at: `.DS_Store`, `.gitkeep`, a marker or an empty store directory is an entry like any other.

**The no-trace property.** A refused `initialize` over a directory without `.json-state/` leaves that directory byte-identical and creates no `.json-state/` in it, because the refusal comes from step 3, before the lock. A legacy store that FJ04 must migrate therefore gains nothing from a mistaken `initialize`.

### `list.result.state`

`list` answers `{workbench, state, scope, records}`. `state` is `json-control` or `legacy`, the same value `inspect`, `validate` and `reconcile` report. An `unsupported` workbench stays a refusal, as now. On a legacy workbench `records` stays `[]`. This is closure (a) of item 28, folded into this revision as `ad21e58` accepted. It does not waive the gate: a consumer that derives scope, work order or dispatch still calls `inspect` first and proceeds only on `json-control`.

### `inspect`: fifteen operations, and `pending`

`inspect.result.operations.implemented` gains `initialize` after `validate`. The table then holds fifteen operations: fourteen implemented, with `migration` still deferred. At `3c0903f4` `OPERATIONS` in `codec/src/cli/protocol.ts` holds fourteen, and thirteen of them are implemented.

`inspect` gains one additive field, `pending`. It is `null`, or `{operation_id, blocked}`. It is non-null exactly when the state is `legacy` and the target's only entry is a `.json-state/` holding a committed `initialize` intent, with the same exemption as above. It is computed by the same content check that `initialize` runs, so the exemption list stays in the codec. Item 33 states why.

### The `reconcile` index: placement and preserved orderings

This change is for speed alone and moves no answer byte. At `3c0903f4` `readContext` in `codec/src/kernel.ts` resolves a record id by walking `controlFiles(wb, wb.root)` and strict-parsing every control file, on each call. `reconcile` calls it per reference site, evidence binding and dependency edge. Fusion issue `260930-1712_*_the-codecs-reconcile-grows-with-the-square-of-the-record-count-and-outlasts-the-clients-timeout-from-about-1200-records.md` measured an unscoped `reconcile` at 2.1 s for 200 records, 11.8 s for 500, 47.1 s for 1 000 and 310 s for 2 500. Those are the issue's figures, taken on an M2 Max and not re-run for this text.

- **Placement.** The index is built inside `reconcile`'s body and nowhere else. The body wraps the read context it already builds, and the wrapper's `resolveRecordId` answers from one walk. `readContext`, its `resolveRecordId`, and every mutation (the free-id check of `create` included) stay as they are. A cached index inside a mutation could go stale within that mutation.
- **Lifetime.** One index per run of the body. `read` runs the body again after a consistency retry or a recovery, so the index is rebuilt with the view. Nothing is persisted, and no index outlives a request.
- **Preserved orderings and outcomes.** The walk is `controlFiles` in its existing sorted order. Every file is strict-parsed, and a refused file is skipped, so it stays unresolvable. No `blockedOn` filter applies, as today. The detail of `conflict/ambiguous-reference` lists the hits in walk order. Missing and foreign targets and blocked-recovery findings are unchanged. Every answer byte of every recorded session and of the handback stays as it is.

### The role in `reconcile`'s references

A reference entry becomes `{path, at, role?, status, target?, class?, reason?}`.

- **Applicability.** Every entry whose `at` is `/active_documents/<i>/ref` carries `role`, whatever its `status` (`resolved`, `unresolved`, `ambiguous` or `foreign`). Every other entry carries none.
- **Value.** The stored `active_documents[i].role` of the record at `path`, when that is `plan` or `spec`. It is left out when the stored value is anything else, a case the record's schema finding already reports. The role is taken from the binding at its source, never inferred from the target's kind, file name or array position. Both roles can name plan-kind records.
- **Placement.** Immediately after `at` and before `status` in the entry's key order, which the answer keeps as written (the recorded entries read `path`, `at`, `status`, then `target` or `class` and `reason`).
- **Unchanged.** `path`, `at`, `status`, `target`, `class`, `reason` and revision semantics. An unresolved or ambiguous binding carries `role` and no `target`, so nothing is invented about a target that did not resolve.

On the fusion side, `bin/fusion-citation-sweep` then takes each binding's role from this report and sends no `show` per package or evidence row. Its request count becomes exactly `inspect`, `list` and `reconcile` for any number of packages.

### The FJ02 delta file

`codec/fixtures/protocol-session-fj02/15-reconcile.response.json` holds ten reference entries. Two of them are at `/active_documents/0/ref`: `work-packages/260927-0900-strict-reader/package.json`, `unresolved` (`record-not-found`), and `work-packages/260929-0900-fj02-session/package.json`, `resolved`. The FJ02 gate replays exchange 15 against the recorded bytes with exactly that delta applied, and every other exchange byte for byte. It is shown red against an answer that carries one field more or one less. The session's `README.md` states the delta and why. Nothing is regenerated silently. The evidence is kept in two stages, as `a15dfc8` asks. The index lands first, and every recorded session and the handback replay byte for byte without the delta. Only then does the role move the two reviewed fields.

### The measurement protocol

Kept apart from the deterministic tests, as `a15dfc8` asks.

- **Deterministic work count** (in the codec suite). A fixture of N packages, each carrying several references, is reconciled at N and 2N. The test counts whole-store walks and control-file parses in one `reconcile`. Parses at 2N may be at most twice the figure at N plus a constant: work grows with records plus references, not their product. The code at `3c0903f4` fails it. A second test pins the rebuild on the retry path: a record lands during the first read attempt and the answer resolves it. Timing is not asserted in the suite.
- **Timing at scale** (outside the suite). A generator, `codec/scripts/bench-fixture.mjs`, is committed so that Prior can rebuild the fixtures. It builds the store through the bundle with fixed ids, as the issue did: packages each with one adopted plan, at 200, 500, 1 000 and 2 500 records. Each run goes through the committed bundle with an empty environment. The hand-over reports, per size: records and reference count, machine and Node version, at least three repetitions, median and maximum elapsed time, peak memory (max RSS), and the output bytes of unscoped `reconcile` and unscoped `list`.
- **The consumers at scale.** At 2 500 records, in a `git init` project, the complete helpers: `bin/fusion-claimed-package`, `bin/fusion-work-order`, `bin/fusion-citation-check` and `bin/fusion-citation-sweep --dry-run`. A fast lookup in isolation is not taken as proof that they finish in time.
- **The targets.** An unscoped `reconcile` at 2 500 records answers within the 5 s post-wait allowance (`POST_WAIT_MARGIN_MS` in `hooks/lib/record-client.ts`) on the reference machine, an M2 Max. Each consumer exits 0 within the client's 70 s (`CODEC_WAIT_MS` 65 s plus that margin), with its time recorded. If `reconcile` misses the target, the remaining cost is located and fixed before the hand-over. The timeout is never raised. Output bytes are stated against 1 MiB, and an answer above it is reported for item 31. It does not stop this revision, and no migration readiness is claimed.

### 33. No read finishes a committed `initialize` whose manifest has not landed; `inspect` names that window

**Closes:** fusion decision `260930-1654_*_does-a-read-finish-a-committed-initialize-whose-manifest-has-not-landed-or-report-the-target-as-legacy.md`, option 3, answered by the user on 2026-09-30 together with the plan's approval. This is fusion's decision, stated openly for Prior to object to. Prior has not co-decided it, and `a15dfc8` says that choosing the bundle grouping does not decide it. Preferred form: an objection before the hand-over that freezes this revision's digest, or none.

The window: `initialize` is the first operation whose intent can stand in a workbench that has no manifest. Between its commit point (the intent directory renamed into `.json-state/journal/`) and the write of `workbench.json`, the target holds `.json-state/` and nothing else. At `3c0903f4`, `openWorkbench` reports such a target `legacy`, because the state is a function of the manifest alone. `read` in `codec/src/kernel.ts` runs a read on every state but `json-control` once, without recovery (its first line). `inspect` runs outside `read` and recovers nothing.

> **33. No read finishes a committed `initialize` whose manifest has not landed; `inspect` names that window.** The target then holds only `.json-state/` and is `legacy` under section 4.1. Not finishing is inside section 6's permission ("dürfen", "kann"). The statement is about this intent alone: ordinary committed intents are still recovered by FJ02 reads, as `a15dfc8` requires. Any `initialize` request finishes it under the lock. The same request answers the committed result; another one lands the committed intent first and is then refused `conflict/manifest-present`. `inspect` gains one additive field, `pending`. It is non-null exactly when the state is `legacy` and the only entry is a `.json-state/` holding a committed `initialize`, and it names that intent's operation id and whether it is blocked. **A duty on Prior's host:** its provisioning route acts on what `inspect` reports for that window (it sends `initialize`, never FJ04) and does not re-derive the codec's exemption list.

The permission cited: section 6 at `a15dfc8`, the `inspect`, `list`, `show`, `validate` row ("eindeutige bereits committete Intents dürfen zuvor rekonstruiert werden"), and the paragraph on `recovery-blocked` ("Lesen kann einen committeten Intent fertigstellen"). Section 4.1 adds that reading creates no new initialisation ("Lesen erzeugt weiterhin keinen neuen Initialisierungsauftrag"), and it leaves open who reconstructs the committed initialisation bytes after an abort. The decision answers that: an `initialize` request does.

Why `pending`, and not `legacy` alone: without a report from the codec, each host would have to rebuild the exemption list to tell a pending initialisation apart from a legacy store bound for FJ04. Two copies of that list would drift. With `pending`, the list stays in one place, and Setup and Prior's provisioning route each read one field. This is inferred, not measured.

The two alternatives the record weighed, for Prior's review. In option 1, reads report `legacy` with no field, so a caller has to look for `.json-state/` itself. In option 2, every read, `inspect` included, finishes the intent. That would make the gate both hosts call first into a read that may write, on a legacy-state target too.

What it fixes in the bytes both hosts replay: the `initialize` recorded session, planned for the hand-over. There, `inspect` over a committed intent from an in-process cut answers `legacy` with `pending`. The intent's own `initialize` request then answers the committed result, and a following `inspect` answers `json-control`. The flowchart under "The order" does not depend on this item. If Prior objects, `read`, `inspect` and those exchanges change, and the order stays as stated.
