# CLAUDE.md — fusion plugin source

**Language:** de
**Artifact language:** en

This repository is the **source of the fusion Claude Code plugin** (`tenzoki-plugins/fusion`). It is *not* a fusion-consuming project. **No part of the guard self-disables here any more, because no part of it decides anything anywhere.** One stand-down used to: the write-tool branch of `hooks/guard.ts` recognised this repository by a `.claude-plugin/plugin.json` matching the plugin's own name and allowed every write, so a fusion developer could edit the plugin's own source. It was built because the guard used to protect `agents/**`, `rules/**` and the plugin manifest, which is correct for a project *using* fusion and wrong when developing fusion itself, where every edit to those files would have been blocked and written back. **That protection was removed on 260812**, along with the whole protected-path half of the guard, and the stand-down outlived it by four days: it went on 260816 with the guard's last verdict, so the hook now behaves identically in this tree and in a consuming project (`hooks/guard.ts`, the header's account of what it used to check). A second stand-down covered the churn heatmap in `hooks/tracker.ts` and went with the heatmap on 260815.

**The rule the two established outlives both of them, and it is what the next stand-down is measured against:** a stand-down is evaluated in the coordinate space the mechanism keys its state by. The write-tool check read cwd (`isFusionPluginCwd()`, deleted from `hooks/lib/self-detect.ts` on 260816), because `guard.ts` computed its verdict in cwd's space; churn asked about the workbench root it walked up to (`isFusionPluginRoot(dir)`), because its keys were anchored there. A root-anchored mechanism with a cwd-anchored stand-down misses every session started one directory down, and the reverse is the reverse hole. Both halves of that were measured on the protected-path measurement — whose stand-down had to move up to the root in v6.0.1 when its measurement root did, or a session started in `fusion-workbench/`, the ordinary case here, would have begun reverting the developer's own files. Two mechanisms and their stand-downs are gone. `hooks/lib/self-detect.ts` now keeps `isFusionPluginRoot(dir)` alone and with no caller, so the root-anchored form stays available to whoever needs it next, and `bin/fusion-plugin-cwd` is the only surviving implementation of the cwd-anchored form.

A **git branch-switch policy** used to run here too, and it was the one thing the stand-down never covered. It was deleted outright on 260809: it decided from a shell command's *text* whether the command would move HEAD, which is the same undecidable question the write-path classifier answered until v6.0.0, and in one afternoon it cost five patches, a sixth open entrance, and 24 consecutive false blocks against the agents' own verification commands. Nothing about a `Bash` command is read by the guard any more, in this repository or any other, and since 260812 nothing a `Bash` command *does* is measured either.

## What this is

Plugin published to the `tenzoki-plugins` marketplace (repo: `tenzoki/claude-plugins`). Provides:

- 15 specialized agents — orchestrator (top-level dispatcher) plus coder, ontocoder, coderev, ontorev, planner, shaper, taskplanner, reconciler, analyst, bugfixer, consultant, playmaker, editor, curator. Three (`reconciler`, `taskplanner`, `playmaker`) are parameterised by domain (`code | data`) since v1.11.0 — `strategic` and `knowledge` left on 2026-08-15, measured at zero and two dispatches respectively; `planner` is **not** one of them and parses no `**Domain:**` line — it takes `**Executors:**` and `**Circle:**` instead. Seven agents in all read a dispatch parameter; the roster is authored once, in `README-agents.md` `## Dispatch parameters`. `editor` (added v5.2.0) is the produce-only Redakteur — it writes, revises, translates (en↔de), and renders customer-ready deliverables (Markdown, branded pptx) to a project-side location; it never reviews, files issues, or dispatches. `curator` (added v8.2.0) reconciles a project's three normative surfaces — its decision records, its project-owned rule files and `CLAUDE.md` — against the project's own recorded history; every proposed change carries an evidence tier and a citation, and nothing lands before a user gate.
- Compliance guard, **observation-only since 260816** (TypeScript hooks, compiled to `hooks/dist/`) — it decides nothing. The PreToolUse hook receives the four write tools and Bash, allows every one of them, and exists for two products: one `guard_allow` row per write-tool call in `.guard-state/events.jsonl`, which is what the monitor's panel renders, and one `guard_advisory` per problem the configuration loader hands back. Every path through it writes `{}`; the name is historical and is kept because the event vocabulary, the state directory and the monitor panel all carry it (`hooks/guard.ts`, header). What it used to do went in three steps. It blocked the four write tools against a `protectedPaths` list and measured those paths around every guarded call so a change reaching them any other way was written back; that half was removed on 260812. It counted per-file churn in a heatmap and emitted warning events for the monitor at configured thresholds; that half warned, never blocked, and was removed on 260815. It blocked writes into the decision-governed categories at `high` sensitivity and halted after three consecutive blocks; that check, the halt, the consecutive-block counter, the escalation module and the halt-clearing script were removed on 260816
- Real-time HTML monitor dashboard (`bin/monitor`)
- Pattern-based rule discovery helper (`bin/fusion-rules`)
- Per-consumer workbench path resolver (`bin/fusion-paths`) — Circle-container layout, v4.0.0+
- Skill bodies, one per directory under `skills/`; that listing is the authoritative set. **The administrative surface is three names** — `/fusion:setup` at the start of a session, `/fusion:cleanup` at the end, `/fusion:cadence` to see what happened. Three further bodies are steps of the cleanup pipeline rather than commands: `/fusion:archive` (Step 4), `/fusion:curate` (Step 5, the `CLAUDE.md` gate) and `/fusion:log-activity` (Step 6), each reachable alone as `/fusion:cleanup --only archive`, `--only claude-md` and `--only log-activity`. **Two of those three selectors are the body's own name and one is not** — the `CLAUDE.md` step's selector is `claude-md`, and `--only curate` is rejected by the selector's error path. **They keep their directories, so a session can still invoke them by name** — the collapse is what fusion presents and documents, not a mechanism that unregisters a skill, and the three are listed here because `derivable-enumerations-lint` asserts a two-way match between this listing and `skills/*/`. The rest are situational: `/fusion:migrate`, `/fusion:help`, `/fusion:memo`, `/fusion:commit`, `/fusion:next`, `/fusion:direct`. Two directories left on 2026-08-15 with the collapse: `revise-claude-md`, whose autonomous three-pass rewrite of `CLAUDE.md` was replaced by the curator's gated pass, and `unlock`, whose settings merge became Setup Step 0g. Neither name may be written in the `/fusion:` form anywhere in this file — the lint reads every such token and fails on one that names no directory

| `.claude-plugin/plugin.json` | Manifest. **Bump version on every change.** |
| `agents/*.md` | The 15 agent prompts. Only `orchestrator.md` declares a `tools:` allowlist (sub-agent dispatch + permitted tools); the other 14 inherit tools and model from the parent session. |
| `hooks/` | TypeScript source + compiled `dist/`. SessionStart, PreToolUse, PostToolUse hooks. Uses `process.cwd()` not `__dirname` for project-local state. SessionStart runs three independent commands: the `FUSION_PLUGIN_ROOT` export, the static "Fusion loaded" banner, and `session-start.ts` — which warns, as a `systemMessage`, when a workbench root is found *above* the working directory rather than at it. One cwd-anchored resolution is left for that warning to be about, the work-tree preference of the three `bin/` helpers listed under `bin/fusion-plugin-cwd`; the two sharper ones it used to name went with the protected-path deny on 260812 and with the guard's last verdict on 260816. The warning fixes none of it, and makes the assumption audible at the one moment the working directory is still cheap to change. The PreToolUse guard inspects `Bash` for **nothing** and allows it immediately, writing no guard state at all **when the project's `fusion.json` is valid**. A broken file, a retired top-level key inside it, or a leftover `fusion-guard.json` at the project root each emit one `guard_advisory` per guarded call, Bash included, because the diagnostic loop sits above the Bash return (`hooks/guard.ts`, and the comment there states the departure). The last policy that read a command's text — the git branch/worktree guard, with the shell lexer and command-word resolver under it — was deleted on 260809; the last thing that watched what a command *did* — the protected-path measurement, a fingerprint of the whole protected list taken in `guard.ts` before the call and compared again in `tracker.ts` after it, with anything that moved written back and the guard halted — was deleted on 260812 with the rest of that half. **No check remains**: the halt and the decision-governed categories both went on 260816. Documented for users in `README-hooks.md`. |
| `fusion.json` + `templates/fusion.json` | The per-project configuration, renamed from `fusion-guard.json` on 260816 when the last guard setting left it. `/fusion:setup` seeds the template into a consuming project's root, git-tracked so every change to it shows in a diff; the root copy here equals the template outside the top-level keys a project is meant to set for itself, and that is exactly what `config.test.ts` pins: it cuts the keys named in its `PROJECT_SET_KEYS` out of both sides and holds every remaining byte identical. This repository sets the one key that constant names, its own Turn budget (`orchestrator.maxTurns`), which is now the loader's only live leaf. The merge is per **leaf** key across **two** layers — this file, then the built-in `DEFAULTS` in `hooks/lib/config.ts` — so a declared value wins outright and an omitted or invalid one falls straight through to what fusion ships. The plugin layer that used to sit between them went with the guard settings it carried. Retirement now has two scopes rather than one leaf: `RETIRED_PROJECT_FILES` names a leftover `fusion-guard.json` at the project root and `RETIRED_TOP_LEVEL_KEYS` names `guard`, `decisions` and `escalation` inside the new file; either earns one advisory per guarded call until the file or the key is deleted, and the file advisory names `orchestrator.maxTurns` and the JSON to copy across, because a budget left behind is silently not read. Nothing in the guard defends this file from an agent; the git diff is the only bound left, which is what the template's `_gitTracked` note says. |
| `bin/monitor` | HTML dashboard binary, served by the orchestrator from `fusion-workbench/monitor` (copied at Setup) |
| `bin/fusion-rules` | Per-agent rule discovery helper (used in every agent's Setup). Takes an optional second arg `fusion-rules <agent> [<topic>]` and reads an optional consuming-project manifest `./rules/context-manifest.yaml` to emit topic- and agent-scoped units (a `path` file or a `skill:<name>` pointer). When the manifest is absent, output is **byte-identical** to before (`HYG-NO-REGRESS`); a malformed manifest fails loudly (exit 3). Topic is derived from the active Circle (slug keywords, or an explicit `Topic:`/`Tags:` record line) unless the CLI arg overrides it. Convention authored in `rules/context-manifest.md` + `rules/context-lean-claude-md.md`. Added v5.x (Circle B). |
| `bin/fusion-paths` | Per-consumer path resolver (used in every agent's and skill's Setup, alongside `bin/fusion-rules`). Reads `.active-circle`, emits `KEY=value` write/scan targets (`OUT_*`, `SCAN_*`, `WORKBENCH`, `CIRCLE`) so no prompt hard-codes a store path. The set of keys a consumer gets is *derived* from grepping that consumer's own prompt — never declared. `<name>` is an agent OR a skill (one flat namespace). Since v8.1.0 the signature is `fusion-paths <name> [<circle-dir>]`: an optional second argument names an existing Circle directory, which becomes the **Circle in scope** — it replaces the active Circle as the `OUT_*` base and as the Circle half of every `SCAN_*`, while `.active-circle` is neither consulted for the substitution nor written and the emitted `CIRCLE` key still names the *active* Circle (a target Circle is in scope, not active). It is what lets shaper and planner write a Circle's founding documents inside an anticipated Circle before activation. Exit shape mirrors `fusion-rules` (0/1/2) plus its own 3 (corrupt/orphaned `.active-circle` — user's to fix) and 4 (prompt names a key the resolver can't value — a fusion bug); a `<circle-dir>` naming no existing directory is exit **1**, a caller usage error rather than a workbench fault. Introduced v4.0.0 with the Circle-container restructure. |
| `install.sh` | HTTPS `curl \| bash` installer (repo root). Downloads the tarball into `~/.fusion`, writes the `~/.local/bin/fusion` launcher. The launcher takes an agent arg (`fusion coder`, default `orchestrator`, auto-namespaced), an opt-in `--yolo` (`--dangerously-skip-permissions`), and `--update`/`--uninstall`/`--where`. Replaced the old `bin/fu` project-local launcher (removed v3.20.0). |
| `bin/fusion-workbench-root` | Walks up from `pwd` to find a directory containing `fusion-workbench/.fusion-setup`. Prints the absolute path or exits 1. The single source of truth for "is this project fusion-set-up, and where". Hooks call the TS equivalent (`hooks/lib/workbench-root.ts`); agents call this script. |
| `bin/fusion-plugin-cwd` | Answers "is cwd the fusion plugin's own source repo?" — exit 0/1, prints nothing. **The only cwd-anchored implementation of the criterion.** It was the shell half of `hooks/lib/self-detect.ts` `isFusionPluginCwd()` until that function was deleted on 260816 with the guard's stand-down; what survives on the TypeScript side is the root-anchored `isFusionPluginRoot(dir)`, which is the other coordinate space rather than a duplicate. The criterion is still kept consistent across the two, and the helper's own header carries the pairing and its residual imprecision. Consumed by `bin/fusion-rules` (work-tree rules preference), `bin/fusion-paths` (work-tree prompt preference) and `bin/fusion-source-root` (the root a skill body's citations of shipped files open against) — see the Rules-loading convention below. Checks `./.claude-plugin/plugin.json` **at cwd, with no upward walk** — deliberately congruent with the root-anchored form's criterion, so from a subdirectory of this repo the helpers behave as in a consuming project. That used to happen *silently*; since the SessionStart warning (`hooks/session-start.ts`) a session started below the root says so on its first screen, naming both directories. The behaviour is unchanged — only its visibility. Added v5.x per decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md` (option c, textschicht Circle). |
| `bin/fusion-source-root` | The root a citation of a plugin-shipped **file** resolves against, read at the first step of `/fusion:setup`, `/fusion:next`, `/fusion:cleanup` and `/fusion:help` instead of each body restating the branch. Prints `$PWD` when `bin/fusion-plugin-cwd` says cwd is this repo, `$FUSION_PLUGIN_ROOT` otherwise; exits 2 printing nothing when neither is available, which is the `UNRESOLVED` the callers report. It replaced four executable copies of that criterion across two skill bodies — a correction to one of them once reached two and left two standing (issue `260811-0109`, decision `260810-2145` option 1). Every call site guards with `[ -x ]`, per that record's part (b): the installed copy need not carry a helper added between releases, and a bare call is exit 127 at a skill's own first step. |
| `bin/fusion-turn-budget` | The orchestrator's Phase-2 Turn budget, resolved from configuration and read once at Setup (`agents/orchestrator.md` Setup Step 2, `skills/setup/SKILL.md` Step 2) instead of the number being written into the prompt — it *was* written into it, `5`, in seven places and four spellings, one of which already called itself a default while no source could override it (issue `260811-1712`). ## Conventions

- **Agent dispatch** — always namespaced: `Agent(fusion:coder)`, `Agent(fusion:ontocoder)`, etc. Bare names don't resolve. Any agent with a `tools: Agent(...)` allowlist must list sub-agents in `<plugin>:<name>` form.
- **Dispatch parameters (v1.11.0+)** — seven agents read run-time parameters off the dispatch prompt as plain markdown `**<Keyword>:**` lines. **The roster is authored once, in `README-agents.md` `## Dispatch parameters`** — that table carries the agent, the line, its values, what happens when it is absent, and who passes it, each row cited to the prompt line it was read against. Do not restate it here; a second copy is how the planner came to be listed as domain-parameterised in four places while `agents/planner.md` never parsed the string. Two facts belong in this file because they shape dispatch decisions rather than describe one agent. First: `**Domain:** <code|data>` changes behaviour in `taskplanner`, `reconciler` and `playmaker` only, defaulting to `code`; `shaper` accepts the line in anticipated-circle mode and merely copies it into the record it writes; `planner` takes `**Executors:** coder, ontocoder, analyst` (default `[coder, ontocoder]`), which the orchestrator passes on **every** planner dispatch with no condition in front of it. The domain-conditional derivation was deleted on 2026-08-15: whether a step needs `analyst` is a question the plan answers, and no caller upstream of the plan holds the input to answer it. Second: `editor`'s `**Deliverable language:** <de|en>` is the one parameter with **no default** — the agent halts when the dispatch names no language rather than falling back to the chat or artifact declaration (decision `260807-2131_*_which-language-governs-a-customer-deliverable.md`, option 3; the customer-deliverable case in `rules/fusion-workbench-conventions.md` `## Project language`). The loudness is the point — a silent default hands the customer a finished document in the wrong language instead of stopping. Any caller dispatching these agents from outside the orchestrator prefixes the dispatch prompt with the appropriate parameter line.
- **Rules loading** — agents call `"$FUSION_PLUGIN_ROOT/bin/fusion-rules" <agent-name>` and read every emitted path. Plugin files are NOT auto-loaded into agent context; this helper is the only correct discovery path. The helper emits `rules/agent-setup.md` **first** (Circle D) — the factored Setup contract (read-every-emitted-path, the `bin/fusion-paths` `OUT_*`/`SCAN_*` semantics, the exit-3/exit-4 distinction) that every agent prompt points at through a shared Setup pointer — ahead of `fusion-workbench-conventions.md` and the other always-on rules, so an agent reads *how Setup works* before the detailed conventions. `$FUSION_PLUGIN_ROOT` is exported by `hooks/hooks.json` SessionStart. The helper searches three roots (in this order): the plugin's `rules/`, the project's `./rules/` (fusion-agent-specific rules — taskplanner priority overrides, anything no other Claude session would care about), and the project's `.claude/rules/` (project-wide rules every Claude session should respect — coding/ontology/normative guidelines). Filename patterns per agent are unchanged. Since v5.x (Circle B) the helper also accepts an optional topic (`fusion-rules <agent> [<topic>]`) and, if a consuming project ships `./rules/context-manifest.yaml`, additionally emits the manifest units whose agent AND topic match — `path` files loaded as today, `skill:<name>` pointers invoked on demand. Absent the manifest, the emitted set is byte-identical to before; the mechanism is authored in `rules/context-manifest.md` and the lean-`CLAUDE.md` convention in `rules/context-lean-claude-md.md`. **In this repo the helpers prefer the work tree** (v5.x, decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md` option c): when `bin/fusion-plugin-cwd` says cwd is the plugin's own repo, `bin/fusion-rules` reads the checkout's `./rules/` instead of `$FUSION_PLUGIN_ROOT/rules/`, `bin/fusion-paths` reads the work-tree prompts instead of the install copy's, and `bin/fusion-source-root` hands a skill body the checkout as the root its citations of shipped files open against. That closed the stale-rules failure where a four-day session read the installed v5.8.0 rules while editing v5.9.1 sources ($FUSION_PLUGIN_ROOT pins to the installed copy for the whole session). **The bound is exact and unforgiving:** the check is at cwd with no upward walk, so a session whose cwd is a *subdirectory* of this repo gets the installed copy again, indistinguishable *to the helpers* from a legitimate consuming project — start sessions at the repo root. It is no longer indistinguishable to **you**: `hooks/session-start.ts` warns at SessionStart whenever the workbench root sits above the working directory, which is precisely this condition, and names both directories. The warning is a signal, not a fix — the helpers still resolve against cwd and still read the installed copy.
- **User-facing output style** — every agent loads `rules/user-facing-output.md` (auto-emitted by `bin/fusion-rules` alongside `fusion-workbench-conventions.md` and `decision-record-examples.md`). It mandates action-first ordering, plain-English option labels, no undefined jargon, and trailing details/references blocks. Applies to status reports, gate prompts, AskUserQuestion text, session summaries — anything the user reads. Agent prompts' "Output Style" sections point at the rule and add only domain-specific bits.
- **Critical stance (v3.21.2+)** — every agent also loads `rules/critical-stance.md` (auto-emitted by `bin/fusion-rules` alongside the three files above). Unlike `user-facing-output.md`, which governs *formatting*, this rule governs *reasoning substance*: (1) own your errors instead of praising the user who caught them, (2) no premature/half-baked solutions — research the root cause and prefer the clean integrated fix over additive workarounds, (3) calibrated certainty — separate verified from inference from speculation, label the latter two, and never dress an unchecked claim as a checked one. It generalises to every agent (notably the orchestrator) the per-agent honesty lines that consultant/analyst/coderev/ontorev already carried.
- **No guard rule is emitted any more.** The always-on `protected-path-discipline.md` (under `rules/` until 260812) was the agent-facing half of the protected-path measurement and went with it, as its sibling rule for the branch policy had gone on 260809. It was 10 541 bytes on every one of the sixteen agents' every dispatch. **Measured on 260812, the day it went:** the always-on floor stood at 98 443 bytes per dispatch before the removal, 91 090 of shipped rule text plus this project's 7 353-byte chat voice profile, and the step took 10 420 off that rather than the full 10 541, because it also had to correct a present-tense claim in `rules/critical-stance.md` that the removal made false, at +121 bytes. **The floor as it stands today is deliberately not stated here.** It moves with every rule edit, so any number written into this line is stale before it is committed: by 260813 the two that stood here had each drifted 5 796 bytes low. Measure it when you need it, with `wc -c` over the always-on set — the **unindented** `emit_if_exists` lines in `bin/fusion-rules`, plus the project's chat voice profile. The indented ones are conditional emissions and are not part of the floor; the same `wc -c` over those three files gives what they add, which has been about a third again. In this repository `bin/fusion-rules coder | xargs wc -c` prints the same total in one command, because `coder` draws no conditional rule. **Consequence worth knowing, and since 260816 it has shrunk to nothing:** no rule tells a sub-agent what a halt is or how it is cleared, and there is no longer anything to tell. No halt is reachable, the counter that raised one and the script that cleared one are both gone, and a legacy flag a consuming project still carries blocks nothing — the two migration rows at the end of this document say what to do about it. **The always-on set is an explicit `emit_if_exists` list in `bin/fusion-rules`** (not a pattern match), so a new always-on rule needs a line there or it will not load.
- **Four shipped surfaces have a failing growth bound (260815).** Editing `agents/*.md`, `skills/*/SKILL.md`, the hook tests, or an always-on rule file can now turn `npm test` red — not for what the text says, but for how much it grew. Each surface has its own baseline, its own head-room and its own failure, derived from that surface's own replayed history: 12 000 bytes for the always-on rule set (`hooks/lib/__tests__/rules-emission-golden.test.ts`), 18 000 for `agents/`, 20 000 for `skills/`, 2 500 lines for the hook tests (`hooks/lib/__tests__/surface-growth-bound.test.ts`). **They are four budgets, not one:** shrinking `skills/` buys `agents/` nothing, by construction. A shrink never trips a bound — this measures the rate of addition, which is what the project's own history says the binding constraint is. **The way out of a red bound is a cut, never an edit to the baseline:** a baseline moves at exactly two written-down moments, after a cleanup or at a one-time arming, and the rule is authored once in `hooks/lib/__tests__/helpers/growth-bound.ts`. Read `README-hooks.md` `### Growth bounds on the shipped text` before touching a number. What no bound covers is stated there too, rather than left to be discovered.
- **Two stylometric profile families (v3.16.0+)** — both under `./fusion-workbench/stilwerk/`, each resolved from its own CLAUDE.md declaration line (`en`/`de`) by the rule that owns that resolution and every fallback in it, `rules/fusion-workbench-conventions.md` `## Project language`: `default-voice-<lang>.yaml` is the long-form **writing** profile (narrative outputs: session summaries, consultant reports, analysis reports, spec/plan prose), resolved from `**Artifact language:**` and emitted by `bin/fusion-rules` only for the prose agents. `chat-voice-<lang>.yaml` is the short-form **chat** profile (gate prompts, AskUserQuestion text, status reports, chat replies), resolved from `**Language:**` and emitted for **every** agent; it is a lean blacklist (em-dash/AI-tell anti-patterns) plus a minimal terse-and-direct whitelist, carrying no sentence-length bands so it never fights the length caps in `user-facing-output.md`. The chat profile's apply-to-short-form semantics live centrally in `user-facing-output.md` `## Style anti-patterns apply to everything`; agents pick it up via the "read every emitted path" rules-loading contract. Setup copies all four files into the project workbench.
- **Critical procedures** — model as user-invocable skills (e.g. `/fusion:setup`), never as "MUST" directives in agent prompts. A skill body becomes the user prompt; that's the only reliable enforcement.
- **Workbench writes** — agents write only to `fusion-workbench/`. Sub-agents share no memory; everything persists through workbench files.
- **Workbench bootstrap is exclusive to `/fusion:setup`** — since v2.5.0, **only** the setup skill creates a workbench. Setup writes `fusion-workbench/.fusion-setup` (a JSON marker with timestamp + plugin version). Every agent and hook locates the workbench by walking up from `pwd` looking for that marker (`bin/fusion-workbench-root` for agents, `hooks/lib/workbench-root.ts` for hooks). If no marker is found: agents halt with "run /fusion:setup", hooks no-op silently. This prevents stray workbench creation when a Claude session's cwd happens to be in any non-fusion directory. Since v4.0.0, setup also **detects a pre-v4 (type-folder) workbench and refuses**, pointing the user at `/fusion:migrate` — the migration skill moves the old type-folders wholesale into `shared/` and stands up the `circles/`-container scaffold (`/fusion:migrate` is the only consumer allowed to name both layouts literally, because it is the transition between them).
- **Single orchestrator per project** (advisory) — fusion has no concurrency lock. Two orchestrators running against the same project simultaneously can corrupt `agentstate.yaml` (interrupted-session resume becomes unreliable), double-dispatch the same work, and produce interleaved commit history. The most damaging mode is two parallel sessions each completing half of the same task with overlapping edits. Mitigation since v2.8.0: `/fusion:setup` Step 0c checks for an active-session marker (`fusion-workbench/.session-marker` whose mtime is refreshed at each orchestrator Turn) and **warns** the user when one is detected — `running` if heartbeat ≤ 10 min ago, `stale` if older. The warning is advisory; the user can still proceed but takes responsibility for sequencing.
- **Issues vs decisions (v2.0+)** — defects ("go fix it") go to `$OUT_ISSUE` with markers `_o_/_p_/_c_/_d_`; decisions / open questions ("decide and record") go to `$OUT_DECISION` with the richer `_o_/_a_/_i_/_d_/_s_` vocabulary. Both resolve (via `bin/fusion-paths`) into the active Circle when one exists and into `shared/` when none does — the Origin Rule decides which. See `rules/fusion-workbench-conventions.md` for the decision rule and the decision-record template.
- **SessionStart hook output** — `systemMessage` JSON for user-visible banners; plain stdout is `additionalContext` for the model only.
- **`.gitignore`** — for shipped binaries inside excluded dirs use `dir/*` (file pattern) so `!path` exceptions work for new files. `dir/` (trailing slash) blocks all re-inclusion of files added later.
- **Circles (v3+ via Track C; became the container in v4.0.0)** — a Circle is a *directory* under `fusion-workbench/circles/<stamp>-<slug>/` that holds the `_t_circle.md` record plus that unit of work's own artifact subdirectories. The state marker sits on `_t_circle.md`, not on the directory (the directory name is stable across the whole lifecycle, so references into a Circle never break). A second reason was given at the time — an immutable natural key for the Plane mirror — and it went with the mirror on 2026-08-15; the first reason stands on its own and always did.. Empty or absent `circles/` preserves single-Circle behaviour. Playmaker is the dispatchable agent for portfolio ranking; `/fusion:next` is the user surface. See `rules/circle-records.md` for the vocabulary and the two correct glob forms (one state via `_t_circle.md`, all states via `*_circle.md` with the marker read from the name — the underscore is inert in globs, so neither needs escaping).
- **Bus protocol removed (v3.15.0)** — earlier versions of fusion shipped a workbench-mediated A2A messaging surface under `fusion-workbench/bus/`. It was removed in v3.15.0; concurrent agent sessions exchange work through the user (copy-paste between chat windows) again, the same way they did pre-v3.4. Consultant remains user-initiated; reviewers (coderev / ontorev) file findings as issues, not as bus messages. The bus-era decision records were marked superseded by this removal and have since left the workbench (archived/cleaned); no live record documents the old protocol.

## Release process

Two repos involved: the **plugin** (this repo, `tenzoki/fusion`) and the **marketplace** (`tenzoki/claude-plugins`).

**The marketplace working clone is at `/Users/k1/Projects/productive/F03-CLAUDE-plugin-marketplace/claude-plugins`** (note the nested directory — the outer one is not the repo). That is the clone the release steps below mean. It is a development checkout, not the cache clone `/plugin install` reads: see the note after step 6, which is a separate copy and may not exist at all. At v6.0.0 it did not, so a release can complete correctly while `/plugin install` still serves the previous version locally.

Every release:

0. **Validate first:** `claude plugin validate .` must report **passed** (warnings are fine). This catches broken agent frontmatter before it ships — e.g. an unquoted `:` in a `description` makes the whole frontmatter fail to parse and the agent loads with empty metadata. Also run a smoke test that the default agent resolves under the install mechanism: `claude --plugin-dir . --agent fusion:orchestrator -p "reply SMOKE-OK"` (a wrong agent name aborts Claude immediately at startup). If the release touches the guard, also confirm before tagging that its behaviour was verified against a project root that is **not** this repository (the guard-harness integration tests spawn such roots; a scratch consuming project works too). **The reason for that step changed on 260816 and the step did not.** Until then the write guard's self-detect stand-down made local testing unrepresentative by construction; the stand-down is gone, so the hook is supposed to behave identically in both trees. The check is what establishes that identity against a real consuming root instead of asserting it.
1. Bump `.claude-plugin/plugin.json` `version`
2. `git -C <marketplace> pull --rebase origin main` (it can drift if edited from elsewhere)
3. Bump fusion's `version` in `<marketplace>/.claude-plugin/marketplace.json`
4. Commit and push **both** repos
5. **Tag the fusion release** on the commit you just pushed: `git tag -a v<version> -m "fusion v<version>" && git push origin v<version>`. The tag is what `install.sh`'s `FUSION_REF=tags/v<version>` pinning resolves against — skip it and the documented pin is unusable for that version. (Tagging started at v5.5.0; `v5.5.0` was applied retroactively to its release commit.)
6. To pick up the new version locally:
   ```bash
   git -C ~/.claude/plugins/marketplaces/tenzoki-plugins pull origin main
   ```
   Then in Claude Code: `/plugin install fusion@tenzoki-plugins` and `/reload-plugins`.

**And between releases, before rule or guard work in this repo: run `fusion --update` and restart the session.** The work-tree preference (see Layout, `bin/fusion-plugin-cwd`) covers only `bin/fusion-rules`, `bin/fusion-paths` and `bin/fusion-source-root` — and the third of those roots which *documents* a skill body opens, never which helper it runs, because whether the preference reaches helper resolution is part (c) of decision `260810-1544` and is unanswered. The hooks themselves (guard, tracker) always run from the installed copy, pinned for the whole session, so a stale install still means stale guard behaviour while you edit guard sources. Behaviour rule (a) of decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md`; it stays documented here even though option (c) landed, for exactly that residual.

The marketplace **cache clone** at `~/.claude/plugins/marketplaces/<name>/` is the source-of-truth `/plugin install` reads — not the GitHub remote, and not the working clone named at the top of this section. Without the manual `git pull` on that cache clone, version bumps don't propagate locally even after uninstall/reinstall. If it does not exist (it did not at v6.0.0), `/plugin install` cannot see the release at all; `install.sh` is unaffected, because it reads the GitHub tarball directly.

### HTTPS installer (`install.sh`) — the recommended end-user path

`install.sh` at the repo root is a `curl | bash` installer that downloads the plugin tarball over plain HTTPS (`https://github.com/tenzoki/fusion/archive/refs/heads/main.tar.gz`), unpacks it into `~/.fusion`, and writes a `~/.local/bin/fusion` launcher that runs `claude --plugin-dir ~/.fusion --agent fusion:orchestrator`. It sidesteps the three marketplace failure modes for end users: git/SSH cloning, the unreliable plugin cache, and broken uninstall. Modelled on `tenzoki/flight`'s installer (v0.6.0).

fusion-specific invariants the installer relies on:
- **Compiled hooks must be committed.** `hooks/dist/*.js` are in git (`.gitignore` has the `!hooks/dist/` exception) and are self-contained (no external `require`s) — the tarball is runnable with no `npm`/`node_modules`. The installer defensively `rm -rf`s `hooks/node_modules` after copy.
- **`bin/` executables ship with the +x bit** (preserved through tar/`cp -R`).
- **`CLAUDE_PLUGIN_ROOT` resolves to `~/.fusion`** under `--plugin-dir`, so the SessionStart hook's `export FUSION_PLUGIN_ROOT=${CLAUDE_PLUGIN_ROOT}` and all `bin/` helpers work.
- The installer copies plugin assets — the set is the copy loop in `install.sh`, and that loop is the authority rather than a list here — and **no permission file is among them, because a plugin's own permission settings are not read under `--plugin-dir`.** Measured on Claude Code 2.1.226 by placing one identical `permissions.allow` entry in each of two locations: a project's `.claude/settings.local.json` honoured it, a plugin's own did not. fusion shipped such a file at its root for months, sixteen scoped auto-allows granting nothing on either install path; it was deleted on 2026-08-15 rather than annotated, so nothing in the tree looks like a grant while being inert. A fusion session's permissions come entirely from the consuming project's `.claude/` settings, which `/fusion:setup` Step 0g offers once to seed (defect `fusion-workbench/shared/issues/260810-0326_*_setup-must-seed-claude-settings-because-the-plugin-settings-json-is-not-a-permission-source.md`, decision `260815-0029_*_what-permission-grant-does-setup-seed-when-unlock-becomes-a-setup-step`). **Seed bare tool names only.** The same measurement found every directory-scoped form denied — `Write(fusion-workbench/**)` and each variant of it — even from a settings file that *is* read, so a scoped pattern grants nothing wherever it is written. The installer never copies `CLAUDE.md` or `.gitignore` (dev-only), and defensively drops `hooks/node_modules`.

So there are effectively **four version surfaces** to keep coherent: `plugin.json`, `marketplace.json`, the `install.sh` header comment's `FUSION_REF=tags/v<version>` example, and the same pin example in `README.md` (the surface a user reads first — it drifted for months because the old count stopped at three). The default ref is `heads/main`, so a stale example still doesn't break a plain install — but since step 5 tags every release, the example now names a tag that actually exists and a user who copies it gets exactly that version. Refresh it at each release rather than letting it drift back to a version nobody tagged. The marketplace entry stays as a documented alternative.

A fifth thing to keep coherent is not a version at all, which is why it is the one that slips: `plugin.json`'s `description` and the fusion entry's `description` in `marketplace.json` describe one product out of two repositories, and each install path shows only its own. They drift when a release rewrites one and leaves the other alone, which is what v9.0.0 did: the marketplace copy was brought up to date while the manifest went on describing the previous shape. Nothing catches that, because two version strings are either equal or not while two prose descriptions can both be well-formed and still disagree, so rewrite the pair together in the same release and read the two side by side before pushing.

| A protected path was changed and the guard wrote it back, halting the write tools | Cannot happen at HEAD. The whole protected-path half — the write-tool deny, the before/after fingerprint, the write-back, the `FUSION_ALLOW_RULES_WRITE` exemption and the `guard.protectedPaths` configuration leaf — was removed on 260812. If you meet this, you are running an installed copy older than that; `fusion --update` and restart, since the hooks always run from the installed copy and are pinned for the whole session. |
| A consuming project is halted and nothing at HEAD could have raised it | Expected, and it is the migration case. A halt raised by a removed mechanism is a value in that project's `escalation.json`, and it outlives the code that wrote it. At this version it blocks nothing: the halt check, the consecutive-block counter, the escalation module and the halt-clearing script all went on 260816, and no shipped code reads or rewrites the file. `/fusion:setup` offers to delete it. All three properties — nothing blocks, nothing rewrites the file, the offer exists — are pinned by `hooks/lib/__tests__/legacy-halt-clearing.test.ts` against both triggers no surviving code produces (`protected_path`, `protected_path_measured`). |
| A consuming project sees an advisory on every tool call naming `fusion-guard.json`, or one naming `guard`, `decisions` or `escalation` | Working as designed, and the two are the v10 migration. The first says that project's root still carries `fusion-guard.json`, which fusion no longer reads a byte of: if that file set a Turn budget, copy `{"orchestrator": {"maxTurns": <n>}}` into `fusion.json` **first**, because a budget left behind is silently not applied, then delete the old file. The second says the new file still carries one of the three retired top-level keys; delete the key. Nothing else in either file is affected while the advisory stands. `docs/upgrading-to-v10.md` states both at length. |
| An agent writes a plan / issue / decision to the workbench root or into the wrong Circle (v4.0.0+) | The prompt named a store directory as a path literal instead of resolving it through `bin/fusion-paths`. Since the v4.0.0 Circle-container restructure, store paths are NOT written in prompts — the agent resolves `$OUT_*` / `$SCAN_*` at Setup step 2 (alongside `bin/fusion-rules`) and the resolver decides Circle-vs-`shared/` from `.active-circle` + the Origin Rule. Two guards make a hard-coded literal impossible to ship: the resolver exits 4 (not a silent `KEY=`) when a prompt names a key it can't value, and the path-lint test (`hooks/lib/__tests__/path-literal-lint.test.ts`) fails `npm test` if any type-folder literal reappears in an `agents/*.md` or `skills/*/SKILL.md`. The files allowed to name store literals are enumerated as `DEFINITION_SITES` in that same test — `rules/fusion-workbench-conventions.md`, `bin/fusion-paths`, and the two rule files that inherited a definition when the conventions file was partitioned (`workbench-path-resolution.md`, `circle-records.md`). They sit outside the gate's file set by construction, so the list grants nothing; it exists so that a fifth site has to be added by hand rather than arriving because the gate never looked. If a write still lands wrong, check whether the consumer actually calls `fusion-paths <name>` under its own name (agents AND skills share one flat namespace). |
