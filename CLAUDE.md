# CLAUDE.md — fusion plugin source

**Language:** de

This repository is the **source of the fusion Claude Code plugin** (`tenzoki-plugins/fusion`). It is *not* a fusion-consuming project. The plugin's **write guard** self-disables here: `hooks/guard.ts` detects when cwd has `.claude-plugin/plugin.json` matching the plugin's own name and stands the write-protection (agents/**, rules/**, plugin.json, etc.) down so a fusion developer can edit its own source. Since v5.x that stand-down covers **both** halves of the write protection; since v6.0.0 the second half is the protected-path measurement in `hooks/tracker.ts` rather than the shell-command check it replaced, so the pair is now the four write tools and that measurement. Both stand down here because leaving one active while the other stood down would teach an agent to route around the guard rather than respect it, and because a measurement left running here would revert a fusion developer's own edits on the next tool call. The **git branch-switch policy stays active even here** — it only ever gated the agent's Bash tool calls, never the human's own terminal, so disabling it bought no human freedom while removing agent protection exactly where fusion is developed. Agents in this repo are still blocked from `git switch` / `git checkout <branch>` / `git worktree add` unless `FUSION_ALLOW_BRANCH_SWITCH=1` / `FUSION_ALLOW_WORKTREE=1` is set.

## What this is

Plugin published to the `tenzoki-plugins` marketplace (repo: `tenzoki/claude-plugins`). Provides:

- 16 specialized agents — orchestrator (top-level dispatcher) plus coder, ontocoder, coderev, ontorev, conceptrev, planner, shaper, taskplanner, reconciler, analyst, investigator, bugfixer, consultant, playmaker, editor. Three (`reconciler`, `taskplanner`, `planner`) are parameterised by domain (`code | data | strategic | knowledge`) since v1.11.0. `conceptrev` (added v3.24.0) is the design-diagram evaluator — it parses the Mermaid diagrams that planning/analysis agents emit and returns an advisory coherence verdict at the plan/spec gate. `editor` (added v5.2.0) is the produce-only Redakteur — it writes, revises, translates (en↔de), and renders customer-ready deliverables (Markdown, branded pptx) to a project-side location; it never reviews, files issues, or dispatches.
- Compliance guard with churn/escalation tracking (TypeScript hooks, compiled to `hooks/dist/`) — blocks the four write tools against `protectedPaths`, and measures those same paths around every guarded tool call so a change reaching them any other way is written back
- Real-time HTML monitor dashboard (`bin/monitor`)
- Pattern-based rule discovery helper (`bin/fusion-rules`)
- Per-consumer workbench path resolver (`bin/fusion-paths`) — Circle-container layout, v4.0.0+
- User-invocable skills: `/fusion:setup`, `/fusion:migrate`, `/fusion:help`, `/fusion:cleanup`, `/fusion:memo`, `/fusion:commit`, `/fusion:log-activity`, `/fusion:cadence`, `/fusion:revise-claude-md`, `/fusion:unlock`, `/fusion:archive`, `/fusion:next`, `/fusion:direct`, `/fusion:circle-stash`, `/fusion:circle-pop`, `/fusion:seed-from-plane` — one per directory under `skills/`; that listing is the authoritative set

## Layout

| Path | Purpose |
|---|---|
| `.claude-plugin/plugin.json` | Manifest. **Bump version on every change.** |
| `agents/*.md` | The 16 agent prompts. Only `orchestrator.md` declares a `tools:` allowlist (sub-agent dispatch + permitted tools); the other 15 inherit tools and model from the parent session. |
| `hooks/` | TypeScript source + compiled `dist/`. SessionStart, PreToolUse, PostToolUse hooks. Uses `process.cwd()` not `__dirname` for project-local state. The PreToolUse guard inspects `Bash` for **one** policy, the git branch/worktree policy (`lib/git-branch-guard.ts` over the `blank`-mode lexer in `lib/shell-parse.ts`, active everywhere including this repo). The protected paths are not read out of a command at all: `lib/protected-snapshot.ts` fingerprints every one of them before the tool call (`guard.ts`) and again after it (`tracker.ts`), and a path whose fingerprint moved is written back to its pre-call bytes while the halt is raised — measured, not predicted, so the route to the file (write tool, shell, `eval`, alias, a string built at run time) does not matter. That half stands down in this repo, the branch policy does not. Documented for users in `README-hooks.md` and for agents in `rules/protected-path-discipline.md`. |
| `fusion-guard.json` + `templates/fusion-guard.json` | The per-project guard configuration. `/fusion:setup` seeds the template into a consuming project's root, git-tracked so every change to what the guard protects shows in a diff; the root copy here is byte-identical to the template (pinned by `config.test.ts`). The loader merges per **leaf** key — project, then plugin `hooks/config.json`, then built-in defaults — so a declared value (including `"protectedPaths": []`) wins outright and an omitted or invalid one inherits. `guard.enabled` is the one key the project layer may not set (declaring it earns a diagnostic), and once the file exists the guard protects the file itself, whatever its own list says. |
| `bin/monitor` | HTML dashboard binary, served by the orchestrator from `fusion-workbench/monitor` (copied at Setup) |
| `bin/fusion-rules` | Per-agent rule discovery helper (used in every agent's Setup). Takes an optional second arg `fusion-rules <agent> [<topic>]` and reads an optional consuming-project manifest `./rules/context-manifest.yaml` to emit topic- and agent-scoped units (a `path` file or a `skill:<name>` pointer). When the manifest is absent, output is **byte-identical** to before (`HYG-NO-REGRESS`); a malformed manifest fails loudly (exit 3). Topic is derived from the active Circle (slug keywords, or an explicit `Topic:`/`Tags:` record line) unless the CLI arg overrides it. Convention authored in `rules/context-manifest.md` + `rules/context-lean-claude-md.md`. Added v5.x (Circle B). |
| `bin/fusion-paths` | Per-consumer path resolver (used in every agent's and skill's Setup, alongside `bin/fusion-rules`). Reads `.active-circle`, emits `KEY=value` write/scan targets (`OUT_*`, `SCAN_*`, `WORKBENCH`, `CIRCLE`) so no prompt hard-codes a store path. The set of keys a consumer gets is *derived* from grepping that consumer's own prompt — never declared. `<name>` is an agent OR a skill (one flat namespace). Exit shape mirrors `fusion-rules` (0/1/2) plus its own 3 (corrupt/orphaned `.active-circle` — user's to fix) and 4 (prompt names a key the resolver can't value — a fusion bug). Introduced v4.0.0 with the Circle-container restructure. |
| `install.sh` | HTTPS `curl \| bash` installer (repo root). Downloads the tarball into `~/.fusion`, writes the `~/.local/bin/fusion` launcher. The launcher takes an agent arg (`fusion coder`, default `orchestrator`, auto-namespaced), an opt-in `--yolo` (`--dangerously-skip-permissions`), and `--update`/`--uninstall`/`--where`. Replaced the old `bin/fu` project-local launcher (removed v3.20.0). |
| `bin/fusion-workbench-root` | Walks up from `pwd` to find a directory containing `fusion-workbench/.fusion-setup`. Prints the absolute path or exits 1. The single source of truth for "is this project fusion-set-up, and where". Hooks call the TS equivalent (`hooks/lib/workbench-root.ts`); agents call this script. |
| `bin/fusion-plugin-cwd` | Answers "is cwd the fusion plugin's own source repo?" — exit 0/1, prints nothing. The shell half of `hooks/lib/self-detect.ts` `isFusionPluginCwd()`: one criterion, two implementations, change one change the other (the pairing is commented in the helper). Consumed by `bin/fusion-rules` (work-tree rules preference) and `bin/fusion-paths` (work-tree prompt preference) — see the Rules-loading convention below. Checks `./.claude-plugin/plugin.json` **at cwd, with no upward walk** — deliberately congruent with the TS half, so from a subdirectory of this repo the helpers silently behave as in a consuming project. Used by `/fusion:setup` Step 0c to warn the user when a second orchestrator is starting against the same project. Advisory only — fusion has no concurrency lock; the warning lets the user notice the collision and decide. |

## Conventions

- **Agent dispatch** — always namespaced: `Agent(fusion:coder)`, `Agent(fusion:ontocoder)`, etc. Bare names don't resolve. Any agent with a `tools: Agent(...)` allowlist must list sub-agents in `<plugin>:<name>` form.
- **Domain / executors dispatch parameters (v1.11.0+)** — three agents accept run-time parameters passed via the dispatch prompt as plain markdown lines:
  - `taskplanner` and `reconciler` accept `**Domain:** <code|data|strategic|knowledge>` — the orchestrator detects domain at Setup Step 5 and passes it; agents default to `code` if absent.
  - `planner` accepts `**Executors:** coder, ontocoder, analyst` — pass for `strategic`/`knowledge` so plan steps can route to `analyst`. Defaults to `[coder, ontocoder]`.
  Any caller dispatching these agents from outside the orchestrator should prefix the dispatch prompt with the appropriate parameter line.
- **Rules loading** — agents call `"$FUSION_PLUGIN_ROOT/bin/fusion-rules" <agent-name>` and read every emitted path. Plugin files are NOT auto-loaded into agent context; this helper is the only correct discovery path. The helper emits `rules/agent-setup.md` **first** (Circle D) — the factored Setup contract (read-every-emitted-path, the `bin/fusion-paths` `OUT_*`/`SCAN_*` semantics, the exit-3/exit-4 distinction) that all 16 agent prompts point at through a shared Setup pointer — ahead of `fusion-workbench-conventions.md` and the other always-on rules, so an agent reads *how Setup works* before the detailed conventions. `$FUSION_PLUGIN_ROOT` is exported by `hooks/hooks.json` SessionStart. The helper searches three roots (in this order): the plugin's `rules/`, the project's `./rules/` (fusion-agent-specific rules — capture layouts, taskplanner priority overrides, anything no other Claude session would care about), and the project's `.claude/rules/` (project-wide rules every Claude session should respect — coding/ontology/normative guidelines). Filename patterns per agent are unchanged. Since v5.x (Circle B) the helper also accepts an optional topic (`fusion-rules <agent> [<topic>]`) and, if a consuming project ships `./rules/context-manifest.yaml`, additionally emits the manifest units whose agent AND topic match — `path` files loaded as today, `skill:<name>` pointers invoked on demand. Absent the manifest, the emitted set is byte-identical to before; the mechanism is authored in `rules/context-manifest.md` and the lean-`CLAUDE.md` convention in `rules/context-lean-claude-md.md`. **In this repo the helpers prefer the work tree** (v5.x, decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md` option c): when `bin/fusion-plugin-cwd` says cwd is the plugin's own repo, `bin/fusion-rules` reads the checkout's `./rules/` instead of `$FUSION_PLUGIN_ROOT/rules/`, and `bin/fusion-paths` reads the work-tree prompts instead of the install copy's. That closed the stale-rules failure where a four-day session read the installed v5.8.0 rules while editing v5.9.1 sources ($FUSION_PLUGIN_ROOT pins to the installed copy for the whole session). **The bound is exact and unforgiving:** the check is at cwd with no upward walk, so a session whose cwd is a *subdirectory* of this repo silently gets the installed copy again, indistinguishable from a legitimate consuming project — start sessions at the repo root.
- **User-facing output style** — every agent loads `rules/user-facing-output.md` (auto-emitted by `bin/fusion-rules` alongside `fusion-workbench-conventions.md` and `decision-record-examples.md`). It mandates action-first ordering, plain-English option labels, no undefined jargon, and trailing details/references blocks. Applies to status reports, gate prompts, AskUserQuestion text, session summaries — anything the user reads. Agent prompts' "Output Style" sections point at the rule and add only domain-specific bits.
- **Critical stance (v3.21.2+)** — every agent also loads `rules/critical-stance.md` (auto-emitted by `bin/fusion-rules` alongside the three files above). Unlike `user-facing-output.md`, which governs *formatting*, this rule governs *reasoning substance*: (1) own your errors instead of praising the user who caught them, (2) no premature/half-baked solutions — research the root cause and prefer the clean integrated fix over additive workarounds, (3) calibrated certainty — separate verified from inference from speculation, label the latter two, and never dress an unchecked claim as a checked one. It generalises to every agent (notably the orchestrator) the per-agent honesty lines that consultant/analyst/coderev/ontorev/investigator already carried.
- **The two guard rules (v5.x)** — every agent loads `rules/git-branch-discipline.md` and its sibling `rules/protected-path-discipline.md` (both auto-emitted by `bin/fusion-rules`, in that order). The first is the agent-facing half of the one remaining `Bash` policy; the second is the agent-facing half of the protected-path measurement. Since the classifier fell (v6.0.0, Circle `circles/260807-0923-guard-misst-statt-orakelt`) the protected-path rule is short: a changed protected path is written back and halts, the route to the file does not matter, the one narrow env override is `FUSION_ALLOW_RULES_WRITE` (rule directories only, outranked by a protected entry the project declares in `fusion-guard.json`), and the way out is the Human Gate. It no longer carries a command grammar or a residual catalogue, because measuring the result needs neither. Its job is that an agent never meets an unexplained revert and works around it — the failure the branch rule was written to prevent. **The always-on set is an explicit `emit_if_exists` list in `bin/fusion-rules`** (not a pattern match), so a new always-on rule needs a line there or it will not load.
- **Two stylometric profile families (v3.16.0+)** — both under `./fusion-workbench/stilwerk/`, both resolved from CLAUDE.md's `**Language:**` line (`en`/`de`): `default-voice-<lang>.yaml` is the long-form **writing** profile (narrative outputs: session summaries, consultant reports, analysis reports, spec/plan prose), emitted by `bin/fusion-rules` only for the nine prose agents. `chat-voice-<lang>.yaml` is the short-form **chat** profile (gate prompts, AskUserQuestion text, status reports, chat replies), emitted for **every** agent; it is a lean blacklist (em-dash/AI-tell anti-patterns) plus a minimal terse-and-direct whitelist, carrying no sentence-length bands so it never fights the length caps in `user-facing-output.md`. The chat profile's apply-to-short-form semantics live centrally in `user-facing-output.md` `## Style anti-patterns apply to everything`; agents pick it up via the "read every emitted path" rules-loading contract. Both families share one en-fallback. Setup copies all four files into the project workbench.
- **Critical procedures** — model as user-invocable skills (e.g. `/fusion:setup`), never as "MUST" directives in agent prompts. A skill body becomes the user prompt; that's the only reliable enforcement.
- **Workbench writes** — agents write only to `fusion-workbench/`. Sub-agents share no memory; everything persists through workbench files.
- **Workbench bootstrap is exclusive to `/fusion:setup`** — since v2.5.0, **only** the setup skill creates a workbench. Setup writes `fusion-workbench/.fusion-setup` (a JSON marker with timestamp + plugin version). Every agent and hook locates the workbench by walking up from `pwd` looking for that marker (`bin/fusion-workbench-root` for agents, `hooks/lib/workbench-root.ts` for hooks). If no marker is found: agents halt with "run /fusion:setup", hooks no-op silently. This prevents stray workbench creation when a Claude session's cwd happens to be in any non-fusion directory. Since v4.0.0, setup also **detects a pre-v4 (type-folder) workbench and refuses**, pointing the user at `/fusion:migrate` — the migration skill moves the old type-folders wholesale into `shared/` and stands up the `circles/`-container scaffold (`/fusion:migrate` is the only consumer allowed to name both layouts literally, because it is the transition between them).
- **Single orchestrator per project** (advisory) — fusion has no concurrency lock. Two orchestrators running against the same project simultaneously can corrupt `agentstate.yaml` (interrupted-session resume becomes unreliable), double-dispatch tasks from the same `tasklist.md`, race on `.guard-state/{churn,cross-file,escalation}.json` counters, and produce interleaved commit history. The most damaging mode is two parallel sessions each completing half of the same task with overlapping edits. Mitigation since v2.8.0: `/fusion:setup` Step 0c checks for an active-session marker (`fusion-workbench/.session-marker` whose mtime is refreshed at each orchestrator Turn) and **warns** the user when one is detected — `running` if heartbeat ≤ 10 min ago, `stale` if older. The warning is advisory; the user can still proceed but takes responsibility for sequencing.
- **Issues vs decisions (v2.0+)** — defects ("go fix it") go to `$OUT_ISSUE` with markers `_o_/_p_/_c_/_d_`; decisions / open questions ("decide and record") go to `$OUT_DECISION` with the richer `_o_/_a_/_i_/_d_/_s_` vocabulary. Both resolve (via `bin/fusion-paths`) into the active Circle when one exists and into `shared/` when none does — the Origin Rule decides which. See `rules/fusion-workbench-conventions.md` for the decision rule and the decision-record template.
- **SessionStart hook output** — `systemMessage` JSON for user-visible banners; plain stdout is `additionalContext` for the model only.
- **`.gitignore`** — for shipped binaries inside excluded dirs use `dir/*` (file pattern) so `!path` exceptions work for new files. `dir/` (trailing slash) blocks all re-inclusion of files added later.
- **Circles (v3+ via Track C; became the container in v4.0.0)** — a Circle is a *directory* under `fusion-workbench/circles/<stamp>-<slug>/` that holds the `_t_circle.md` record plus that unit of work's own artifact subdirectories. The state marker sits on `_t_circle.md`, not on the directory (the directory name is stable across the whole lifecycle, so references into a Circle never break, and the later Plane mirror gets an immutable natural key). Empty or absent `circles/` preserves single-Circle behaviour. Playmaker is the dispatchable agent for portfolio ranking; `/fusion:next` is the user surface. See `rules/circle-records.md` for the vocabulary and the two correct glob forms (one state via `_t_circle.md`, all states via `*_circle.md` with the marker read from the name — the underscore is inert in globs, so neither needs escaping).
- **Bus protocol removed (v3.15.0)** — earlier versions of fusion shipped a workbench-mediated A2A messaging surface under `fusion-workbench/bus/`. It was removed in v3.15.0; concurrent agent sessions exchange work through the user (copy-paste between chat windows) again, the same way they did pre-v3.4. Consultant remains user-initiated; reviewers (coderev / ontorev) file findings as issues, not as bus messages. The bus-era decision records were marked superseded by this removal and have since left the workbench (archived/cleaned); no live record documents the old protocol.

## Release process

Two repos involved: the **plugin** (this repo, `tenzoki/fusion`) and the **marketplace** (`tenzoki/claude-plugins`).

**The marketplace working clone is at `/Users/k1/Projects/productive/F03-CLAUDE-plugin-marketplace/claude-plugins`** (note the nested directory — the outer one is not the repo). That is the clone the release steps below mean. It is a development checkout, not the cache clone `/plugin install` reads: see the note after step 6, which is a separate copy and may not exist at all. At v6.0.0 it did not, so a release can complete correctly while `/plugin install` still serves the previous version locally.

Every release:

0. **Validate first:** `claude plugin validate .` must report **passed** (warnings are fine). This catches broken agent frontmatter before it ships — e.g. an unquoted `:` in a `description` makes the whole frontmatter fail to parse and the agent loads with empty metadata. Also run a smoke test that the default agent resolves under the install mechanism: `claude --plugin-dir . --agent fusion:orchestrator -p "reply SMOKE-OK"` (a wrong agent name aborts Claude immediately at startup). If the release touches the guard, also confirm before tagging that its behaviour was verified against a project root that is **not** this repository (the guard-harness integration tests spawn such roots; a scratch consuming project works too) — the write guard's self-detect stand-down here makes local testing unrepresentative by construction.
1. Bump `.claude-plugin/plugin.json` `version`
2. `git -C <marketplace> pull --rebase origin main` (it can drift if edited from elsewhere)
3. Bump fusion's `version` in `<marketplace>/.claude-plugin/marketplace.json`
4. Commit and push **both** repos
5. **Tag the fusion release** on the commit you just pushed: `git tag -a v<version> -m "fusion v<version>" && git push origin v<version>`. The tag is what `install.sh`'s `FUSION_REF=tags/v<version>` pinning resolves against — skip it and the documented pin is unusable for that version. (Tagging started at v5.5.0; `v5.5.0` was applied retroactively to its release commit.)
6. To pick up the new version locally:
   ```bash
   git -C ~/.claude/plugins/marketplaces/tenzoki-plugins pull origin main
   ```
   Then in Claude Code: `/plugin install fusion@tenzoki-plugins` and `/reload-plugins`.

**And between releases, before rule or guard work in this repo: run `fusion --update` and restart the session.** The work-tree preference (see Layout, `bin/fusion-plugin-cwd`) covers only `bin/fusion-rules` and `bin/fusion-paths` — the hooks themselves (guard, tracker) always run from the installed copy, pinned for the whole session, so a stale install still means stale guard behaviour while you edit guard sources. Behaviour rule (a) of decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md`; it stays documented here even though option (c) landed, for exactly that residual.

The marketplace **cache clone** at `~/.claude/plugins/marketplaces/<name>/` is the source-of-truth `/plugin install` reads — not the GitHub remote, and not the working clone named at the top of this section. Without the manual `git pull` on that cache clone, version bumps don't propagate locally even after uninstall/reinstall. If it does not exist (it did not at v6.0.0), `/plugin install` cannot see the release at all; `install.sh` is unaffected, because it reads the GitHub tarball directly.

### HTTPS installer (`install.sh`) — the recommended end-user path

`install.sh` at the repo root is a `curl | bash` installer that downloads the plugin tarball over plain HTTPS (`https://github.com/tenzoki/fusion/archive/refs/heads/main.tar.gz`), unpacks it into `~/.fusion`, and writes a `~/.local/bin/fusion` launcher that runs `claude --plugin-dir ~/.fusion --agent fusion:orchestrator`. It sidesteps the three marketplace failure modes for end users: git/SSH cloning, the unreliable plugin cache, and broken uninstall. Modelled on `tenzoki/flight`'s installer (v0.6.0).

fusion-specific invariants the installer relies on:
- **Compiled hooks must be committed.** `hooks/dist/*.js` are in git (`.gitignore` has the `!hooks/dist/` exception) and are self-contained (no external `require`s) — the tarball is runnable with no `npm`/`node_modules`. The installer defensively `rm -rf`s `hooks/node_modules` after copy.
- **`bin/` executables ship with the +x bit** (preserved through tar/`cp -R`).
- **`CLAUDE_PLUGIN_ROOT` resolves to `~/.fusion`** under `--plugin-dir`, so the SessionStart hook's `export FUSION_PLUGIN_ROOT=${CLAUDE_PLUGIN_ROOT}` and all `bin/` helpers work.
- The installer copies plugin assets (`.claude-plugin agents skills rules hooks bin stilwerk templates docs settings.json README*.md`) — `settings.json` ships fusion's scoped permission auto-allows so an HTTPS install has permission parity with a marketplace install. It never copies `CLAUDE.md` or `.gitignore` (dev-only), and defensively drops `hooks/node_modules`.

So there are effectively **four version surfaces** to keep coherent: `plugin.json`, `marketplace.json`, the `install.sh` header comment's `FUSION_REF=tags/v<version>` example, and the same pin example in `README.md` (the surface a user reads first — it drifted for months because the old count stopped at three). The default ref is `heads/main`, so a stale example still doesn't break a plain install — but since step 5 tags every release, the example now names a tag that actually exists and a user who copies it gets exactly that version. Refresh it at each release rather than letting it drift back to a version nobody tagged. The marketplace entry stays as a documented alternative.

## Testing during development

Use `claude --plugin-dir /path/to/this/repo` to load directly from disk — no install, no cache, no version bumping required. Reserve the marketplace flow for releases.

## Where to look when something breaks

| Symptom | Likely cause |
|---|---|
| `Agent type 'X' not found` / `denied by permission rule 'Agent(...)' from settings` | Agent dispatch with bare name, or `tools:` allowlist missing namespace prefix. Every dispatch must use `<plugin>:<name>` form. |
| Agent reports it can't find a rule file | Rule discovery not run, or the expected file is project-specific — the plugin ships only its own `rules/` directory (the always-on set plus the conditional emissions in `bin/fusion-rules`); domain rules must live in `./rules/` or `.claude/rules/` of the consuming project. Problem 10. |
| Investigator halts at Setup with "no investigator rules found" | The project hasn't copied `templates/investigator-capture-layout.md` to `./rules/investigator-capture-layout.md` and filled it in. The investigator is fully project-agnostic since v2.1; it requires this rule to know where captures live. |
| Agent halts at Setup with "no fusion workbench found above pwd" | The project never ran `/fusion:setup`, or setup ran in a different directory. Run `/fusion:setup` at the project root once. The setup skill writes `fusion-workbench/.fusion-setup` which all subsequent agents and hooks look for. |
| Stray empty `fusion-workbench/.guard-state/` directories appearing in random folders | Pre-v2.5 behavior. Hooks bootstrapped the workbench from any `process.cwd()` they fired in. Fixed in v2.5: hooks no-op when no `.fusion-setup` marker is found upward. Safe to delete the stray directories. |
| All sub-agents fail to load after a fusion upgrade | Likely a frontmatter-syntax breakage. v2.8.1 added `disallowedTools: [Agent]` to 12 agents based on docs that turned out incorrect for our parser; agent loading broke entirely. Rolled back in v2.8.3. **Lesson:** changes to agent frontmatter beyond `name`/`description`/`tools` need empirical verification (run a sub-agent dispatch end-to-end) before release, not just docs-driven inference. |
| Orchestrator skipped Setup, dashboard never refreshed | "MUST run Setup" in agent prompt was overridden by user task urgency. The fix is `/fusion:setup`. Problem 11. |
| `/plugin install` keeps returning an old version | Marketplace cache clone at `~/.claude/plugins/marketplaces/` is stale; manual git pull required. Problem 12. |
| SessionStart banner not visible | Hook used plain stdout instead of `systemMessage` JSON. Problem 13. |
| Orchestrator skips the portfolio hint when `_a_` Circles exist | `/fusion:setup` not re-run since Track C landed (so `circles/` isn't pre-created) OR `.active-circle` corruption preventing the count snapshot |
| `/fusion:next` errors with "no Circles yet" but `circles/` has files | All Circle files have terminal markers (`_c_`, `_b_`, `_s_`, `_d_`) — `/fusion:next` short-circuits when no `_a_` or `_t_` exist. File a fresh `_a_` Circle via shaper or the user's own request to the orchestrator. |
| Orchestrator falls back to `Agent(general-purpose)` (denied) when trying to ask the user — at interrupted-session prompt, Coherence gate, Rebalance Grounding sub-flow, etc. | `AskUserQuestion` missing from `agents/orchestrator.md` `tools:` allowlist. Fixed in v3.0.1. The skill body (`/fusion:setup`) had `AskUserQuestion` in its `allowed-tools` so the skill path worked, but the orchestrator agent itself was denied — and sub-agents (shaper, planner) inheriting from the orchestrator would also have been denied if reached. **Lesson:** when adding `AskUserQuestion` references to the orchestrator prompt, also verify the frontmatter allowlist. The orchestrator is the only agent with an explicit `tools:` line; every tool sub-agents need has to be listed there. |
| Monitor times displayed off by user's TZ offset | `orchestrator-events.jsonl` timestamps are UTC but written by `date -u +%Y-%m-%dT%H:%M:%S` without the `Z` designator. JavaScript `new Date(ts)` parses such strings as local time per ECMA-262, so any rendering via `getHours()/getMinutes()` is wrong by the user's TZ offset. **Fix at consumer:** the `parseUTCTs()` helper in `bin/monitor` (or append `Z` before parsing) — `bin/monitor` now routes the ETA (v3.9.0, `6209645`) and the event-list/warning times through it. **Lesson:** any future tool consuming `orchestrator-events.jsonl` for time-based computation (JS, Python, Go) must defensively parse — the emit convention is intentional (clean strings in the file) but transfers the parsing burden to every consumer. |
| A protected path was changed and the guard wrote it back, halting the write tools | Working as designed, in a consuming project. The guard no longer reads a command to predict a write: `lib/protected-snapshot.ts` fingerprints every path on `guard.protectedPaths` before the tool call and again after it, and any path whose bytes moved is restored to its pre-call content while the halt goes up (`hooks/tracker.ts`). The route does not matter — a write tool, a shell command of any shape, `eval`, an alias, a path built at run time — so there is nothing to rephrase and no point re-routing through `Edit`. One env override exists and it is narrow: `FUSION_ALLOW_RULES_WRITE` exempts the project's rule directories (plus their `retired/` destination) and nothing else, and a protected entry the project declares in its own `fusion-guard.json` outranks even that flag. For every other protected path there is no override: it is a human decision, and `clear-halt.js` clears the halt afterwards. In this repo the measurement stands down entirely, so seeing it here means the cwd was not the plugin root. |
| An agent writes a plan / issue / decision to the workbench root or into the wrong Circle (v4.0.0+) | The prompt named a store directory as a path literal instead of resolving it through `bin/fusion-paths`. Since the v4.0.0 Circle-container restructure, store paths are NOT written in prompts — the agent resolves `$OUT_*` / `$SCAN_*` at Setup step 2 (alongside `bin/fusion-rules`) and the resolver decides Circle-vs-`shared/` from `.active-circle` + the Origin Rule. Two guards make a hard-coded literal impossible to ship: the resolver exits 4 (not a silent `KEY=`) when a prompt names a key it can't value, and the path-lint test (`hooks/lib/__tests__/path-literal-lint.test.ts`) fails `npm test` if any type-folder literal reappears in an `agents/*.md` or `skills/*/SKILL.md`. The files allowed to name store literals are enumerated as `DEFINITION_SITES` in that same test — `rules/fusion-workbench-conventions.md`, `bin/fusion-paths`, and the three rule files that inherited a definition when the conventions file was partitioned (`workbench-path-resolution.md`, `circle-records.md`, `workbench-stash-and-lock.md`). They sit outside the gate's file set by construction, so the list grants nothing; it exists so that a sixth site has to be added by hand rather than arriving because the gate never looked. If a write still lands wrong, check whether the consumer actually calls `fusion-paths <name>` under its own name (agents AND skills share one flat namespace). |
