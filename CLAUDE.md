# CLAUDE.md — fusion plugin source

**Language:** de
**Artifact language:** en

This repository is the **source of the fusion Claude Code plugin** (`tenzoki-plugins/fusion`). It is *not* a fusion-consuming project. One part of the guard **self-disables** here: the write-tool branch of `hooks/guard.ts` recognises this repository by a `.claude-plugin/plugin.json` matching the plugin's own name, and stands down so a fusion developer can edit the plugin's own source. It was built because the guard used to protect `agents/**`, `rules/**` and the plugin manifest, which is correct for a project *using* fusion and wrong when developing fusion itself, where every edit to those files would have been blocked and written back. **That protection was removed on 260812**, along with the whole protected-path half of the guard, and the stand-down outlived it. A second stand-down covered the churn heatmap in `hooks/tracker.ts` and went with the heatmap on 260815.

**The rule the two established outlives both of them, and it is what the next stand-down is measured against:** a stand-down is evaluated in the coordinate space the mechanism keys its state by. The surviving write-tool check reads cwd (`isFusionPluginCwd()` in `hooks/lib/self-detect.ts`), because `guard.ts` computes its verdict in cwd's space; churn asked about the workbench root it walked up to (`isFusionPluginRoot(dir)`), because its keys were anchored there. A root-anchored mechanism with a cwd-anchored stand-down misses every session started one directory down, and the reverse is the reverse hole. Both halves of that were measured on the protected-path measurement — whose stand-down had to move up to the root in v6.0.1 when its measurement root did, or a session started in `fusion-workbench/`, the ordinary case here, would have begun reverting the developer's own files. Two mechanisms and their stand-downs are gone; `hooks/lib/self-detect.ts` keeps both entry points so the rule stays available to whoever needs the root-anchored form next.

A **git branch-switch policy** used to run here too, and it was the one thing the stand-down never covered. It was deleted outright on 260809: it decided from a shell command's *text* whether the command would move HEAD, which is the same undecidable question the write-path classifier answered until v6.0.0, and in one afternoon it cost five patches, a sixth open entrance, and 24 consecutive false blocks against the agents' own verification commands. Nothing about a `Bash` command is read by the guard any more, in this repository or any other, and since 260812 nothing a `Bash` command *does* is measured either.

## What this is

Plugin published to the `tenzoki-plugins` marketplace (repo: `tenzoki/claude-plugins`). Provides:

- 15 specialized agents — orchestrator (top-level dispatcher) plus coder, ontocoder, coderev, ontorev, planner, shaper, taskplanner, reconciler, analyst, bugfixer, consultant, playmaker, editor, curator. Three (`reconciler`, `taskplanner`, `playmaker`) are parameterised by domain (`code | data | strategic | knowledge`) since v1.11.0; `planner` is **not** one of them and parses no `**Domain:**` line — it takes `**Executors:**` and `**Circle:**` instead. Seven agents in all read a dispatch parameter; the roster is authored once, in `README-agents.md` `## Dispatch parameters`. `editor` (added v5.2.0) is the produce-only Redakteur — it writes, revises, translates (en↔de), and renders customer-ready deliverables (Markdown, branded pptx) to a project-side location; it never reviews, files issues, or dispatches. `curator` (added v8.2.0) reconciles a project's three normative surfaces — its decision records, its project-owned rule files and `CLAUDE.md` — against the project's own recorded history; every proposed change carries an evidence tier and a citation, and nothing lands before a user gate.
- Compliance guard with escalation tracking (TypeScript hooks, compiled to `hooks/dist/`) — blocks the four write tools against the decision-governed categories at `high` sensitivity, and halts after three consecutive blocks. It used to block them against a `protectedPaths` list as well, and to measure those paths around every guarded tool call so a change reaching them any other way was written back; that whole half was removed on 260812. It also used to count per-file churn in a heatmap and emit warning events for the monitor at configured thresholds; that half warned, never blocked, and was removed on 260815
- Real-time HTML monitor dashboard (`bin/monitor`)
- Pattern-based rule discovery helper (`bin/fusion-rules`)
- Per-consumer workbench path resolver (`bin/fusion-paths`) — Circle-container layout, v4.0.0+
- User-invocable skills: `/fusion:setup`, `/fusion:migrate`, `/fusion:help`, `/fusion:cleanup`, `/fusion:memo`, `/fusion:commit`, `/fusion:log-activity`, `/fusion:cadence`, `/fusion:revise-claude-md`, `/fusion:unlock`, `/fusion:archive`, `/fusion:next`, `/fusion:direct`, `/fusion:curate` — one per directory under `skills/`; that listing is the authoritative set

## Conventions

- **Agent dispatch** — always namespaced: `Agent(fusion:coder)`, `Agent(fusion:ontocoder)`, etc. Bare names don't resolve. Any agent with a `tools: Agent(...)` allowlist must list sub-agents in `<plugin>:<name>` form.
- **Dispatch parameters (v1.11.0+)** — seven agents read run-time parameters off the dispatch prompt as plain markdown `**<Keyword>:**` lines. **The roster is authored once, in `README-agents.md` `## Dispatch parameters`** — that table carries the agent, the line, its values, what happens when it is absent, and who passes it, each row cited to the prompt line it was read against. Do not restate it here; a second copy is how the planner came to be listed as domain-parameterised in four places while `agents/planner.md` never parsed the string. Two facts belong in this file because they shape dispatch decisions rather than describe one agent. First: `**Domain:** <code|data|strategic|knowledge>` changes behaviour in `taskplanner`, `reconciler` and `playmaker` only, defaulting to `code`; `shaper` accepts the line in anticipated-circle mode and merely copies it into the record it writes; `planner` takes `**Executors:** coder, ontocoder, analyst` (default `[coder, ontocoder]`), which the orchestrator derives from the detected domain. Second: `editor`'s `**Deliverable language:** <de|en>` is the one parameter with **no default** — the agent halts when the dispatch names no language rather than falling back to the chat or artifact declaration (decision `260807-2131_*_which-language-governs-a-customer-deliverable.md`, option 3; the customer-deliverable case in `rules/fusion-workbench-conventions.md` `## Project language`). The loudness is the point — a silent default hands the customer a finished document in the wrong language instead of stopping. Any caller dispatching these agents from outside the orchestrator prefixes the dispatch prompt with the appropriate parameter line.
- **Rules loading** — agents call `"$FUSION_PLUGIN_ROOT/bin/fusion-rules" <agent-name>` and read every emitted path. Plugin files are NOT auto-loaded into agent context; this helper is the only correct discovery path. The helper emits `rules/agent-setup.md` **first** (Circle D) — the factored Setup contract (read-every-emitted-path, the `bin/fusion-paths` `OUT_*`/`SCAN_*` semantics, the exit-3/exit-4 distinction) that every agent prompt points at through a shared Setup pointer — ahead of `fusion-workbench-conventions.md` and the other always-on rules, so an agent reads *how Setup works* before the detailed conventions. `$FUSION_PLUGIN_ROOT` is exported by `hooks/hooks.json` SessionStart. The helper searches three roots (in this order): the plugin's `rules/`, the project's `./rules/` (fusion-agent-specific rules — capture layouts, taskplanner priority overrides, anything no other Claude session would care about), and the project's `.claude/rules/` (project-wide rules every Claude session should respect — coding/ontology/normative guidelines). Filename patterns per agent are unchanged. Since v5.x (Circle B) the helper also accepts an optional topic (`fusion-rules <agent> [<topic>]`) and, if a consuming project ships `./rules/context-manifest.yaml`, additionally emits the manifest units whose agent AND topic match — `path` files loaded as today, `skill:<name>` pointers invoked on demand. Absent the manifest, the emitted set is byte-identical to before; the mechanism is authored in `rules/context-manifest.md` and the lean-`CLAUDE.md` convention in `rules/context-lean-claude-md.md`. **In this repo the helpers prefer the work tree** (v5.x, decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md` option c): when `bin/fusion-plugin-cwd` says cwd is the plugin's own repo, `bin/fusion-rules` reads the checkout's `./rules/` instead of `$FUSION_PLUGIN_ROOT/rules/`, `bin/fusion-paths` reads the work-tree prompts instead of the install copy's, and `bin/fusion-source-root` hands a skill body the checkout as the root its citations of shipped files open against. That closed the stale-rules failure where a four-day session read the installed v5.8.0 rules while editing v5.9.1 sources ($FUSION_PLUGIN_ROOT pins to the installed copy for the whole session). **The bound is exact and unforgiving:** the check is at cwd with no upward walk, so a session whose cwd is a *subdirectory* of this repo gets the installed copy again, indistinguishable *to the helpers* from a legitimate consuming project — start sessions at the repo root. It is no longer indistinguishable to **you**: `hooks/session-start.ts` warns at SessionStart whenever the workbench root sits above the working directory, which is precisely this condition, and names both directories. The warning is a signal, not a fix — the helpers still resolve against cwd and still read the installed copy.
- **User-facing output style** — every agent loads `rules/user-facing-output.md` (auto-emitted by `bin/fusion-rules` alongside `fusion-workbench-conventions.md` and `decision-record-examples.md`). It mandates action-first ordering, plain-English option labels, no undefined jargon, and trailing details/references blocks. Applies to status reports, gate prompts, AskUserQuestion text, session summaries — anything the user reads. Agent prompts' "Output Style" sections point at the rule and add only domain-specific bits.
- **Critical stance (v3.21.2+)** — every agent also loads `rules/critical-stance.md` (auto-emitted by `bin/fusion-rules` alongside the three files above). Unlike `user-facing-output.md`, which governs *formatting*, this rule governs *reasoning substance*: (1) own your errors instead of praising the user who caught them, (2) no premature/half-baked solutions — research the root cause and prefer the clean integrated fix over additive workarounds, (3) calibrated certainty — separate verified from inference from speculation, label the latter two, and never dress an unchecked claim as a checked one. It generalises to every agent (notably the orchestrator) the per-agent honesty lines that consultant/analyst/coderev/ontorev already carried.
- **No guard rule is emitted any more.** The always-on `protected-path-discipline.md` (under `rules/` until 260812) was the agent-facing half of the protected-path measurement and went with it, as its sibling rule for the branch policy had gone on 260809. It was 10 541 bytes on every one of the sixteen agents' every dispatch. **Measured on 260812, the day it went:** the always-on floor stood at 98 443 bytes per dispatch before the removal, 91 090 of shipped rule text plus this project's 7 353-byte chat voice profile, and the step took 10 420 off that rather than the full 10 541, because it also had to correct a present-tense claim in `rules/critical-stance.md` that the removal made false, at +121 bytes. **The floor as it stands today is deliberately not stated here.** It moves with every rule edit, so any number written into this line is stale before it is committed: by 260813 the two that stood here had each drifted 5 796 bytes low. Measure it when you need it, with `wc -c` over the always-on set — the **unindented** `emit_if_exists` lines in `bin/fusion-rules`, plus the project's chat voice profile. The indented ones are conditional emissions and are not part of the floor; the same `wc -c` over those three files gives what they add, which has been about a third again. In this repository `bin/fusion-rules coder | xargs wc -c` prints the same total in one command, because `coder` draws no conditional rule. **Consequence worth knowing:** no rule now tells a sub-agent what a halt is or how it is cleared. A halt is still reachable — three consecutive CHECK 3 blocks — and a legacy halt from the removed mechanism still blocks and still clears; what an agent has is the block message itself, which names the full `cd <project-root> && node <plugin-root>/hooks/dist/clear-halt.js` command. **The always-on set is an explicit `emit_if_exists` list in `bin/fusion-rules`** (not a pattern match), so a new always-on rule needs a line there or it will not load.
- **Two stylometric profile families (v3.16.0+)** — both under `./fusion-workbench/stilwerk/`, each resolved from its own CLAUDE.md declaration line (`en`/`de`) by the rule that owns that resolution and every fallback in it, `rules/fusion-workbench-conventions.md` `## Project language`: `default-voice-<lang>.yaml` is the long-form **writing** profile (narrative outputs: session summaries, consultant reports, analysis reports, spec/plan prose), resolved from `**Artifact language:**` and emitted by `bin/fusion-rules` only for the prose agents. `chat-voice-<lang>.yaml` is the short-form **chat** profile (gate prompts, AskUserQuestion text, status reports, chat replies), resolved from `**Language:**` and emitted for **every** agent; it is a lean blacklist (em-dash/AI-tell anti-patterns) plus a minimal terse-and-direct whitelist, carrying no sentence-length bands so it never fights the length caps in `user-facing-output.md`. The chat profile's apply-to-short-form semantics live centrally in `user-facing-output.md` `## Style anti-patterns apply to everything`; agents pick it up via the "read every emitted path" rules-loading contract. Setup copies all four files into the project workbench.
- **Critical procedures** — model as user-invocable skills (e.g. `/fusion:setup`), never as "MUST" directives in agent prompts. A skill body becomes the user prompt; that's the only reliable enforcement.
- **Workbench writes** — agents write only to `fusion-workbench/`. Sub-agents share no memory; everything persists through workbench files.
- **Workbench bootstrap is exclusive to `/fusion:setup`** — since v2.5.0, **only** the setup skill creates a workbench. Setup writes `fusion-workbench/.fusion-setup` (a JSON marker with timestamp + plugin version). Every agent and hook locates the workbench by walking up from `pwd` looking for that marker (`bin/fusion-workbench-root` for agents, `hooks/lib/workbench-root.ts` for hooks). If no marker is found: agents halt with "run /fusion:setup", hooks no-op silently. This prevents stray workbench creation when a Claude session's cwd happens to be in any non-fusion directory. Since v4.0.0, setup also **detects a pre-v4 (type-folder) workbench and refuses**, pointing the user at `/fusion:migrate` — the migration skill moves the old type-folders wholesale into `shared/` and stands up the `circles/`-container scaffold (`/fusion:migrate` is the only consumer allowed to name both layouts literally, because it is the transition between them).
- **Single orchestrator per project** (advisory) — fusion has no concurrency lock. Two orchestrators running against the same project simultaneously can corrupt `agentstate.yaml` (interrupted-session resume becomes unreliable), double-dispatch the same work, race on the `.guard-state/escalation.json` counter, and produce interleaved commit history. The most damaging mode is two parallel sessions each completing half of the same task with overlapping edits. Mitigation since v2.8.0: `/fusion:setup` Step 0c checks for an active-session marker (`fusion-workbench/.session-marker` whose mtime is refreshed at each orchestrator Turn) and **warns** the user when one is detected — `running` if heartbeat ≤ 10 min ago, `stale` if older. The warning is advisory; the user can still proceed but takes responsibility for sequencing.
- **Issues vs decisions (v2.0+)** — defects ("go fix it") go to `$OUT_ISSUE` with markers `_o_/_p_/_c_/_d_`; decisions / open questions ("decide and record") go to `$OUT_DECISION` with the richer `_o_/_a_/_i_/_d_/_s_` vocabulary. Both resolve (via `bin/fusion-paths`) into the active Circle when one exists and into `shared/` when none does — the Origin Rule decides which. See `rules/fusion-workbench-conventions.md` for the decision rule and the decision-record template.
- **SessionStart hook output** — `systemMessage` JSON for user-visible banners; plain stdout is `additionalContext` for the model only.
- **`.gitignore`** — for shipped binaries inside excluded dirs use `dir/*` (file pattern) so `!path` exceptions work for new files. `dir/` (trailing slash) blocks all re-inclusion of files added later.
- **Circles (v3+ via Track C; became the container in v4.0.0)** — a Circle is a *directory* under `fusion-workbench/circles/<stamp>-<slug>/` that holds the `_t_circle.md` record plus that unit of work's own artifact subdirectories. The state marker sits on `_t_circle.md`, not on the directory (the directory name is stable across the whole lifecycle, so references into a Circle never break, and the later Plane mirror gets an immutable natural key). Empty or absent `circles/` preserves single-Circle behaviour. Playmaker is the dispatchable agent for portfolio ranking; `/fusion:next` is the user surface. See `rules/circle-records.md` for the vocabulary and the two correct glob forms (one state via `_t_circle.md`, all states via `*_circle.md` with the marker read from the name — the underscore is inert in globs, so neither needs escaping).
- **Bus protocol removed (v3.15.0)** — earlier versions of fusion shipped a workbench-mediated A2A messaging surface under `fusion-workbench/bus/`. It was removed in v3.15.0; concurrent agent sessions exchange work through the user (copy-paste between chat windows) again, the same way they did pre-v3.4. Consultant remains user-initiated; reviewers (coderev / ontorev) file findings as issues, not as bus messages. The bus-era decision records were marked superseded by this removal and have since left the workbench (archived/cleaned); no live record documents the old protocol.

## Release process

Two repos involved: the **plugin** (this repo, `tenzoki/fusion`) and the **marketplace** (`tenzoki/claude-plugins`).

**The marketplace working clone is at `/Users/k1/Projects/productive/F03-CLAUDE-plugin-marketplace/claude-plugins`** (note the nested directory — the outer one is not the repo). That is the clone the release steps below mean. It is a development checkout, not the cache clone `/plugin install` reads: see the note after step 6, which is a separate copy and may not exist at all. At v6.0.0 it did not, so a release can complete correctly while `/plugin install` still serves the previous version locally.

Every release:

0. **Validate first:** `claude plugin validate .` must report **passed** (warnings are fine). This catches broken agent frontmatter before it ships — e.g. an unquoted `:` in a `description` makes the whole frontmatter fail to parse and the agent loads with empty metadata. Also run a smoke test that the default agent resolves under the install mechanism: `claude --plugin-dir . --agent fusion:orchestrator -p "reply SMOKE-OK"` (a wrong agent name aborts Claude immediately at startup). If the release touches the guard, also confirm before tagging that its behaviour was verified against a project root that is **not** this repository (the guard-harness integration tests spawn such roots; a scratch consuming project works too) — the write guard's self-detect stand-down here makes local testing unrepresentative by construction.
1. Bump `.claude-plugin/plugin.json` `version`
2. `git -C <marketplace> pull --rebase origin main` (it can drift if edited from elsewhere)
3. Bump fusion's `version` in `<marketplace>/.claude-plugin/marketplace.json`
4. Commit and push **both** repos
5. **Tag the fusion release** on the commit you just pushed: `git tag -a v<version> -m "fusion v<version>" && git push origin v<version>`. The tag is what `install.sh`'s `FUSION_REF=tags/v<version>` pinning resolves against — skip it and the documented pin is unusable for that version. (Tagging started at v5.5.0; `v5.5.0` was applied retroactively to its release commit.)
6. To pick up the new version locally:
   ```bash
   git -C ~/.claude/plugins/marketplaces/tenzoki-plugins pull origin main
   ```
   Then in Claude Code: `/plugin install fusion@tenzoki-plugins` and `/reload-plugins`.

**And between releases, before rule or guard work in this repo: run `fusion --update` and restart the session.** The work-tree preference (see Layout, `bin/fusion-plugin-cwd`) covers only `bin/fusion-rules`, `bin/fusion-paths` and `bin/fusion-source-root` — and the third of those roots which *documents* a skill body opens, never which helper it runs, because whether the preference reaches helper resolution is part (c) of decision `260810-1544` and is unanswered. The hooks themselves (guard, tracker) always run from the installed copy, pinned for the whole session, so a stale install still means stale guard behaviour while you edit guard sources. Behaviour rule (a) of decision `260806-0015_*_veraltete-regeln-im-eigenen-repo-melden-oder-umgehen.md`; it stays documented here even though option (c) landed, for exactly that residual.

The marketplace **cache clone** at `~/.claude/plugins/marketplaces/<name>/` is the source-of-truth `/plugin install` reads — not the GitHub remote, and not the working clone named at the top of this section. Without the manual `git pull` on that cache clone, version bumps don't propagate locally even after uninstall/reinstall. If it does not exist (it did not at v6.0.0), `/plugin install` cannot see the release at all; `install.sh` is unaffected, because it reads the GitHub tarball directly.

### HTTPS installer (`install.sh`) — the recommended end-user path

`install.sh` at the repo root is a `curl | bash` installer that downloads the plugin tarball over plain HTTPS (`https://github.com/tenzoki/fusion/archive/refs/heads/main.tar.gz`), unpacks it into `~/.fusion`, and writes a `~/.local/bin/fusion` launcher that runs `claude --plugin-dir ~/.fusion --agent fusion:orchestrator`. It sidesteps the three marketplace failure modes for end users: git/SSH cloning, the unreliable plugin cache, and broken uninstall. Modelled on `tenzoki/flight`'s installer (v0.6.0).

fusion-specific invariants the installer relies on:
- **Compiled hooks must be committed.** `hooks/dist/*.js` are in git (`.gitignore` has the `!hooks/dist/` exception) and are self-contained (no external `require`s) — the tarball is runnable with no `npm`/`node_modules`. The installer defensively `rm -rf`s `hooks/node_modules` after copy.
- **`bin/` executables ship with the +x bit** (preserved through tar/`cp -R`).
- **`CLAUDE_PLUGIN_ROOT` resolves to `~/.fusion`** under `--plugin-dir`, so the SessionStart hook's `export FUSION_PLUGIN_ROOT=${CLAUDE_PLUGIN_ROOT}` and all `bin/` helpers work.
- The installer copies plugin assets (`.claude-plugin agents skills rules hooks bin stilwerk templates docs settings.json README*.md`), and `settings.json` is inert among them. **A plugin's own `settings.json` is not a permission source under `--plugin-dir`**, measured on Claude Code 2.1.226 by placing one identical `permissions.allow` entry in each of two locations: a project's `.claude/settings.json` honoured it, the plugin's `settings.json` did not. So the 16 scoped auto-allows it ships grant nothing, to an HTTPS install and a marketplace install alike — the parity this line used to claim holds only in the sense that both paths get zero. A fusion session's permissions come entirely from whatever `.claude/settings.json` or `.claude/settings.local.json` the consuming project holds, which is what `/fusion:unlock` writes; making `/fusion:setup` seed the same file is tracked in `fusion-workbench/shared/issues/260810-0326_o_setup-must-seed-claude-settings-because-the-plugin-settings-json-is-not-a-permission-source.md`, which also records that the scoped path patterns in that file (`Write(fusion-workbench/**)` and its siblings) did not match even from a source that *is* read. Do not conclude from its contents what a session is allowed to do. The installer never copies `CLAUDE.md` or `.gitignore` (dev-only), and defensively drops `hooks/node_modules`.

So there are effectively **four version surfaces** to keep coherent: `plugin.json`, `marketplace.json`, the `install.sh` header comment's `FUSION_REF=tags/v<version>` example, and the same pin example in `README.md` (the surface a user reads first — it drifted for months because the old count stopped at three). The default ref is `heads/main`, so a stale example still doesn't break a plain install — but since step 5 tags every release, the example now names a tag that actually exists and a user who copies it gets exactly that version. Refresh it at each release rather than letting it drift back to a version nobody tagged. The marketplace entry stays as a documented alternative.
