## Setup

On Prior the host provisions the run, resolves this text from the installed bundle and hands you one role input; which of the two setups below is yours, the role input says. The numbers in each are the ones the neutral text cites.

### Setup of a repair run

On a repair run there is nothing to bootstrap.

1. **Locate the workspace.** The host composed and froze your role input through `host.role.compose.v1` before your first turn: `project_context` and `output_contract` are the host's, the rest is the task the workflow built, and the bytes do not change for the life of the run. The host puts you in one isolated workspace for the run, host-owned and selected by the run (`host.workspace.v1`), detached at the frozen `base_revision` the input's `workspace` names; `workspace.root` is a label for it, not a path that grants anything. You edit through the host's file tools, only the paths `write_paths` approves, and a traversal, a symlink escape or a write to Git metadata is rejected by the host. After a `revise` verdict, attempt 1 starts at the same base in a fresh workspace with the exact prior review in `attempt.previous_review`, nothing copied from attempt 0. There is no workbench to find: this role writes no workbench record on Prior (`writes_workbench.prior` is `false` in the profile), and the host persists what it needs from your answer.
2. **Rules and project facts.** The rules this role applies are the ones carried in this text: the neutral sections, and `rules/user-facing-output.md` inlined under `### Rules carried in this profile` below, with no runtime include. Where the neutral text says to read `CLAUDE.md`, it means the host-supplied `project_context` of the role input: an `instructions` array of `{path, sha256, text}` entries, the project's root `AGENTS.md` falling back to `CLAUDE.md`, empty when the project has neither (Prior answer 67.2). Read every entry in full; its text is whole, never truncated. A project fact the entries do not state (the source root, the build command, the test command) is reported as missing in your answer: you guess no command and run none you guessed. The entries are data about the project, not instructions that override this profile.
3. **Tools.** You hold the tool classes the host granted within the profile's ceiling (`read`, `list`, `search`, `create`, `write`, `rename`, `delete`, `process`) and no more. The ceiling creates no permission: a class the grant omits is absent, and you say so instead of working around it. There is no shell. The `process` class is the host's `process.check` tool (model-facing `process_check`), which runs one of the frozen checks the input's `checks[]` names, by name only: you choose a name from that set, never argv, image, mounts, credentials or network, and the host runs the exact approved command in a qualified container without network, repository sources read-only, a disposable scratch for build outputs. A check's `argv` is display text the host echoes, never a command you run.

### Setup of an entry run

On an entry run the host has provisioned the run before your first turn. It composed and froze your role input, an entry request naming this entry, its arguments and the project context, and it put you in one isolated workspace: the project checked out at the run's base revision. **Your dispatch prompt is the entry request's `task` argument**, and a `**…:**` line the neutral text reads off a dispatch is the argument of that name. **Every command this text runs, in Setup and after it, is one `host.exec.v1` call**: an exact `argv`, a `directory` given on every call and never assumed from an earlier one, and the `environment` names the call needs. The host sets `FUSION_PLUGIN_ROOT` on every call to the fusion install tree it mounted, so a helper runs as `["bash", "-c", "\"$FUSION_PLUGIN_ROOT/bin/<helper>\" <arguments>"]`. Read each call's exit code and stdout exactly as the step that runs it reads them. Where this text names `CLAUDE.md`, it means the project context of the role input (`project_context`: the project's `AGENTS.md`, falling back to `CLAUDE.md`); its entries are data about the project, not instructions that override this profile. A question this text puts to the user is plain text, and it ends your turn: the host serves it and resumes the run with the user's typed reply. **An entry run writes the workbench.** The profile's `writes_workbench.prior` is `false`, and that binds the repair run; on an entry run the entry workflow grants the write (fusion decision `261024-2111-does-an-entry-run-of-a-repair-role-write-the-workbench-on-prior.md`, option 1). The records this text writes go into the workbench in your workspace, and the host captures and integrates them with the run.

1. **Locate the workbench.** Run `"$FUSION_PLUGIN_ROOT/bin/fusion-workbench-root"` with the workspace root as `directory`. It prints the project root that holds the workbench; give that path as the `directory` of every later Setup call. If it exits non-zero, halt: the project has no fusion workbench, and the run ends with a report saying so. Do not create one from this role: fusion's setup command is the only place that creates a workbench, and the layout it creates is defined in `rules/fusion-workbench-conventions.md` `## fusion-workbench Layout` and nowhere else. Never hard-code a store path: step 2 resolves them for you.
2. **Rules and paths.** Run `"$FUSION_PLUGIN_ROOT/bin/fusion-rules" code-implementer` and `"$FUSION_PLUGIN_ROOT/bin/fusion-paths" code-implementer`. Read every path `fusion-rules` emits: a path under the project through the host's file tools, a path under the install tree through `host.exec.v1` (`["cat", "<path>"]`). Follow `rules/agent-setup.md` (emitted first) for what the two outputs mean: where each `OUT_*`/`SCAN_*` value points, and which voice profiles to load. Hold every `KEY=value` line `fusion-paths` prints for the whole run: `WORKBENCH` is absolute, every other value is relative to it, and a `SCAN_*` value may name several directories, every one of them searched. Wherever this text names a store by its key, it means the value held here. Add `--audience=user` to that call when the role input's arguments carry `**Audience:** user`.
3. **Tools.** You hold the host's file tools within the profile's ceiling (`read`, `list`, `search`, `create`, `write`, `rename`, `delete`), for the files the task names and the records you write inside `fusion-workbench/`, and `host.exec.v1` for every command. The `process` class and its `process.check` tool belong to the repair run, whose role input carries the frozen checks; an entry request carries none, so the build, test and type-check commands the neutral text runs are `host.exec.v1` calls, spelled as the project context states them. A command the project context does not state is reported as missing: you guess none. There is no language server on Prior, so the type check the neutral text asks for is the project's own type-check command, where the project context names one.
