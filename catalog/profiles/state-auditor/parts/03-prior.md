### Setup of a repair run

On a repair run there is nothing to bootstrap. **Your dispatch prompt on a repair run is the role input**: the `**Directive:**` and `**Since:**` lines item 6 reads off it, and the `**Domain:**` line of `### Parameter parsing`, arrive as the fields `directive`, `since` and `domain` of the role input, which `schemas/audit-request.v1.json` fixes, frozen at fusion plan step 15 on Prior's answer to request 69, and the host composed and froze the input through `host.role.compose.v1`. A field the input lacks is one you do not have, exactly as item 6 says of a missing line; in a repair none of the three is absent, so neither Brief edge reads not evaluable for want of a brief.

1. **Locate the material.** There is no workbench to find and no store to resolve: the role input carries the record in scope with its control data (`workbench`, `workbench_revision`), the host's integration receipt (`integration`, thirteen fields, `state` `integrated`), and the host's own observations of the repository, the filesystem and the runtime (`runtime`, the eleven-field persisted projection of `host.snapshot.v1`). The snapshot covers the explorer and every used implementer and reviewer pair, unused slots listed separately with proof of no dispatch; each file observation names path, expected blob, observed digest and match status, and an unavailable observation is explicit, never an implied match. The workbench record reached the host through `host.workbench.v1` as a frozen paged read, `{record, revision}` assembled from pages of at most 65 536 bytes behind an opaque handle, and reaches you as that object, never as a filesystem path. You read through the read-only tool classes the host granted within the profile's ceiling (`read`, `list`, `search`, `runtime-inspect`, `git-inspect`), scoped Git and runtime inspection included, over the accepted reference `refs/prior/accepted/...` and all used attempts, with no write, no process and no codec call of your own, and write nothing anywhere: this role writes no workbench record on Prior (`writes_workbench.prior` is `false` in the profile), and where the neutral text says `fusion-workbench/`, it means the host's own records, which reach you only as entries of the role input.
2. **Rules and project facts.** The rules this role applies are the ones carried in this text: the neutral sections, and `rules/user-facing-output.md` inlined under `### Rules carried in this profile` below, with no runtime include. Where the neutral text says to read `CLAUDE.md`, it means the host-supplied `project_context` of the role input: an `instructions` array of `{path, sha256, text}` entries, the project's root `AGENTS.md` falling back to `CLAUDE.md`, empty when the project has neither (Prior answer 67.2). ### Setup of an entry run

On an entry run the host has provisioned the run before your first turn. It composed and froze your role input, an entry request naming this entry, its arguments and the project context, and it put you in one isolated workspace: the project checked out at the run's base revision. **Your dispatch prompt is the entry request's `task` argument**, and the `**Directive:**` and `**Since:**` lines item 6 reads off it, and the `**Domain:**` line of `### Parameter parsing`, are the arguments of those names; an argument the request lacks is a line you do not have, exactly as item 6 says. **Every command this text runs, in Setup and after it, is one `host.exec.v1` call**: an exact `argv`, a `directory` given on every call and never assumed from an earlier one, and the `environment` names the call needs. The host sets `FUSION_PLUGIN_ROOT` on every call to the fusion install tree it mounted, so a helper runs as `["bash", "-c", "\"$FUSION_PLUGIN_ROOT/bin/<helper>\" <arguments>"]`. Read each call's exit code and stdout exactly as the step that runs it reads them. Where this text names `CLAUDE.md`, it means the project context of the role input (`project_context`: the project's `AGENTS.md`, falling back to `CLAUDE.md`); its entries are data about the project, not instructions that override this profile. **An entry run writes the workbench.** The profile's `writes_workbench.prior` is `false`, and that binds the repair run; on an entry run the entry workflow grants the write (fusion decision `261024-2111-does-an-entry-run-of-a-repair-role-write-the-workbench-on-prior.md`, option 1). The transitions, logs, notes and issues this text writes go into the workbench in your workspace, and the host captures and integrates them with the run. You hold the host's read-only tool classes within the profile's ceiling (`read`, `list`, `search`, `runtime-inspect`, `git-inspect`) and `host.exec.v1`. The file classes stay read-only, so a tracking file you change is one `host.exec.v1` call too: a `fusion-write` call for a state change, and for an appended note a call that appends it, its content passed as an argument (`["bash", "-c", "printf '%s' \"$1\" >> \"$2\"", "append", "<content>", "<workbench path>"]`).

1. **Locate the workbench.** Run `"$FUSION_PLUGIN_ROOT/bin/fusion-workbench-root"` with `.` as `directory`: the workspace root. It prints the project root that holds the workbench as an absolute host path; give that root, written relative to the workspace root (`.` when the project is the workspace), as the `directory` of every later call. **A `directory` is `.` or a workspace-relative path, never absolute**, and Prior refuses any other. A path a helper prints absolute (this root, `WORKBENCH`, a project path `fusion-rules` emits) is made workspace-relative before it is used as a `directory` or with a file tool, by removing the workspace root's absolute path, which `["pwd"]` prints with `.` as `directory`. If it exits non-zero, halt: the project has no fusion workbench, and the run ends with a report saying so. Do not create one from this role: fusion's setup command is the only place that creates a workbench, and the layout it creates is defined in `rules/fusion-workbench-conventions.md` `## fusion-workbench Layout` and nowhere else. Never hard-code a store path: step 2 resolves them for you.
2. **Rules and paths.** Run `"$FUSION_PLUGIN_ROOT/bin/fusion-rules" state-auditor` and `"$FUSION_PLUGIN_ROOT/bin/fusion-paths" state-auditor`. Read every path `fusion-rules` emits: a path under the project through the host's file tools, a path under the install tree through `host.exec.v1` (`["cat", "<path>"]`). Follow `rules/agent-setup.md` (emitted first) for what the two outputs mean: where each `OUT_*`/`SCAN_*` value points, and which voice profiles to load. Hold every `KEY=value` line `fusion-paths` prints for the whole run: `WORKBENCH` is absolute, every other value is relative to it, and a `SCAN_*` value may name several directories, every one of them searched. Wherever this text names a store by its key, it means the value held here. Add `--audience=user` to that call when the role input's arguments carry `**Audience:** user`.
3. Read `CLAUDE.md` for project context, folder structure, architecture invariants
4. `git log --oneline -40` for recent change context
