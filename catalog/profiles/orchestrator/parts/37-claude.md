3. **Write the commit message to a file — the shell never sees the message.** Use the `Write` tool (not `echo`, not a heredoc, not a `-m` flag) to write the full message to `~/.fusion-tmp/<checkout-id>/fusion-commit-msg-<session-id>-<task-id>.txt`, in the directory `"$FUSION_PLUGIN_ROOT/bin/fusion-tmp" path` prints: resolve it once per session (stop if it fails) and give `Write` and `-F` the absolute path. The message is prose, so it will contain apostrophes and may contain backticks, `$` and quotes; each changes what a shell parses if the message reaches a command line. `Write` keeps the shell out of the message path, so no character in it can be special.
   - **`<session-id>` is what makes the path yours, and it is not decoration.** The directory is per checkout, but two sessions in one checkout share it, and task ids are short and conventional (`T1`, `REC`, `CLOSE`), so they write one file whenever their ids agree — and macOS folds case, so `L1-RECONCILE` and `L1-reconcile` are one file. Measured while the path was machine-global: this file was overwritten by another project's message mid-session; reversed, `git commit` exits 0 on the wrong message (`260905-2213_*_two-concurrent-sessions-share-one-tmp-commit-message-path-so-one-can-commit-the-others-message.md`). The commit lock does not cover it: `Write` runs before the lock is held. Use the session identifier because it is the one discriminator you already hold **as a literal** when you call `Write`, which expands no variable — SessionStart put it in front of you as `fusion: session_id=<id>`. If that line never appeared, use the `CHECKOUT=` value from `bin/fusion-identity` in its place and say so: two sessions on one checkout then share the file.
   - **The directory is the one `fusion-tmp path` prints, and that half is enforced too.** It survives a reboot and `git clean -xdf`, and is outside every tree `git status` reports on; `fusion-workbench/` is the tree `git status` reports on (`rules/fusion-workbench-conventions.md` `## Intermediate files`). A message file written inside the workbench becomes a leftover on the next `git status` and — if a staging list ever names a directory — content in a commit. Measured: `fusion-workbench/.commit-msg-tmp`, holding the message of `d169b0d`, at a path no helper names. `hooks/lib/staging-drift.ts` reads a commit-message-shaped file under the workbench as a fault of its own class — scoped to what no artefact store owns, so an authored record whose topic slug says "commit message" stays a `record` — and names this path back to you (see **Staging check**), and `commit-message-path.test.ts` fails `npm test` if this line stops naming that directory, if the path loses its per-session discriminator, or if the two spellings drift apart.
   ```
   <type>(<scope>): <summary>

   Task: <task ID>
   Source: <path to source plan/issue file — omit the line when the task came from no record>

   Co-Authored-By: Claude <noreply@anthropic.com>
   ```
   - `<type>`: `fix`, `feat`, `refactor`, `docs`, `chore`, `test` — conventional commits
   - `<scope>`: affected package or area (e.g., `ai`, `ontology`, `ui`, `pptx`)
   - **This message is the record of what the commit did.** `rules/fusion-workbench-conventions.md` `## Record filing` puts a record file behind five conditions, and a task that meets none of them commits with no record file and no `Source:` line. Do not manufacture one to fill the field, and do not hold a commit back for a record nobody is owed. Write the body so a later reader needs nothing else.
   - Always create a new commit. Never amend.
   - **Why this is a rule and not a preference.** The measured defect is in `rules/commit-lock.md` `## Two measured defects behind this procedure`.
4. **Assemble the staging list — every path written out in full.** Step 5 stages exactly the paths you name here, and the rule is a **shape**, not a list of banned flags: *every path passed to `git add` is one you wrote out yourself.* No `-A`, no `-u`, no directory argument, no glob, no `.`, and no list a command produced: a `$(git status …)` substitution is a glob with more steps, and it once staged a renamed record's deletion without its successor (`7ae6aae`). Stated that way you can check your own command before you run it, which "be explicit" is not. The list is the task-relevant files plus the `fusion-workbench/` tracking updates this task produced, and nothing else.
   - **Write every path out absolute, because step 5 does not run where you are.** `fusion-commit-lock with` `cd`s first, so a relative list stages nothing; the commit-lock rule says where, and what that costs (`bin/fusion-commit-lock`, the `with` branch). **A pathspec failure is not repaired with a directory argument or `-A`.**
   - **A pair is two paths, and so is a move.** A filing writes a narrative and its control file, and a `transition` rewrites the control file beside a narrative that may have gained a line: stage both halves in one commit, never one alone. A moved file is its old name *and* its new one, `git add <old> <new>`.
   - **Why the shape and not just a ban on `-A`.** The measured defect is in `rules/commit-lock.md` `## Two measured defects behind this procedure`.
5. **Empty the index, then stage and commit, as one held command.** Anything staged that your list does not name was staged by a child run earlier in the session, and `git commit` would carry it under this task's message. So the held command begins with `git reset -q`, which unstages everything and touches no working-tree file, before `git add` stages exactly your list; a sibling's path is re-staged by them later and committed under a message about it. Read `git diff --cached --name-only` before the lock only to **name** those paths to the user: the read is advisory, and every index write sits inside the lock, which is the one thing `rules/commit-lock.md` exists for. Whether a child run may stage at all is fusion's own record `260824-2013_*_how-is-a-marker-rename-performed-and-staged-and-by-whom.md`.
   ```bash
   "$FUSION_PLUGIN_ROOT/bin/fusion-commit-lock" with orchestrator -- bash -c 'git reset -q && git add <absolute-path> <absolute-path> && git commit -F ~/.fusion-tmp/<checkout-id>/fusion-commit-msg-<session-id>-<task-id>.txt'
   ```
   Staging and committing sit inside **one** acquisition because `git commit` commits the whole index: a path staged outside the lock is unprotected until the commit lands, and any parallel committer holding the lock in that window absorbs it into its own commit. That race is what the lock exists for — see `rules/commit-lock.md` `## Commit lock` for the protocol and for the closed defect it answers.

   **Which lock form.** Use `with`, which releases on every exit path; use the explicit `acquire` / `release` pair only when the held region contains internal control-flow `with` cannot express (`rules/commit-lock.md`). `add && commit` has none, and the healing retry at step 2 finishes before step 5 acquires anything.

   **Before you send it, check that no path in your staging list contains a `'`.** The `bash -c` string is single-quoted, and it holds only paths and flags because step 3 put the message in a file. fusion's own filenames never contain one; a path that did is an approval matter, not something to quote your way around.
5a. **Pull with rebase, read the campaign, push.** After the commit, run `[ -x "$FUSION_PLUGIN_ROOT/bin/fusion-campaign" ] && "$FUSION_PLUGIN_ROOT/bin/fusion-campaign" sync` and read its lines, not an exit code. `paused=`: dispatch nothing more, report the campaign's reason to the user, leave the package claimed. `state=conflict` or `state=rejected`: report git's words to the user, who resolves it; nothing is forced. `state=fetch-failed` (exit 6: offline, or a credential prompt) and an empty stdout with exit 4 (the workbench at the fetched head was not read) or exit 1 (the helper itself could not run), the cause on stderr each time: nothing rebased or pushed; name the cause to the user and go on. `state=no-work-tree`, `no-branch`, `no-upstream`, `upstream-unresolved`, `workbench-untracked` (exit 5) and `workbench-outside-repo` (exit 7): no ref to rebase onto; say so once and go on. An older install without the helper skips this sub-step, and you say so. **A hash written into a record, a closure note or event row is the one a `pushed=` line names for it, found by subject, never what `git commit` printed**; with no line yet, the write waits for the cycle that prints it. That wait is the rule for the four cases a later cycle can still rebase (`conflict`, `rejected`, `fetch-failed`, an empty stdout), and it ends with the session: a closure note the session must write while one of them stands takes git's hash and names the state beside it, so a reader knows the hash may yet be rewritten. With no helper, or on a state of exit 5 or 7, nothing rebases in this checkout and git's hash stands as before, the record naming the state.

   **In a campaign lane** (a `lane=` row, which names this checkout) `next=` and `question=` decide what follows. Row shapes: the helper's header, `## Output of sync`. Once the held package is finished: `next=` autonomous with waits `none` → claim it, `gate_hit` and `gate_response` `proceed — answered by **Mode:** autonomous on <next>`, and go on with no Step 5 question; `next=` ordinary → file "may I take `<next>`?" in `<next>`'s container as **Human approval rules** routes a lane question, and claim nothing; `next=none`, or a `next` still waiting → report once that the lane is finished, or what it waits for, and stop. A `question=` row of this checkout whose answer is not `none`: pull it first (after a `sync --read`, run `sync`), append `Answered: <answer basename> — <option>; ruled by user, <the answer's person>` to the question and `transition --to answered --answer-ref` it, emit `gate_response` `<option> — answered by <answer basename>`, and resume what its `**Set aside:**` line names.
6. The `commit` event is machine-written by `fusion-commit-lock with` (`rules/commit-lock.md` `## The lock writes the commit event`) — emit none yourself.
7. **Run the staging check** (see **Staging check**) in the same command as your read of `git diff --cached --name-only`, and name any `record` row it reports to the user. Nothing else records what this session authored but did not commit, and a record left in the working tree is a record the next `git clean` takes.
