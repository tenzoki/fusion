## Setup

On Prior the host has provisioned the run before your first turn. It composed and froze your role input, an entry request naming this entry, its arguments and the project context, and it put you in one isolated workspace: a copy of the user's checkout as it stood when the run started, `HEAD` detached at the commit the user's `HEAD` named and every file of the working tree carried byte for byte. That includes the user's uncommitted changes, the untracked and ignored files and the workbench's per-checkout files; `fusion-workbench/.checkout-id` is read-only. **Every command this text runs, in Setup and after it, is one `host.exec.v1` call**: an exact `argv`, a `directory` given on every call and never assumed from an earlier one, and the `environment` names the call needs. The host sets `FUSION_PLUGIN_ROOT` on every call to the fusion install tree it mounted, so a helper runs as `["bash", "-c", "\"$FUSION_PLUGIN_ROOT/bin/<helper>\" <arguments>"]`, and a shell block below runs as its text in the same `bash -c` form. Read each call's exit code and stdout exactly as the step that runs it reads them. Prior guarantees the presence of the commands fusion's text uses, by the list in request 78, question 2, and not their behaviour; once its check ships, it refuses a missing one by name at run start. A `command not found` met anyway, from a block or a helper and at whatever exit, is a host gap: report the command it names, and never repair the gap. Where a rule says `date +%y%m%d-%H%M`, use `["bash", "-c", "printf '%(%y%m%d-%H%M)T\\n' -1"]`. **Where this text dispatches or invokes an agent, it is one `host.dispatch.v1` call**: `entry` the agent's bare entry id, `description` one short line naming the task, and `input` the child's arguments as a JSON object written as a string, `{"arguments": [{"name": "<declared argument name>", "value": "..."}, …]}`. Each item is one argument the child entry declares in `catalog.json`, named exactly as declared, in the order the dispatch text gives them: a parameter line is the item named by its label, such as `**Audience:**`, with the text after the label as its `value`, and the dispatch text without its parameter lines is the item of the child's first-message argument, such as `task` or `request`. An argument the child entry does not declare is never sent, and Prior refuses an `input` that does not decode to an object. The host composes the rest of the child's entry request. Prior takes this shape (request 76, question 13). The call returns when the child run ends, and what it returns is the child's report.

**STEP 0 — IMMEDIATE: Locate the workspace.**

Run `"$FUSION_PLUGIN_ROOT/bin/fusion-workbench-root"` with `.` as `directory`: the workspace root. It prints the project root that holds the workbench as an absolute host path; give that root, written relative to the workspace root (`.` when the project is the workspace), as the `directory` of every later call. **A `directory` is `.` or a workspace-relative path, never absolute**, and Prior refuses any other. A path a helper prints absolute (this root, `WORKBENCH`, a project path `fusion-rules` emits) is made workspace-relative before it is used as a `directory` or with a file tool, by removing the workspace root's absolute path, which `["bash", "-c", "pwd"]` prints with `.` as `directory`. If it exits non-zero, halt: the project has no fusion workbench, and the run ends with a report saying so. Do NOT bootstrap a workbench from this role. Fusion's setup command is the only place that creates one, and it pre-creates the whole layout, which is defined in `rules/fusion-workbench-conventions.md` `## fusion-workbench Layout`. You never need to name a store directory yourself, because Step 2 below resolves every path you write to or search.

**No session state file and no dashboard file are written, here or anywhere below.** Do not write `fusion-workbench/agentstate.yaml`, do not write `fusion-workbench/orchestrator-live.md`, and do not re-create either under another name. A run that was interrupted is restarted like any other, and what it left behind is in the event log and in the records it wrote.

**STEP 0b — No monitor on Prior.** The dashboard binary is not copied and no monitor is started: the host's own view of the run is the live surface. Go on to step 1.

**STEP 1 — Secure the brief before the expensive steps** (fusion's own record `260827-1330_*_does-the-session-ask-for-its-directive-first-and-wait-silently.md`). The brief is the entry's first message, the `brief` argument of the role input. Two cases, disjoint and complete: it carries work ("fix X", "work the item I claimed", a pasted task) → hold it as the brief candidate, ask nothing, continue. It carries none (absent, or a bare opening) → ask now, one question in chat: what to work on, with "just set up, I'll bring the brief later" as an explicit option. "Setup only" is a complete answer, not a failure; it defers the ceremony in step 6 below.

     The two file counts are **not** yours to improvise. Run the helper once, from the project root, in its guarded form:

     ```bash
     if [ -x "$FUSION_PLUGIN_ROOT/bin/fusion-count-sources" ]; then
       "$FUSION_PLUGIN_ROOT/bin/fusion-count-sources"
     else
       printf 'code_files=unavailable\ndata_files=unavailable\ncounted_by=none\n'
       echo "fusion: no bin/fusion-count-sources in the installed plugin at $FUSION_PLUGIN_ROOT — no source count taken" >&2
     fi
     ```

     It prints `code_files=`, `data_files=` and `counted_by=`, one `KEY=value` per line. It counts with `git ls-files`, so it sees the whole source tree at any depth and needs no exclusion list. Exit 2 with `counted_by=none` means **no count was taken** and both values read `unavailable`; the helper's own header names the two causes that reach it (the project is not in a git work tree, or the count was attempted and could not be completed).
