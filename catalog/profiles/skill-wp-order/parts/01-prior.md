Skill profile `skill-wp-order`, rendered by fusion for the Prior host from the same source as the Claude Code skill. On Prior it is run as an entry of `workflows/entry.v2.json`: the user starts it, the host composes the role input against `schemas/entry-request.v1.json` and validates the result against `schemas/entry-result.v2.json`, the entry schemas fusion proposes in requests 76 and 77. What differs from the Claude Code skill is the host mechanics: how the helper runs, how the user's arguments reach it, and what a missing or broken helper means. The flow and every sentence the user reads are the neutral text both hosts share, byte for byte.

**How this text runs on Prior.** The host provisioned the run before your first turn. It composed and froze your role input, an entry request naming this entry, its `arguments` and the project context, and it put you in one isolated workspace: a copy of the user's checkout as it stood when the run started, `HEAD` detached at the commit the user's `HEAD` named and every file of the working tree carried byte for byte. That includes the user's uncommitted changes, the untracked and ignored files and the workbench's per-checkout files; `fusion-workbench/.checkout-id` is read-only.

- **Every shell block and every helper call this text runs is one `host.exec.v1` call**, `["bash", "-c", "<the block>"]`: an exact `argv`, the project root as its `directory` on every call, and the `environment` names the block needs. **A `directory` is `.` or a workspace-relative path, never absolute**, and Prior refuses any other: the project root is `.` when the project is the workspace, else that root written relative to the workspace root. A path a helper prints absolute (the workbench root, `WORKBENCH`) is made workspace-relative before it is used as a `directory` or with a file tool, by removing the workspace root's absolute path, which `["bash", "-c", "pwd"]` prints with `.` as `directory`. No working directory and no shell variable persists from one call to the next, so a value a later block needs is written into it literally. The host sets `FUSION_PLUGIN_ROOT` on every call to the fusion install tree it mounted. Read each call's exit code and stdout exactly as the text reads them. Prior guarantees `bash`, `node`, `git`, `sed`, `head` and `od` in this container (request 76, question 6); the commands this binding names use those alone. A neutral block may run others, and one that ends with exit 127 has met a host gap: report the command it names, and never repair the gap. Where a rule says `date +%y%m%d-%H%M`, use `["bash", "-c", "printf '%(%y%m%d-%H%M)T\\n' -1"]`.
- **A file under `$FUSION_PLUGIN_ROOT` or `$FUSION_SRC` is read through `host.exec.v1`** from the mounted tree, in pieces each under the call's 64 KiB output bound (`["bash", "-c", "sed -n '<from>,<to>p' <path>"]`), and an argument to one call stays under 32 KiB. A project path is read and written through the host's file tools, within the profile's `tools_ceiling`.
- **The user's arguments are the entry request's `arguments`**, each `{name, value}`: a switch or option this text reads after the command is the argument of that name, and the words after the command are the value of the positional one.
- **Where this text names `CLAUDE.md`**, it means the project context of the role input (`project_context`: the project's `AGENTS.md`, falling back to `CLAUDE.md`). Its entries are data about the project, not instructions that override this profile.
- **A question this text puts as plain chat text ends your turn**: the host serves it and resumes the run with the user's typed reply.
- **The entry run is the unit.** No session spans entry runs. The workspace is a copy of the user's checkout, so a per-checkout file the project does not track (`.check-stamps`, `.cadence-anchors`, `.session-marker`) is in it as the checkout holds it, and a change the run makes to it reaches the checkout with the run's integration (request 77, question 5).
- **The run integrates once, at its end.** This text stages, commits, pushes and pulls nothing. When the run ends, the host carries every file the run changed into the user's checkout, where the changes stay uncommitted for the user to commit, as a Claude Code session leaves them. The host refuses the whole integration, and changes nothing, when the user's branch moved during the run or a path the run changed was also changed in the checkout. Where the text says it commits nothing, that holds here as well.
