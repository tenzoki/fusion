# Project Language — the full cascade

**Provenance:** Partitioned out of `rules/fusion-workbench-conventions.md` `## Project language` per decision `shared/decisions/260827-1056_*_which-parts-of-the-language-and-backlog-rules-does-every-dispatch-still-carry.md`; the section's own history is that file's.

The operative core — the two declaration lines, the fallback chain, the four-surface assignment, and the exempt groups — stays always-on at `rules/fusion-workbench-conventions.md` `## Project language`, and this file does not restate it. This is the reasoning and the edge semantics behind that core, emitted to the `editor` (the one agent with a behavioural branch here: its deliverable-language halt); everyone else reaches it by the core's pointer.

**The two persisted cases are cut by who the file is for, and that keeps the split disjoint.** A deliverable persists, so under the earlier three-way split it fell into the artifact-language case by silence — and wrongly: the artifact language exists for the project's internal record-keeping, while a deliverable's language follows its reader, and the two have no reason to agree. Every persisted file is in exactly one of the two cases; the deliverable is the only output whose reader is outside the project.

**Why the deliverable's source is the dispatch and not a third declaration.** A deliverable's language is not a per-project constant: the same consultancy writes for a German client one week and an English one the next, so any project-wide default is wrong a large share of the time, and what it produces is a *finished* document in the wrong language, found by the customer rather than by a stop. So the obligation sits on the dispatch, per deliverable, and the failure is loud by design: `agents/editor.md` `## Deliverable language` halts and names what to pass (decision `260807-2131_*_which-language-governs-a-customer-deliverable.md`, option 3). A single-declaration project is unchanged in every other case and is **not** exempt from this one: its declaration says nothing about a reader outside the project.

**The stylometric profiles follow from the boundary rather than defining it.** Each family governs one surface and resolves from that surface's language: `chat-voice-<lang>.yaml` from the chat language, applied by every agent to short-form user-facing output; `default-voice-<lang>.yaml` from the artifact language, applied by the long-form-prose agents to narrative outputs. It follows that **a customer deliverable's prose takes the writing profile of the language the dispatch named** — `default-voice-de.yaml` for a German deliverable in an `en`-artifact project, the target language's profile on a translation. Not an exception: each family resolves from the language of the surface it governs, and for one surface that language comes from the dispatch.

`bin/fusion-rules` emits the chat profile path for every agent and the writing profile path only for the long-form-prose agents; the two paths naming different languages is the intended configuration for a project whose declarations differ. Each family keeps its **own** missing-variant fallback: when the resolved language's variant is missing, `bin/fusion-rules` falls back to that same family's `-en.yaml`, names the fallback on stderr (family, requested, resolved), and an agent that keeps a session history records that line once. If neither variant of a family exists, the agent emits nothing for that family and follows `rules/user-facing-output.md` alone.

**The universal exempt group's worked case.** `hooks/session-start.ts` `## Why the message is English`: a hook fires before any agent has read `CLAUDE.md`, and localising one of fusion's operator strings while the rest stay English is the inconsistency, not the fix. The count that once stood in that sentence is deliberately not restated — the set has shrunk repeatedly, so a number written into prose about it is stale before it is committed.

**The conditional exempt group divides fusion's own repository rather than exempting it whole.** It is the source of the shipped rule text and at the same time a `de` project with its own workbench: the rule files, agent prompts, skill bodies, `README.md` and `docs/` it ships are English, while its workbench artifacts reach nobody outside it and follow its declarations like any other project's. Universalising the first half — offering "these ship" as the reason a project that ships nothing must write its own README in English — was the defect this replaced (`shared/decisions/260807-1515_*_wie-weit-reicht-die-projektsprache-in-den-regelkorpus.md`, third constraint).

**Persisted-but-profile-exempt surfaces still take the artifact language.** Dashboard lines, commit messages and monitor strings are exempt from both stylometric profiles (their terse, parseable shape), but exemption from a style profile is not exemption from the language rule: they persist, so they take the artifact language. **Settled by user decision rather than derived** — the dashboard is the one surface where "persists" and "direct user interaction" genuinely overlap, and the user chose the persisted reading, commit messages falling with it. Not an oversight, not to be reopened as one.

**Head labels follow the file that defines them.** A label defined in a shipped template (`**Decidability:**`, `**Domain:**`) is English in every project, because the template lives in an exempt file; the artifact *body* under it follows the artifact language. That is what makes `**Decidability:**` the plan-head label everywhere, with no per-language variant.

**Existing artifacts are not translated.** The boundary applies going forward, like the filename patterns; older prose in another language is not evidence against the rule.
