# Which Workbench Entries a Tracked Workbench Tracks

**Provenance:** `260816-0711_*_where-does-the-tracked-workbench-split-live-now-that-the-home-it-was-meant-to-move-to-is-gone.md` (the move that gave this text its own home); `260816-1707_*_to-whom-is-the-new-workbench-tracking-rule-emitted-when-its-consumers-are-a-human-and-a-skill.md` (the emission target that move was blocked on); `260822-1136_*_spec-fusion-becomes-a-multi-user-tool.md` `## The state partition` (the four-class partition that replaced the two-group split, and the reclassification of `portfolio.md` it carries).

**This document is the definition** of what each workbench entry does when a project tracks its workbench: which entries git carries between checkouts, which never leave the checkout they were written in, and what preserves the evidence in the ones git does not carry. It was partitioned out of `rules/fusion-workbench-conventions.md` `## fusion-workbench Layout`, whose tree it ranges over; no other file may carry a competing or supplementary definition.

`bin/fusion-rules` emits it to **no agent**, because no executor agent applies it. Its consumers are a human writing a consuming project's `.gitignore`, who reads a file rather than receiving an emission, and the archive step of `/fusion:cleanup`, which cites this file in its own body (`skills/archive/SKILL.md`).

## Whether to track the workbench at all

fusion ships no `.gitignore` rule for `fusion-workbench/`, so a consuming project's workbench may be tracked, ignored, or neither. One person working in one checkout loses little by ignoring it: the artifacts are on their disk either way.

**A multi-checkout arrangement is different. It requires the project to track its workbench**, and the reason is that git is the only transport there is. Two people working one project work in two clones, and two clones share exactly what git carries between them: no common parent directory, no shared filesystem, no server, nothing a fusion process reaches across. An untracked workbench therefore gives each checkout a private one that nobody else can read, and the Circle records, decisions, issues and plans the whole method is written in stop being a shared surface and become per-machine notes. Everything below is about a workbench that is tracked; for one that is not, only the classification survives, and none of the transport reasoning applies.

## The four classes

The partition ranges over **every entry of the layout tree** in `rules/fusion-workbench-conventions.md` `## fusion-workbench Layout`, which that document states is exhaustive as written, together with the two frozen stores named in the paragraph beneath the tree. **Every entry falls in exactly one class, and no entry falls in none.** That tiling is the property to check whenever the layout gains an entry: a new root-anchored surface joins one of these four classes in the same commit that creates it, in the layout tree and here.

| Class | Entries | What it means under several checkouts |
|---|---|---|
| **R1. Travels. Many files, one writer each.** | `circles/` with every store inside it, `shared/` with every store inside it, `archive/`, `stilwerk/`, and where a workbench still holds them the two frozen stores `stashes/` and `.migration-v2-backup/` | Track them. Two people collide only on one file at a time. A record filename carries a minute stamp and a slug, so two new records collide by accident almost never. Two people editing the *same* existing record is the real case, and the Circle record is the instance of it that matters. |
| **R2. Travels. One file, appended by many.** | `orchestrator-events.jsonl` | Track it. It is the only file in the whole workbench that two checkouts both write and that git must therefore merge, which is why it has a merge driver of its own (below). |
| **R3. Travels. Written once, or rewritten per item.** | `.fusion-setup`, `.asset-provenance` | Track them. Both are written by `/fusion:setup` in each checkout, and both tolerate a second writer: a second setup writes the same lines about the same assets, and the marker is rewritten with the same content per plugin version, carrying no path and no timestamp of its own (`## The setup marker is written on change, not on every run`). |
| **L. Stays in the checkout. Never travels.** | `agentstate.yaml`, `orchestrator-live.md`, `.session-marker`, `.active-circle`, `.checkout-id`, `.cadence-anchors`, `.commit-lock/`, `monitor`, `portfolio.md`, and `.guard-state/` in full, its event log included | Do not track them. Each is per checkout by construction, and that is what makes two sessions in two checkouts independent with no lock between them. |

**Why each class L entry is in class L**, since "do not track" is the half a reader is most likely to get wrong. `agentstate.yaml`, `orchestrator-live.md`, `.session-marker`, `.active-circle` and `.commit-lock/` describe *now*: each is overwritten or removed as a session runs, so a committed version is noise in every diff and, restored by a checkout, a statement about a session that has ended. `.checkout-id` is class L for the opposite reason to the rest: not because a past version answers nothing, but because it answers *which checkout*, and a checkout that pulled another's copy would carry that other one's identifier. Tracking it would defeat the one collision the identifier exists to prevent, so it is the single class L entry whose classification is load-bearing rather than merely tidy. `.cadence-anchors` (v10.8.1, `bin/fusion-cadence-anchor`) holds the high-water marks this checkout's cleanup passes measure their delta from; a pulled mark would claim coverage this checkout never performed, which is the false "already done" the file must never produce. `monitor` is a verbatim copy of the shipped `bin/monitor` that `/fusion:setup` re-creates. `portfolio.md` is regenerated in full on every playmaker run (`agents/playmaker.md`), so a committed copy is a briefing about what one checkout had pulled at the moment it ran; merging two of them settles nothing the next run does not overwrite, and the run is cheap.

**Why the three R classes are tracked** is the common property that a past version of them answers a question somebody still asks. Losing `.asset-provenance` is not neutral: every asset it covered falls back to "fusion cannot tell an adaptation from a stale copy", which is exactly the state the record was written to leave. Ignoring `.fusion-setup` is not free either: it is the marker every agent and hook walks up to find, so a clone without it halts every agent at Setup and silences every hook, set up in appearance and inert in fact.

**`.guard-state/` is not one thing, and the directory is the wrong unit to classify by.** Each file in it is asked separately, and every answer comes back class L — for reasons that differ, which is why the question is worth asking per file at all. What is written at this version is the measurement throttle records `review-coverage.json` and `staging-drift.json`, joined in v10.8.1 by `dispatch-map.json` (the launch-time pairing the SubagentStop hook resolves), and `events.jsonl`. The throttle records and the dispatch map are each rewritten in place and a past version of them answers nothing, so they are class L. A workbench set up under an older fusion may hold inert leftovers beside them, each written by nothing at this version because the commit named retired its writer: `escalation.json` (2026-08-16, `9c79202`; `hooks/lib/guard-state-file.ts`), `churn.json` (`a69d56e`) and `state-drift.json` (`f45f76a`). Nothing reads them, and `/fusion:setup` offers to delete all three in one question (`skills/setup/SKILL.md`, the leftover probe; commit `abb0238`). `events.jsonl` is appended to and never rewritten, and a past version answers a great deal: which tool call the guard blocked, when it halted, when a human cleared the halt. No new row of those three kinds can arrive now that the guard decides nothing, which is a reason to keep the ones already written rather than to reclassify the log. It is classified by what it is rather than by the directory it sits in, and what it is, is **class L**: the live file stays in the checkout that wrote it, like every other entry of that directory. What a past version of it answers is preserved by a mechanism instead of by tracking, and that mechanism is the next paragraph (decision `260811-1534_*_does-the-guard-event-log-get-an-upper-bound-and-what-happens-to-the-evidence-in-it.md`).

**What preserves that evidence is the archive step of `/fusion:cleanup`, not a ceiling and not tracking the live file.** The log has no line or byte limit anywhere, deliberately: every such limit discards the oldest lines first, and the oldest lines are the block, halt and clear events, which are the only ones recording the guard enforcing anything. That step, the whole pipeline or `/fusion:cleanup --only archive` alone, rolls the live log into the archive store under a dated name and starts a fresh empty one. The rolled copies are ordinary archived files and travel in class R1 like every other one. A project therefore holds the evidence in git while paying no diff on every tool call. The live log and its rolled copies sit under two different entries of the layout tree: `.guard-state/`, which is class L, and `archive/`, which is class R1. The roll moves bytes from one entry to the other rather than splitting one entry across two classes, so each entry still falls in exactly one class and the partition owes no exception here. That is the configuration this repository runs.

## The event log carries a union merge driver

`fusion-workbench/orchestrator-events.jsonl` is the whole of class R2. Every session in every checkout appends to it and nothing rewrites it, so two checkouts that both ran a session hold two files differing by added lines in the same region at the end. Git's default text merge calls that a conflict and stops, in a file no person should be resolving by hand. The rule that prevents it is one line, in the project's root `.gitattributes`:

```
# fusion: the orchestrator event log is append-only and two checkouts both append to it.
fusion-workbench/orchestrator-events.jsonl merge=union
```

`union` is one of git's built-in merge drivers, so it needs no `.git/config` entry and nothing is configured per machine: a tracked `.gitattributes` is sufficient on its own. The record that chose it is `260822-1136_*_how-does-the-tracked-event-log-behave-when-two-checkouts-both-appended-to-it.md`.

**The question a mechanism asks about that rule is `git check-attr merge -- fusion-workbench/orchestrator-events.jsonl`, and never a text search of `.gitattributes`.** The two are different questions. `check-attr` returns git's own resolved value for that path, so it sees a broader glob such as `*.jsonl merge=union`, a nested attributes file in a subdirectory, an attribute macro, and an entry in the repository's `info/attributes`. A text search asks only whether one literal line stands in one file, which is false in every one of those cases while the driver is in force, and a mechanism acting on that false answer writes a duplicate rule into a project that already had what it was about to add. Two further properties make the resolved question askable where a fusion run needs to ask it: `check-attr` answers for a path that does not exist yet, so a fresh workbench whose event log has not been created is not a special case, and it resolves the path relative to the working directory, which is the anchor the workbench itself uses.

**`/fusion:setup` asks that question on every run and branches three ways.** The branches are disjoint and exhaustive because `check-attr` returns exactly one value for `merge` on that path, and these partition the value space:

- **`union`**: write nothing. The project already has what the rule asks for, and a broader rule it wrote itself may be what set it.
- **`unspecified`**: no driver applies. Ensure the file ends in a newline, then append the comment and the rule line above. This is the only branch that writes.
- **any other value**: leave the file alone and say in the report what was found. Three kinds of value reach this branch and only one of them is a driver name. `set` is a bare `merge` with no value, and it selects git's **default text merge** — exactly the conflicting behaviour this rule exists to prevent; Setup names it as that rather than as a driver, and still writes nothing, because a project that wrote the line chose it. `unset` is `-merge`, which switches merging off for the path altogether. Anything else is the name of a driver the project picked. All three are deliberate statements about this path, and Setup is not the party to overrule any of them.

Outside a git work tree there is nothing to ask and nothing is written. Setup reports which outcome occurred in every case, and on the writing branch it reports the path it wrote. The write lands at the project root, in the directory Setup ran in and never in a subfolder and never inside `fusion-workbench/`, and it asks the user nothing.

**What a union merge costs, and who pays it.** The merged file holds every line from both sides and loses none, which is the whole point. It is no longer in chronological order, though: one side's block follows the other's rather than interleaving by time. Any reader that walks the log positionally instead of reading each line's `ts` field therefore reads a false order, and the repair belongs to the reader rather than to the file. That is why the Phase-4 sequence diagram sorts by `ts` before it builds anything. Since this Circle the repair has a shape and not only an owner: every emitted line carries the checkout that wrote it, and a reader scopes the log by that field before it sorts by `ts`. The order of those two operations is the whole of the repair, because sorting an unscoped log interleaves two checkouts' sessions into one plausible false sequence, which is worse than the positional reading it replaces in that it looks repaired. How a line comes by that identity is not this file's contract: it is authored in `agents/orchestrator.md` `### 2. Structured Event Log` (commit `8655ec2`) and is cited here rather than restated.

**A line carrying no checkout identifier reads as the reading checkout's own.** That rule is what keeps every line written before this Circle legible, and what makes a reader that cannot resolve its own identifier behave exactly as it did before the field existed. Its cost is real and is stated here rather than softened: another checkout's pre-C4 lines that have already merged into this one read as this checkout's, and nothing later corrects them. The alternative was to treat an absent field as foreign, which would have emptied every surface that reads this log until the first session written under the new contract, and the user took the wrong attribution of the old lines over a monitor that shows nothing.

**Four readers apply that scoping, and three of the four drop what the fourth keeps.** `bin/fusion-events turns`, `bin/monitor` and the post-session sequence diagram at `agents/orchestrator.md` `### 3. Post-Session Sequence Diagram`, generated at Phase 4, drop every line another checkout wrote, because each answers a question about this checkout's own session and a foreign line in that answer is the defect. `bin/fusion-events presence` keeps them, because presence is the one question whose answer lives in the lines this checkout did not write. The asymmetry is the design and not an oversight: one field serves both readings, and which side of it a reader keeps follows from what that reader is asking.

## The setup marker is written on change, not on every run

`/fusion:setup` writes `fusion-workbench/.fusion-setup` when the file is **missing**, or when the `plugin_version` it carries differs from the version the plugin ships. In every other case it writes nothing at all, rather than writing identical bytes.

The marker is class R3 and therefore tracked, and that is what makes the condition worth stating: an identical rewrite still moves the file's modification time, so an unconditional write produces a touched file on every Setup in every checkout, and each checkout then carries a change it did not make. Two consecutive runs at one plugin version leave the marker byte-identical, with its modification time unchanged.

## Two consequences

**Nothing in class L survives a fresh clone**, so no skill may promise that git holds its bytes. That promise is available only for R1, R2 and R3, and only where the project tracks the workbench at all.

**An ignored path is skipped by `git stash --include-untracked`, but not by `git stash --all` or `git clean -xdf`.** Ignoring a transient protects it from the first and from nothing else. This consequence had its consumer in the two stash-and-restore skills and lost it when they were removed on 2026-08-15; it is kept because it governs any command that sweeps the tree, not because a skill reads it today.

This repository applies exactly this partition; see its `.gitignore`.
