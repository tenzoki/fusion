# Upgrading to v10.23 (from v10.22)

One note for 10.23.0. No `upgrading-to` note exists for 10.21 or 10.22; `git log v10.20.0..v10.22.0` is the record for those, and `docs/upgrading-to-v10-20.md` is the rung below this one.

Nothing in your project is rewritten by this release, with one named exception: four personal log files change their name, and the skill that writes each one renames an existing file onto the new name on its next run. Everything else arrives as one new store, one new helper, two new lines of Setup output, and rules that change what gets written from here rather than what is already on disk.

## What you will notice

- **One file appears, and its name is yours to choose once.** On your next `/fusion:setup`, the checkout you run it in registers itself: one file at `fusion-workbench/shared/checkouts/<8hex>.md`, named after the identifier `bin/fusion-identity` already minted for that checkout. Setup asks once, in plain chat text, for the person who works in this checkout and a name for it, offering a suggestion and whatever persons the store already holds. Declining everything still writes the entry, with the suggested name and your git identity. The entry is what records that the question was asked, it publishes nothing that is not already in every commit you have made, and its content reproduces the previous behaviour exactly. Where an entry exists, Setup refreshes the git identity silently and asks nothing. No field carries a hostname, an account name or a folder path, which was a decision and not an oversight (`260904-1058_*_does-a-registry-entry-carry-hostname-account-name-and-folder-path.md`).

- **The name is an attribute; the eight hex characters stay the key.** They stay the key in the filename, in every event line, in every claim field and in every comparison, so no record and no event line is rewritten. Four places render the name where they rendered the hex: the monitor header, `/fusion:next`'s refusal when another checkout holds a Circle, the `party=` lines of `bin/fusion-events presence` (a sixth TAB-separated field, appended, so anything reading five is unaffected), and `FUSION_ALIAS`, which SessionStart exports where an entry exists. Where nothing resolves, all four render the hex exactly as before.

- **Two git identities of one person now count as one.** `bin/fusion-events presence` joins the git identities the registry maps to one person, so `other_people` can go down. That is the correction landing, not a lost figure. If you work from two machines with two git configurations, register both and the count stops reporting you as two people. With no registry the map is empty and the figures are the ones v10.22 printed, from the same code path rather than from a fallback branch. **`/fusion:next`'s claim comparison is untouched**: it still compares the identity as written, because a comparison routed through a pulled file would answer differently before and after a fetch.

- **Four personal log files change their name, from your login to the checkout identifier.** `memos-<checkout>.md`, `tasks-<checkout>.md` and `cadence-<checkout>.md` in the memo store, and `activity-log-<checkout>.md`, which stays in your project root. The login was the wrong key in both directions: two people whose machines both call them `dev` wrote one tracked file from two checkouts, and one person whose machines call him `k1` and `kai` got two of everything with nothing saying they were one person's. The minted identifier gives one writer per file by construction. The cost of the choice is stated rather than smoothed: one person on two machines still gets two sets of these files, and joining them is a lookup through the registry rather than a property of the name (`260904-1058_*_four-tracked-workbench-filenames-are-keyed-by-the-os-account-name-the-identity-decision-rejected.md`).

- **An existing file under the old name is adopted, never orphaned.** The skill that writes one renames `<prefix>-<login>.md` to `<prefix>-<checkout>.md` on its next run, when your login is the suffix and nothing already stands at the new name, and reports the rename. In every other case it leaves the file where it is and names it in the report. Nothing is merged and nothing is deleted, and a legacy file that really did have two writers is not separated by the rename, because no line in these files records who wrote it. One order effect worth knowing: `/fusion:cadence` reads the activity log and never writes it, so until the log's own next run cadence reports that source absent with the legacy file sitting in front of it.

- **A resolution line now cites a heading, and an answered or deferred decision names who ruled.** `Resolved:`, `Answered:`, `Implemented:`, `Deferred:` and `Superseded by:` take a storeless basename plus a `## Heading`, never `path:line`, because an edit above a line moves it silently and the target these lines most often name is a session history still being appended to. `Answered:` and `Deferred:` additionally carry `ruled by <agent name or "user">, <person>`, reusing the shape the `**Filed by:**` head field already uses; the other three cite something a reader verifies without trusting anybody, so they take no ruler. **Existing records are not rewritten and no gate checks the field.** An absent ruler means the record predates the rule, never that nobody ruled (`260905-1228_*_does-a-resolution-line-cite-path-line-or-a-heading-anchor.md`, `260905-1228_*_does-an-answered-record-carry-who-ruled-now-that-only-the-orchestrator-may-transition-it.md`).

- **A citation carrying a store segment inside a fenced code block is now reported.** The fence still covers everything a lookup decides: whether the record exists, whether it resolves to more than one file, whether it has moved to another marker. It still keeps `bin/fusion-citation-sweep` off an exhibit, so nothing verbatim is machine-rewritten. What it stopped covering is the store segment itself, which is read off the token's shape before anything is looked up. So `bin/fusion-citation-check` and the `Citations:` line of `/fusion:cleanup` may report rows in your fenced text that they passed over before, and your `verdict=` can go from clean to violations on a corpus you did not edit. The remedy is to name the store in words rather than spelling it into the token (`260905-1228_*_the-record-example-exemption-silences-a-verdict-that-does-not-depend-on-resolution.md`).

- **A reconciliation pass no longer moves a decision from open to answered.** That transition is the orchestrator's alone now, and only to relay a ruling you gave. Where a pass finds an answer already written under an analysis, a plan or another decision, it appends `Answer located: <citation> — <one-line summary>` to the record, moves no marker, and the session's listing of open decisions names that location beside the question, so you rule with the found text in front of you instead of ruling a second time and leaving two answers behind. The cost is real and was accepted with the choice: an answer sitting on disk now waits for a session to put it to you (`260905-1042_*_may-a-dispatched-agent-perform-the-open-to-answered-transition-at-all-and-under-which-bound.md`).

- **Setup says how far behind its upstream your checkout stands.** A new step in the Done report names the count, the upstream branch, and the age of the view it came from. It reads the local remote-tracking ref and **does not fetch**: a fetch is the only network call in an otherwise wholly local sequence, it writes refs before you have agreed to anything, and against a credentialed remote it blocks at a prompt with no portable timeout. So the number answers "behind what this checkout last saw", which is why the age is printed beside it in every case that carries one and leads above a day. No upstream configured, not a git work tree, and a count that could not be read are each their own rendered case, and no branch prints a zero in place of a read it could not take. Advisory, never blocking (`260905-1850_*_setup-does-not-notice-that-the-checkout-is-behind-its-remote.md`).

- **What fusion says in chat should read differently.** The style rules stopped permitting three things they used to allow: internal vocabulary once it was glossed, narration of which pass ran and what it returned, and self-assessment. A principle was replaced by three word lists (no marker or machine token, no framework noun, no agent name as a sentence subject), because a sentence can be checked against a list and cannot be checked against a principle. The binding is chat, gates and summaries; your workbench records keep the internal names, which are correct there, and machine-read output is exempt as before. Half of this reaches you as soon as you run `fusion --update`, since the rule file is read from the plugin on every dispatch; the other half is the two chat profiles copied into your workbench, which Setup offers to refresh when a shipped profile has moved.

- **The one-release-behind cost applies as usual.** Until you run `fusion --update` and restart, the installed copy has no `bin/fusion-checkout-name`, so every call site takes its `[ -x ]` miss branch and renders the hex (`260810-0921_*_how-should-a-prompt-call-a-bin-helper-that-the-installed-copy-may-not-have.md`).

## If you do not want the checkout store

Delete `fusion-workbench/shared/checkouts/` and every reader falls back to what it did before: the hex renders everywhere, `presence` counts raw git identities, and `FUSION_ALIAS` is not exported. Nothing degrades and nothing warns. The next `/fusion:setup` asks the question again, since an absent entry is exactly the unregistered state. The personal log filenames do **not** revert — they are keyed by the minted identifier, which exists with or without the store.

If your project tracks its workbench, the store is class R1 in `rules/workbench-tracking.md`: it travels in git like every other record store, and it needs no merge driver and no lock, because each checkout writes only the file named after its own identifier. A collision on a name is reported and never enforced, for the reason the claim field already carries: a checkout that has not pulled cannot see an entry that has not been pushed.

## Verify after updating

`fusion --update`, restart, then `/fusion:setup` at your project root. The Done report names which registration branch ran and how far behind your upstream you are. After that:

- `"$FUSION_PLUGIN_ROOT/bin/fusion-checkout-name" roster` prints `entries=` and one `entry=` line per registered checkout.
- `"$FUSION_PLUGIN_ROOT/bin/fusion-events" presence` prints `party=` lines whose sixth field is the name or `-`.
- `"$FUSION_PLUGIN_ROOT/bin/fusion-citation-check"` prints the `verdict=` line over your own corpus, now including fenced tokens that carry a store segment.

Each helper's own header is the authoritative documentation for its subcommands, exit codes and output shape.
