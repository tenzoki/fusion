# A campaign over several checkouts

One project, several clones, and only git between them. Each clone runs its own session, claims a work package and commits; nobody sees what the others hold until the next pull, and nobody can say, from one place, which checkout should take which package next. A campaign is the frame above that: one record naming an objective, the conditions under which the work stops, and the lanes, one ordered list of packages per checkout. The record is a file in the repository like everything else fusion writes. It travels by push and pull, needs no server between the clones, and is legible with `cat` when the tooling is not to hand.

A campaign has one writer, the steering session, which is a session in a checkout that holds no package of its own. Every other checkout is a working session, a peer: it reads the campaign once per commit cycle, and again whenever the remote moves while it waits for an answer, and does what the record says. Nothing on either side holds a lease or a lock; the record is read, and the reader acts on what it read.

**Before the first use, update every checkout and restart.** A session reads its command roster from the installed copy of fusion when it starts, and never re-reads it. An install that predates this feature carries neither the command nor the helper, and more than that: a package that declares areas and a campaign record are both refused by an older reader, by name and not silently, so a workbench in which one checkout has declared areas is unreadable to a checkout that has not updated. Declare areas and open a campaign only once every checkout of the project runs this version. In a workbench a Prior host also reads, that holds only after Prior has re-pinned the codec, which it did at Prior `bf6bb42`, answering request 81 in `codec/fixtures/prior/REQUESTS.md`; whether Prior runs this version's bundle is request 82, asked, and this page predicts nothing about the answer.

## The three commands

**`/fusion:campaign`** is the steering session's command, the body in `skills/campaign/SKILL.md`. Without an argument it shows the overview: who holds what at the commit the remote stands at, when each checkout last pushed, what each package waits for, and, for a running campaign, how each lane stands and which of seven conditions hold. `cut --checkouts <N>` proposes the lanes and writes a proposal file, nothing else; `lanes` writes a confirmed proposal into the record, with the checkout each lane is assigned to, and then asks once whether every lane member runs autonomously. `open`, `pause`, `resume`, `move`, `reassign` and `end` are the six steering acts, each one confirmed write. `answer` files the user's answer to a peer's question, and every use while a campaign runs turns on the steering watch; both are in `## Questions go to the steering session` below.

**`bin/fusion-campaign sync`** is the working session's half, run by the orchestrator in every commit cycle (`agents/orchestrator.md` `### Step 4 — commit`, sub-step 5a), never typed by the user. It fetches, reads the campaign at the fetched commit, writes one `campaign_read` row per campaign into the event log, settles that log, rebases, pushes, and prints the commits the push landed. A `paused` campaign that steers this checkout makes the orchestrator dispatch nothing more and report the reason; the package stays claimed. In a running campaign whose lane names this checkout, the same read also prints the lane, its next package and the open questions, and the orchestrator acts on them (`## The lane handover` below). `sync --read` is the same read without the commit cycle: it fetches and prints and moves nothing, run at Setup, and before a session opened with no task asks its user for one: a `lane=` row naming this checkout is the task, and the session asks nothing.

**`bin/fusion-write set-resources`** declares a package's areas, the paths of the project it works in, relative to the project root and without a trailing slash, each covering everything under it. The entries stand on the user's confirmation; no agent invents one. The cut reads them and nothing else about a package's content.

## What travels

Four things, all by commit and push: the campaign record, the packages' control files with their claims and their declared areas, the event log with its `commit` and `campaign_read` rows, and decision records, a peer's question in its package and the user's answer in the shared decisions store. The steering session writes the record, then commits and pushes it in the turn the user confirmed the act; the act reaches a working session at that session's next commit, when `sync` fetches and reads, or sooner when that session is waiting and its watch reports the act. No time is attached to the first case, and `## What "next commit" has meant in practice` below says why.

A pause is read the same way. On Prior a pause takes effect at once; here the working session finishes the commit cycle it was in, push included, and reads the pause at the fetch after it. The latitude is deliberate: a withheld push would strand a finished commit in one clone.

## The lane handover

A peer in a running campaign takes its lane's next package itself. When the package it holds is finished, `sync` names the lane's next package with that package's own mode and what it waits for. A next package whose mode is `autonomous` and which waits for nothing is claimed at once, with no question to anyone: the package's own field answers the claim. A next package in `ordinary` mode is not claimed; the peer files "may I take it?" as a question to the steering session. A lane with no package left, or whose next one still waits, is reported once, and the peer stops. A checkout that no lane names, and a project with no running campaign, behave exactly as before. A session opened with no task reads its lane before it asks for one, and a `lane=` row is the task. The Prior orchestrator does not: its STEP 1 still asks a lane peer for its brief, which the campaign's spec leaves out of scope. The rows and their order are the helper's header, `## Output of sync`; what the orchestrator does with each is `agents/orchestrator.md` `### Step 4 — commit`, sub-step 5a.

The pause still applies as before: a `paused=` row stops the peer whatever its lane says.

## Questions go to the steering session

A peer in a lane does not ask its own user. Every approval that would stop and ask, every question it would file and skip, and the "what next?" at the end of a task become a decision record in the container of the package it holds (`agents/orchestrator.md` `## Human approval rules`). The record carries the question, options worded so the steering user can answer without the peer's session, and two head lines:

- `**Asked by:** checkout <hex>, package <container>`, naming who waits.
- `**Set aside:** <what>`, naming what the peer put down: a plan step, the claim of a package, or an approval row. A later session of the same checkout finds it there, since nothing else remembers it.

The peer carries on with whatever does not depend on the answer, releases nothing and claims no second package.

The steering session's overview lists each open question and each lane whose next package is ready. `answer` reads the question at the fetched commit, puts it and its options to the user in chat, and files nothing until the user has chosen (`skills/campaign/SKILL.md` `## Step 8`). The answer is a new decision record in the shared decisions store whose head carries a third line, `**Answers:** <question basename>`, exactly once. That one exact line is what makes a question answered, for the overview and for the peer; a cross-reference is not an answer. The spelling was ruled in `261119-1248-how-does-an-answer-name-the-peer-question-it-answers-and-how-does-the-peer-remember-what-it-set-aside.md`, option 1. The user's choice confirms the answer, so the steering session commits and pushes it in the same turn; a peer whose session is open and waiting reads it within about 5 minutes. The peer then marks its question answered, citing the answer and naming the user as the one who ruled, and resumes what `**Set aside:**` names. No agent answers a peer's question, on either side.

## The two watches

Two sessions poll the remote, and nothing else does. Both start `bin/fusion-campaign watch --report` as a background command, with the Bash tool's `run_in_background`, and `TaskStop` ends it. The watch asks the remote for its head every 5 minutes with `git ls-remote`, fetching nothing. When the head moves, it fetches once and compares the rows at the old head and the new. It exits only when there is something for the session to act on, or on the first failure of an outage. The exit wakes the session. Its notice carries no output, so the woken turn reads the task's output file for the row, acts on it, and starts the watch again from the `head=` it printed. A move with nothing to act on, the session's own push included, wakes no one. A background command has no 30-minute expiry, so there is no re-arm on a timer either.

- **The steering watch** (`--report steering`). Every use of `/fusion:campaign` while a campaign runs turns it on. It wakes the session for a new question to answer or a lane whose next package became ready, and the session tells the user only that; a campaign that stopped running wakes it too, and the watch ends. It also stops after a pause or an end in this session, and when the user says so (`skills/campaign/SKILL.md` `## Step 9: the watch`).
- **The waiting peer** (`--report lane`). A peer with an open question and nothing left to do says once that it waits for the steering session and starts the same watch. It wakes for an answer to one of its questions, a pause of its campaign, or an end. It acts on the row as the commit cycle does, and stops once none of its questions is open or the campaign has paused or ended.

**An outage is told once per session.** Every `ls-remote`, and the fetch on a move, is killed after 60 seconds and counts as a failure, so a remote that accepts the connection and then hangs is reported like one that refuses it. The first failure wakes the session with one `failed=` row. A state file beside the watch's pid file records that the session was told, so the watch it starts again stays silent until the remote answers. The issue that raised the hanging remote, `261120-2050-campaign-watch-sets-no-timeout-on-ls-remote-so-a-hanging-remote-silences-it.md`, is closed by that bound.

**Bash must start the watch without a permission prompt** in every checkout that runs either watch, or each restart waits on the prompt, and a watch nobody is there to restart is no watch. The measurement is `261123-1414-can-a-background-command-wake-an-idle-session.md`. A background command ran for 65 minutes, and the session saw no notice. Its exit woke the idle session 10 seconds later. The restart showed no prompt in auto mode. Default permission mode was not measured, so this page names no allow rule for it.

**These two watches set aside one ruling, for themselves only.** The adoption decision `261108-1927-does-the-claude-side-adopt-the-campaign-as-its-one-frame-for-work-spread-over-several-checkouts.md` ruled out polling. The user ruled on 2026-11-19 that the steering session polls the upstream while its session is open (`261119-0851-how-does-a-campaign-steer-its-peers-and-get-their-results-and-questions-back.md`, ruling 2(a)), and the waiting peer uses the same poll. Nothing else in fusion polls: no daemon, no lock server, no shared dashboard.

The rows, the state file and the bound are the helper's header, `## probe and watch`.

## No message between sessions

**A message between sessions carries no authority, and this release sends none.** A peer acts on records it read at a fetched commit: the campaign record, its packages' fields, and an answer that names the user who ruled. A wake-up from one session to another would carry no consent under the harness, and none is sent. If one is added later, it may only make a peer read the records again; it carries no instruction.

## What the overview can and cannot see

**It is as old as the slowest checkout's last push.** The overview reads one commit, the one the branch's upstream stands at after a fetch, and reports that commit's age as the age of the picture. Everything a checkout has done since its last push is invisible, and the picture is never newer than the newest push by anybody.

**A last-push time is a lower bound.** The time comes from the checkout's own `commit` rows in the event log, matched to commits on the ref by hash or, where a rebase renamed the commit, by subject and author time. A row reaches the ref only with the commit that carries the log, so the figure trails the checkout's newest push by that one commit, and a row that names no commit on the ref is counted in a note rather than dropped. The measurement behind the rule, and the three alternatives it ruled out, are in `hooks/lib/campaign.ts`.

**A file several lanes share by design is declared on none of them, and then reported by neither the cut nor the overview.** The cut groups packages whose declared areas overlap into one lane; a file every lane touches, declared on each, would pull every package into one lane. So it is declared on no package, and a commit into it by any lane prints no cross-lane row. The user ruled on 2026-11-09 (ruling B, in the campaign package's narrative) that this limit stands and is stated rather than engineered around.

**A commit by a checkout in no lane produces no cross-lane row.** The row compares two lanes, the committer's and the declaring one; a checkout outside every lane has no lane to compare, so its commits into a declared area are not reported. A commit that no checkout's rows name is reported as unattributed, in a note.

**The lane view is evaluated for a running or paused campaign only, and only once it has lanes.** A campaign that has ended steers nobody, and a campaign whose lanes are still to be cut has nothing to be in or out of. A campaign whose record the codec refuses is named as unreadable and evaluated no further. Those two states are the one reading of a live campaign, for the writes as for the reads: a steering act without `--campaign` names the one running or paused campaign of the workbench, and a `draft` or `authorised` one, which Prior writes and `open` never does, is named with the flag alone and steers no checkout until it runs.

## What "next commit" has meant in practice

The gap between two commits of a working session is the delay with which a steering act can reach it. Fusion measured that gap once, over the event logs of two projects, in `261109-1515-commit-cadence-of-autonomous-sessions.md` in fusion's own workbench. The 90th percentile of the gaps between consecutive commits of an autonomous session was **137.8 minutes** in the consuming project's log (45 sessions, 1 369 gaps), **146.1 minutes** in fusion's own log (11 sessions, 470 gaps) and **139.8 minutes** pooled (56 sessions, 1 839 gaps); the medians were 21.2, 14.0 and 18.6 minutes. Gaps of 24 hours or more were cut, five in all.

Read the figures for what they are. They are gaps between commits, not a bound on how long a pause goes unread: a session that sits idle writes no commit, and nothing bounds how long it sits. A peer that waits on an open question is the exception: its watch reads the remote every 5 minutes and wakes it for an answer, a pause or an end (`## The two watches`). An idle peer with no open question still reads nothing until its next commit. Most of the long gaps follow a finished commit or a finished task: in 247 of the 316 gaps over an hour in the consuming project, and 76 of 104 in fusion, the longest stretch without any row begins where the session has just committed or just received a finished task. That reads as a session waiting for its user, and it is inference: no row marks a wait, and an orchestrator working for an hour in its own loop would look the same. Three gaps in four are under an hour in both logs.

The user accepted the measured figure as the intervention delay on 2026-11-09 (ruling C). That is why the user-facing sentence is "at the holding session's next commit" and names no time. For a peer that is waiting on its watch, a pause, an end or an answer arrives within about 5 minutes of the steering session's push; every other act waits for its next commit.

## Commit hashes in records

**A commit hash written into a record is a pushed one.** A working session's cycle is commit, then fetch and read, then rebase, then push, and a rebase over a moved upstream replaces the hash the commit had locally. A hash copied from `git commit` into a decision's implementation reference, a closure note or an issue's resolution line therefore names a commit no other clone may ever hold. The rule, in the orchestrator's commit step, is that a record takes the hash a `pushed=` line of `sync` names for that commit, found by its subject, and never the one `git commit` printed; where no line has been printed yet, the write waits for the cycle that prints it. With no helper installed, or a branch with no upstream, nothing rebases and git's hash stands as before.

**A record already carrying an older hash that no clone resolves is left as it stands.** A terminal record is never rewritten, and a hash in a live one is not corrected by hand. Its commit is found by subject and author time, which a rebase keeps, the same join the overview uses for a checkout's last push. The issue that raised the point is `261109-1341-a-commit-hash-written-into-a-record-before-the-rebase-goes-stale-when-the-rebase-rewrites-the-commit.md`, in the campaign package's workbench.

## Where the Claude side deviates from Prior

The campaign record is Prior's format, `fusion.campaign/v1`, and fusion's codec reads it as Prior's does. What the Claude side does with it differs from Prior in these points, and this section is the one home of the list.

- **N lanes against Prior's two-writer bound.** Prior's campaign admits two writers; the Claude side cuts the work into as many lanes as the user names checkouts.
- **A pause takes effect at once on Prior.** After it, no protected action runs and no attempt records its outcome. Here a pause is read at the fetch after the working session's next commit, and that commit cycle is finished, push included.
- **A first stored state of `running` with empty `sessions` and `runs`.** `open` writes it; Prior's own lifecycle cannot produce it, and Prior reads it as a shape its `Start` never writes. It grants nothing on Prior, and it holds only while no import of a Claude-written campaign into Prior is planned; none is. A `resume` writes the reason back to null, which is Prior's correction and no deviation.
- **The cut groups nested areas.** Two declared areas overlap for the cut when they are equal or one lies under the other at a `/` boundary. Prior's `overlap` reads equal strings only, so Prior's reading is the narrower one: every pair Prior groups the cut groups too, and the cut groups nested pairs Prior would not.

**The two hash values are no deviation.** `state.charter_hash` and `state.revision` of a campaign the Claude side writes are Prior's own `charterHash` and `stateRevision`, computed by the codec on `show` and copied into the record by the writer, so they equal what Prior would compute over the same bytes. An interim rule that would have labelled a different value as Prior's was withdrawn before any campaign was written.

**Areas and campaigns are for this version's readers.** A package carrying `resources` and a campaign record are each refused by an older codec, so areas are declared and a campaign is opened only once every checkout runs this version, and in a workbench a Prior host also reads, only after Prior has re-pinned the codec, which it did at Prior `bf6bb42` (request 81). Whether Prior runs this version's bundle is request 82's, and this page does not say.

## Where the mechanism is written down

`bin/fusion-campaign`'s own header is the authoritative documentation for every sub-command: the fetch and the read at the commit, the `last_push` rule, the lane view and the seven conditions, the cut's rules and its proposal file, each steering act with its refusals, the `answer` write, the commit cycle of `sync` and the lane rows of `sync --read`, `probe` and `watch`, the notes, the state vocabulary and the exit codes. None of it is copied here, deliberately: a second copy drifts from the first, and the first is the one the program obeys. The computations behind it are `hooks/lib/campaign.ts` (the overview and the lane view), `hooks/lib/campaign-cut.ts` (the cut), `hooks/lib/campaign-write.ts` (the seven writes and `answer`), `hooks/lib/campaign-sync.ts` (the commit cycle and `sync --read`) and `hooks/lib/campaign-watch.ts` (`probe` and `watch`), each with its own header.

The flow on the steering side lives in `skills/campaign/SKILL.md`; the working side's is in `agents/orchestrator.md`: Setup, `### Step 4 — commit` (sub-step 5a), `### Step 5 — say where things stand, and ask what is next` and `## Human approval rules`, each in its campaign-lane paragraph. What a work package is, and which of its fields a campaign reads, is `rules/fusion-workbench-conventions.md` `## Work packages`. The companion page for the other thing that travels between checkouts, a message, is `docs/messages-between-checkouts.md`.
