## What changed

Two files, and no source file.

**`hooks/lib/__tests__/citation-sweep.test.ts`**, +85 lines: one import line and
one new `describe` block carrying a six-row fixture table and a single property
loop over it. The block sits between the `--repair` describe and the
release-gate describe, so the file still reads dry-run, write, repair, property,
release gate.

The table is data. Each row is `[label, directory, citation]`; the loop writes
one fixture record per row into a scratch workbench inside a scratch git
repository, commits it, runs `--write --yes`, and then compares the scan of each
file's committed text with the scan of its swept text. A token is *judged* when
its kind is in `GATE_KINDS` and its status is not `exempt` — the same predicate
`readsBackWhole()` in `hooks/citation-sweep.ts` applies to its own output — and
tokens are matched by `line:col`, so a token that disappears fails exactly as
loudly as one whose status becomes something nothing judges. Every judged token
before must have a judged token at its own column after; the failure message
lists each loss as `<label>: '<token>' <kind>/<status> -> <what is there now>`.

There is no per-shape assertion beside the loop, by instruction and for the
reason `rules/critical-stance.md` §2 gives: an enumeration beside the property
is the thicket, and the property is what catches the seventh shape nobody wrote
a row for.

The six rows. Fenced, because every one of them is a deliberately malformed
citation and fencing is how this project states a path without claiming it as a
live pointer — unfenced, the last three would move this repository's own
`rewrites=0` release gate:

run against that old grammar. Exit 1. **Five of the six rows fail, and each in
the same way — `record`/`store-prefixed` becomes no token at that column:**

```
a foreign path segment before a store: 'issues/260101-0101_o_alpha.md' record/store-prefixed -> no token at that column
a word character before a store: 'planning/260101-0101_o_alpha.md' record/store-prefixed -> no token at that column
a bracket-marked store-prefixed citation: 'shared/issues/260519-0438' record/store-prefixed -> no token at that column
a bare Circle-directory rooting: 'issues/260101-0101_o_alpha.md' record/store-prefixed -> no token at that column
an archive rooting: 'shared/issues/260101-0101_o_alpha.md' record/store-prefixed -> no token at that column
```

The one row that holds at `cda72f71` is *a citation inside a frozen store*: its
token already began at its own left edge, so the splice replaced the whole path
and the storeless basename read back as `bare-record`/`resolved`. It is in the
table for corpus coverage, not because it ever failed.

Two things the transitions say that the summary line does not. The three
unanchored rows each lose the token because the rewrite spliced a storeless
basename in behind a path fragment the token never covered; the four spliced
results are in the fenced failure listing above, in the four rows whose fixture
names begin with a foreign path, a word character, a bare Circle directory and
an archive rooting. `BARE_RE`'s
lookbehind refuses every one of those left contexts — the corruption and the
blindness are one defect seen from two sides. The bracket row loses it
differently: the old tail class stopped at the stamp, so the token was the store
segment plus that stamp alone, its rewrite was the bare stamp `260519-0438`, and
the resulting `260519-0438[o]-loader-check.md` is refused by `STAMP_RE`'s
`(?![0-9A-Za-z_\[])` lookahead. Not a demotion to `stamp-bare`, which is what a
reader might expect: no token at all.

At HEAD all six hold. Rows 1 and 2 hold vacuously — the left anchor means the
grammar reports nothing there to begin with, which is the repair — row 3 holds
because the visibility guard declines the rewrite outright, and rows 4, 5 and 6
rewrite to the fixture's storeless basename, as the fenced listing shows, and
read back `bare-record`/`resolved`.

The worktree was removed with `git worktree remove --force` and pruned. No
