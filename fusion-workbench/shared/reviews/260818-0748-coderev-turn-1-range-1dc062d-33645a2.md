The implementer's report claims one of these six. The other five hold, and the two per-branch
injections establish something the tail injections cannot: the gate localises. A citation added to one
conditional clause reddens only the cases that drive that clause, so the failing test names tell you

The hash count differs from the stamp count by one on the coverage builder, and the reason is worth
recording: the `detects a foreign identifier` self-test at `:230-242` appends its own stamp to the
sentence and asserts `foreign()` returns **exactly** that one identifier, so a second injected stamp is
absorbed by the `Map` dedup while an injected hash is not. That is the test behaving correctly in both
cases.

### 2. Branch coverage — nine cases, and nine is the whole set

Walked both builders line by line.

`coverageSentence` (`lib/review-coverage.ts:673-700`): `uncovered.length > 0`; `carried.length > 0`
with the `carriedFrom === null` ternary both ways; the `parts.length === 0` early return; the
unconditional tail. Registry cases: `empty report` (silent), `uncovered only`, `carried, no
carriedFrom`, `carried, with carriedFrom`, `uncovered and carried`. Complete.

`stagingSentence` (`lib/staging-drift.ts:621-663`): the `faults.length === 0` early return;
`records.length > 0`, which contains a second conditional per row
(`r.code.trim() === "??" ? "untracked" : "unstaged"`); `messages.length > 0`; the unconditional tail.
Registry cases: `no faults` (silent), `records only, untracked and unstaged` — the two rows carry
`??` and ` M`, so both arms of the inner ternary are driven — `commit-message only`, `records and
commit-message`. Complete.

Both silent branches are pinned to `""` rather than skipped (`:216`), which is the right call: a
builder that started speaking on an empty report would otherwise be invisible here.

One thing the gate correctly does not need to cover, checked rather than assumed: `hooks/tracker.ts`
returns the builder's string **unmodified** (`:327-335`, `:411-419`). It composes a separate `detail`
string, but that goes to `emitEvent` and the event log, not to the model. So the builder's output is
the model-facing text, and the boundary the gate tests is the boundary that matters.

### 3. The extraction

Two classes, and I checked the claim they leave nothing important out.

*Record paths and Circle directory names.* The header's claim at `:32-33` holds. Every record filename
in this workbench opens with `YYMMDD-HHMM` and every Circle directory is `<stamp>-<slug>`; the stamp
pattern's trailing `\b` is satisfied by the `-` or `_` that follows, so both forms match the stamp
class without a class of their own. I checked this against the actual store rather than the convention
text.

*What the no-digit exclusion lets through.* A foreign 7-character short hash drawn entirely from `a`-`f`
passes silently. The cost is stated at `:31-33` and the `continue` at `:69` points back at it, which is
the right placement — but the rate is wrong, and that is finding 3 below.

*What neither class matches.* A Circle slug in prose ("the guard-rules-write Circle"), a bare
plugin-file path, a version tag. The header names the first of these under `WHAT IT DOES NOT COVER`
and the analysis names it as accepted residual. Nothing new to file.

One latent asymmetry is finding 2 below: the permitted set is drawn from the whole report, and a
`StagingReport` carries fusion-authored `why` prose. No builder emits it today.

### 4. The registry-completeness assertion — works, and misses two import forms

Tested the way it will fail: a third builder added to `hooks/tracker.ts`'s imports and deliberately
left out of `REGISTRY` turns the suite red with a message that names the symbol and says what to do.
That is the case it was built for and it works.

An aliased import that drops the suffix (`budgetSentence as budgetLine`) and a namespace import
(`import * as rc`) both leave the suite at 12 passed. Filed as finding 1.

Two forms it handles correctly, checked: multi-line import blocks (the `[^}]*` class spans newlines,
which is why the current two-block parse works at all), and inline `type` specifiers — `type Foo`
survives the split as `"type Foo"` and fails the identifier regex on the space.

### 5. The failure message

I rendered it from a live failure rather than reading it. Someone meeting it cold gets, in order: which
builder, how many foreign identifiers, which branch, each identifier with its class, the identifiers
the input DID supply, the sentence as returned, the criterion with the reason a consuming project
cannot resolve it, the incident it came from, and the fix. It is a deliverable and it reads as one.

The no-allowlist instruction is in the right place. The person about to relax the gate into a shape
allowlist is the person who just tripped it, and the last two sentences of the message are addressed to
exactly them, with the reason attached rather than asserted — the uncovered branch's own hashes are
what a shape gate would redden on. The same argument is in the file header at `:19-25` for the other
reader, the one editing `identifiers()`.

One ergonomic cost, reported rather than filed: the ~18-line criterion block is re-emitted per failing
case, so a citation added to a shared tail prints it four or five times. That is scrollback, not a
defect, and the alternative — printing it once — would require state the test framework does not give
a test body.

## Findings

All three are filed as separate records under `shared/issues/`.

1. **`260818-0745`** — the registry-completeness parse misses an aliased and a namespace import, so a
   correctly named builder still escapes. Measured, both forms. Low; neither form is this codebase's
   style, and the fix is two lines that add no allowlist.
2. **`260818-0746`** — the header's "Nothing authored in the source may contribute an identifier"
   (`:14`) is wider than the relation enforced. `supplied()` reads the whole report, and
   `StagingRow.why` / `StagingReport.why` are fusion-authored literals. Latent: no `why` literal
   carries an identifier today and no builder emits one. Fix the sentence, not the relation — narrowing
   `supplied()` would need the per-field allowlist the design refused.
3. **`260818-0747`** — the hex exclusion's stated miss rate, "about 1 in 700" (`:32`), is
   `0.375^7 = 1 in 959` for a 7-character short hash. The error runs conservative. Filed because a
   stated cost nobody can reproduce defeats its own purpose.
