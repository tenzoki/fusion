## What was implemented

A pure module answering the two questions the `FUSION_ALLOW_RULES_WRITE` exemption needs
answered, exported for both write surfaces to consume in Steps 3 and 4:

- `RULES_WRITE_ENV` — `"FUSION_ALLOW_RULES_WRITE"`, for diagnostics.
- `RULE_DIR_PATTERNS` — `["rules/**", ".claude/rules/**"]`, `readonly`.
- `isProjectRulePath(path)` — canonicalises, then `matchesAny` from `./paths.js`.
- `rulesWriteExemptionActive(env)` — `isEnvFlagSet` from `./git-branch-guard.js`, so the
  accepted spellings are `"1"` and `"true"` case-insensitively and nothing else, exactly
  what the two git overrides accept. The environment is a parameter; the module never
  reads `process.env`.
- `rulesWriteDetail(paths)` — the advisory message, shaped like the git override note at
  `hooks/guard.ts:293-309`: it names the variable that granted the permission and what the
  permission let through.

No filesystem access, no cache, no ambient state. 60 test cases, written as matrices.

## One deviation from the plan letter, and why

The plan says the boundary "falls out of the glob semantics rather than needing a special
case" (`:222`). That is true for the case it names — the bare directory `rules` does not
match `rules/**` — but two other spellings of a path reach the predicate and would have
granted more than the flag names. Both were verified at HEAD `e8988d9` rather than
inferred, so `isProjectRulePath` canonicalises lexically (trailing separators dropped,
`.` and `..` collapsed) before matching.

1. **A trailing separator.** `rules/**` compiles to `^rules/.*$`, whose `.*` matches the
   empty string, so `matchesAny("rules/", ["rules/**"])` is **true** while
   `matchesAny("rules", …)` is false. The Bash path applies `node:path.normalize` to every
   operand (`bash-mutation-guard.ts:1043`), and `normalize("rules/")` keeps the separator.
   So with the flag set, `rm -rf rules` would have stayed denied through the ancestor pass
   while `rm -rf rules/` walked through the exemption and took the rule directory with it —
   the exact outcome the plan's own sentence at `:222` rules out.
2. **A `..` segment.** `rules/../agents/coder.md` matches `rules/**` textually, which is
   why it is protected today, but it writes `agents/coder.md`. The Bash path collapses this
   before the predicate sees it; the write-tool path does not, because
   `normalizeToRelative` (`guard.ts:113-125`) returns a relative path untouched. So an
   `Edit` of that path would have been exempted and would have written an agent prompt.

Canonicalisation only ever **shrinks** the exempt set: it resolves a path to the target it
actually names. Since the exemption is consulted only for a path the protected list already
matched, shrinking it cannot allow a write the guard would otherwise have blocked. The
reasoning is in the module docstring so a later editor does not simplify it away.

Consequence worth naming for Step 4's cases: `rules/retired` (the subdirectory) **is**
exempt, `rules` and `.claude/rules` (the roots) are not, in any spelling.

  `fusion-workbench/.guard-state/events.jsonl`, `fusion-guard.json`. Plus ordinary files,
  prefix-siblings (`rules-draft/`, `rulesx.md`, `.claude/rulesets/`), absolute and
  `../`-rooted rule paths, and the empty string.
- **The bare rule directory** — eight spellings, all outside the exempt set.
- **Canonicalisation** — traversals that leave the rule directory are not exempt;
  traversals that stay inside still are; the project root in four spellings is not.
- **Flag spellings** — accepted: `1`, `true`, `TRUE`, `True`, and both padded. Rejected:
  `0`, `yes`, `on`, `no`, `false`, `""`, `" "`, `2`, `1.0`, `truthy`, `undefined`, absent,
  and a similarly named variable. One case pins that two environments give two answers in
  one process.
- **`rulesWriteDetail`** — names the variable and every path, singular and plural label,
  a non-silent empty case, single line.
