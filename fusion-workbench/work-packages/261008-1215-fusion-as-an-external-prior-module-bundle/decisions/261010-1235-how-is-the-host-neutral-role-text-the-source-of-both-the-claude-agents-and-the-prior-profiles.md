# How is the host-neutral role text the source of both the Claude agents and the Prior profiles?

## Question

The ruling of 2026-10-09 binds fusion to author the host-neutral part of every role once, extracted from today's `agents/*.md`, and to generate both host outputs from it. It does not say how that source relates to the eleven Claude prompts that ship today. The choice binds every later edit of an agent prompt, so it is made once, before any role text moves. Three constraints narrow it. The standalone Claude distribution must not change. `agents/*.md` carries a failing growth bound, and every dispatch path is charged at zero head-room (`README-hooks.md` `### Growth bounds on the shipped text`). Today's prompts mix host-neutral rules with Claude mechanics inside one section, for example `$OUT_ISSUE` and `bin/fusion-write` inside a `## Scope` paragraph, so a heading is not a clean cut.

## Options

1. **Span parts, Claude output generated byte-equal.** Each role that has a Prior rendering gets `catalog/profiles/<id>/` holding `profile.json` and an ordered list of Markdown parts, each tagged `neutral`, `claude` or `prior`. The Claude render concatenates the `neutral` and `claude` parts in order and must reproduce `agents/<id>.md` byte for byte; a test in the new package fails on any difference. The Prior render concatenates the `neutral` and `prior` parts. `agents/<id>.md` stays committed, becomes generated output for those roles, and keeps every lint and bound that reads it. A role without a Prior rendering keeps its hand-edited `agents/<id>.md` and appears in the catalog with its support state and no parts; converting it is part of adding its Prior support.
   - Pros: the Claude bytes cannot drift, so the distribution is unchanged by construction and no growth bound moves. A cut can fall inside a section, which the mixed prompts need. The neutral text is literally shared, so "the same tasks, hand-overs and quality requirements" reduces to a byte comparison.
   - Cons: editors of the converted prompts edit parts, not `agents/<id>.md`. The parts duplicate the converted prompts' text inside the repository. Two kinds of agent file coexist until every role is converted.
2. **Agents stay the source; neutral sections declared by heading.** `profile.json` lists the headings of `agents/<id>.md` that are host-neutral; the Prior render copies those sections and appends a Prior overlay. Nothing in `agents/` changes and nothing is generated.
   - Pros: no new editing surface; no duplication.
   - Cons: the sections are not neutral today. Making them so means rewriting Claude text, which changes the distribution and spends head-room the paths do not have, or shipping Claude mechanics into Prior's role text, which the ruling excludes.
3. **Convert all eleven prompts to parts now.**
   - Pros: one kind of agent file from the start.
   - Cons: 323 031 bytes of prompt text (`wc -c agents/*.md` at `4eb4380a`), `orchestrator.md` and `policy-curator.md` among it, change their editing route in a package whose proof needs `code-implementer`, `reviewer` and `state-auditor` alone. That is scope the directive does not ask for.

## Constraints

- `agents/*.md`, `skills/`, `rules/` and `CLAUDE.md` keep their bytes, or every change is paid for inside the same bound. No head-room raise is planned.
- No host syntax in a `neutral` part: no `$FUSION_PLUGIN_ROOT`, no `bin/` helper, no `$OUT_*` or `$SCAN_*` key, no `Agent(`, no `AskUserQuestion`, no slash command. A test enforces it.
- The Claude render of a converted role is byte-equal to the committed `agents/<id>.md`, and a test enforces it.

## Recommendation

Option 1. It is the only option that meets all three constraints at once. Its cost, the editing route of the `code-implementer`, `reviewer` and `state-auditor` prompts, is stated in `README-agents.md` when the conversion lands, and it grows only as Prior support grows.
