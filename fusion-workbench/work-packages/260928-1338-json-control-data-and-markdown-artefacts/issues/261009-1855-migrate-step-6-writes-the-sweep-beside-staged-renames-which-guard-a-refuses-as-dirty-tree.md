/fusion:migrate Step 6 runs the sweep's write beside staged renames, which guard (a) refuses as dirty-tree, and names no reading of exit 4
---
`skills/migrate/SKILL.md` Step 6 says the sweep's writes stay "unstaged beside the staged renames" and are committed after the migration commit. But the sweep's guard (a) counts every corpus file a staged `git mv` renamed as an uncommitted change, so `--write --yes` exits 4 `dirty-tree` whenever Step 4 moved a Markdown file. Step 6 gives the exits of the dry run (3, 6) and none of the write.
---
**Filed by:** reviewer, Kai Stalmann <ks@qantr.com>

**Evidence.** `skills/migrate/SKILL.md:156`: "On a yes run `"$SWEEP" --write --yes --kinds "$K"` and report its summary, and say that it wrote record content, which stays unstaged beside the staged renames and is committed separately, after the migration commit". `hooks/citation-sweep.ts:571-608`: `porcelainPaths` returns both halves of an `R` entry, and `dirtyCorpusPaths` matches the new path against the corpus. Reproduced on the `78680a11` build: in a scratch repo with a committed JSON workbench, one corpus file was moved with `git mv` from the shared decisions store to the shared analyses store and left staged (porcelain `R`). `--write --yes` then printed `refused (dirty-tree): uncommitted changes name 1 file this run reads:`, naming the renamed file at its new path, and exited 4. The real trials ran because the renames were committed first (`261004-1516-fj04-step12-rerun-proof-on-fresh-copies.md:57`). That order is the one Step 5 advises and Step 6's own sentence contradicts. Since `78680a11`, exit 4 also carries `git-failed`, and Step 6 still says nothing about a non-zero exit from the write.

**Acceptance.** Either (a) Step 6 requires the rename commit before the write, says so, and drops "beside the staged renames", or (b) the sweep's dirty check exempts a staged rename whose content is unchanged (`R100`), with a test. Either way, Step 6 says what to do on a non-zero exit from the write. For exit 4: show the stderr line, write nothing more, and name the refusal (`dirty-tree`, `git-failed`, …). Choosing (a) or (b) changes the guard's meaning in one case, so it is the user's call.
