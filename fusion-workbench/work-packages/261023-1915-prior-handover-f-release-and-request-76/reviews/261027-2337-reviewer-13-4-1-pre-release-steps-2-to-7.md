### Theme A: `prior` text that still states what step 17 or decision 2224 changed

**Finding 1, Medium: three rows of the orchestrator's failure table still revert a file Setup listed.** `catalog/profiles/orchestrator/parts/54a-prior.md:1-3`:

```
| Agent modifies wrong files (out of scope) | Revert the out-of-scope files no earlier task of this run changed with `git checkout HEAD -- <file>`, name the others to the user, … |
| … On failure: revert the task's files no earlier task of this run changed, name the others to the user, … |
| Agent edits outside its declared scope (…) | Revert the out-of-scope files no earlier task of this run changed, name the others to the user, … |
```

Decision `261027-2224` option 1 rules that "a listed file or one an earlier task changed is never reverted". The rows name only the second condition, so a file the user had uncommitted before the run, which this task alone touched, falls in the rows' revert set. Line 7 of the same part forbids that revert. The model meets the row first, and the row is the action instruction. On step 17 that revert becomes a discard in the user's checkout at integration, which is the exact loss the decision exists to prevent. The map rowed only lines 2 and 5 of this part, as class (iii) (O19, O20), and not the revert clauses, so step 6 had no sentence for them. The bold leads of `35-prior.md:1` and `36c-prior.md:1` have the same incomplete condition, but the sentence after it in the same paragraph adds the Setup-listed files, so those two parts are consistent as read. Scope: orchestrator `prior` render only. Fix: in each of the three rows, "no earlier task of this run changed" becomes "no earlier task of this run changed and Setup's `git status --porcelain` did not list". Issue filed.

**Finding 2, Medium: `skill-news` still says the seen mark does not outlive the run.** `catalog/profiles/skill-news/parts/01-prior.md:1`: "What differs from the Claude Code skill is the host mechanics: how a block runs, that the container has no network unless the entry declares its remote, **that the seen mark does not outlive the run**, and that this run pulls nothing." ### Theme C: two narrow gaps in the frozen v2 contract

Both gaps sit in `workflows/entry.v2.json` or `schemas/entry-result.v2.json`, which step 3 froze. Neither asset has left the tree yet: 13.4.1 has not been built or delivered. Whether a correction now is an edit or must be a v3 is not a question the plan answers. Its stopping section holds only the six kept lines byte-equal, but it also says "no frozen file changes its bytes". So each issue needs a ruling on its timing.

**Finding 4, Low: the workbench step reads a control record the integration deleted.** `entry.v2.json` `workbench.input_from.request.record` reads "each workbench control path among the paths of commits[].changes and delta whose status is not D". `internal/entry/entry.go:513-535` `controlRecords` implements that literally. It skips a `D` line but does not drop a path an earlier line admitted when a later line deletes it. So a record changed in a commit and deleted in `delta`, or added in one commit and deleted in a later one, is read. The read is refused, because the record is gone after integration, and `w.service` ends the envelope `refused` (`entry.go:449-452`) although the integration succeeded. `TestControlRecordsAreTheWorkbenchJSONPathsNotDeleted` (`entry_test.go:988-1003`) covers a lone `D` and an `R`, not a `D` after an admitting line. Reachability: every shipped `prior` text forbids a commit inside a run, so `commits` is empty in practice, and a delta names each path once (inference from the map's `entryDelta`, `EW:1356-1373`). So this is a contract gap, not a live failure. Fix: read each path at its last status in commit order and then the delta, and skip it when that status is `D`. That changes the definition's sentence and `controlRecords`, and adds one test row. Verdict on the executor's point: **defect, needs a ruling on its timing.** Issue filed.

**Finding 5, Low: the receipt check admits `..` segments.** The plan's step 4 asks for "every `changes` and `delta` item … in name-status form with a valid relative path". `entry-result.v2.json` `$defs/name_status` and the module's `nameStatus` (`entry.go:465`) reject only an empty path, an absolute path, a tab and a newline. `M\ta/../../x` passes both. `controlRecords` re-checks with `fs.ValidPath` before a read, so nothing the module does with such a path escapes. But the envelope would carry a path outside the repository as an integrated change. The host is trusted and has already applied the delta, so this is a reporting gap. Fix: tighten the pattern to refuse a `.` or `..` segment, in the schema and in the module together. `TestTheNameStatusCheckIsTheSchemasPattern` keeps the two equal. Needs the same timing ruling as finding 4. Issue filed.
