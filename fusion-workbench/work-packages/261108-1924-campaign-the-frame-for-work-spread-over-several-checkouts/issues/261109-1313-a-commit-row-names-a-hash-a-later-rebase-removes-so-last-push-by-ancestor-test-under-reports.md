A commit row names a hash a later rebase removes, so `last_push` by ancestor test under-reports
---
Plan steps 7 and 14 take a checkout's `last_push` from the newest of its `commit` rows whose short hash is an ancestor of the head read (`git merge-base --is-ancestor`). In the measured case five such rows of one checkout name hashes that resolve to no object in the clone at all. If a rebase after the row was appended is the cause, the campaign's own cycle (commit, pull with rebase, read, push) produces the same on every commit that the rebase rewrites: the lock writes the row with the pre-rebase hash, and the hash that reaches the remote is another one.
---
**Filed by:** orchestrator, Kai Stalmann <ks@qantr.com>

**Evidence.** Reported by the data-implementer on plan step 6, from the consuming project's clone at `56c19983a`, read with `git show` and never from its working tree: the five newest `commit` rows of checkout `cb430046` in that project's `fusion-workbench/orchestrator-events.jsonl` name short hashes that are no object in the clone; the fixture `hooks/lib/__tests__/fixtures/campaign/ax-k2-3-261105.json` therefore records that checkout's newest row whose commit is an ancestor of `56c19983a`, dated 2026-11-03, and says so in the row's `_source`. The orchestrator has not repeated the lookup. *Inference, by the executor and not measured:* the cause is a rebase after the row was written. A commit made in another clone and never pushed, or a row carried in by the union merge from a checkout whose objects were never fetched, would read the same.

**Why it matters for this package.** The overview exists to show whether a held package is being worked. A `last_push` that silently falls back to an older commit shows a working checkout as idle, and the reduced tier of step 7 would report it so from its first run. The decision `261108-2301-how-does-a-working-session-rebase-pull-over-the-log-row-the-lock-just-appended.md` settles how the rebase gets over the row; it does not say what the row's hash is worth afterwards.

**Acceptance.** The cause is measured on the five rows (is each hash reachable in any clone of that project, and does a commit with the same subject and author time stand on the head under another hash). Steps 7 and 14 then state what `last_push` is when a checkout's newest rows name no ancestor of the head: a rule that finds the rewritten commit, or a `note=` line that says rows were skipped and how many, so that an under-report is never silent. A test over the step-6 fixture holds the stated behaviour for `cb430046`.

Resolved: `commitNamedBy` in `hooks/lib/campaign.ts` (`## Which commit a commit row names`) says which commit on the head read a `commit` row names, over one `git log` listing of that head: the one commit whose hash the row's short hash abbreviates; else the one commit carrying the row's subject and an author time within 60 seconds of the row's `ts`, which is what a rebase made of the row's commit; else none, two candidates included. `last_push` is the newest committer time among the commits a checkout's rows name, and every row of that checkout that names nothing and is newer than the row the figure came from is counted in a `note=commit-rows-unmatched` line carrying the checkout, the count and the newest such `ts`, so the under-report is never silent (`bin/fusion-campaign` `## last_push` and `## The notes`). The cause the acceptance asks to be measured stands in `261108-2301-plan-campaign-the-frame-for-work-spread-over-several-checkouts.md` `## Current State`, measured on 2026-11-09 and not repeated by this step: each of the five rows has one commit on the head under another hash, with the row's subject and its author time. `hooks/lib/__tests__/campaign-overview.test.ts` holds the behaviour over the step-6 fixture: the five holders, `cb430046` with three later rows whose commits a forced rebase rewrote before the push, the third reworded as well; the origin holds none of the three hashes, `last_push` is the committer time of the second rewritten commit, and one unmatched row is counted for that checkout and for no other. The function is exported for plan step 14, which attributes commits with it.
